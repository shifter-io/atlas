Browser pulse: targets, outcomes, settings and bundles

The browser pulse measures real-browser targets (a marketplace product page, a search results page, AI answers and others) through each network from dedicated browser hosts. This page is the operator reference for its frozen contracts: target identities (K-BP1), outcomes (K-BP2), the settings file (K-BP3), the run bundle (K-BP4), scheduling (K-BP5) and the manager's ingest endpoint (K-BP7). The code holding them is atlas.browser.contracts and atlas.browser.settings. Snapshot and API fields (K-BP6) are documented with the calculator and the API.

Status: the names, formats and checks exist and are tested, and the orchestrator's planner (job browser_plan, Scheduling) opens the browser batches. The manager's ingest endpoint (Ingest) accepts bundles. The host process (Host) runs the browser batches, seals each run into a bundle and sends it from its outbox (Bundles and outbox).

1. Targets (K-BP1)

Browser targets are rows of configs/targets.toml with engine = "browser", pulse_enabled = false and census = false: the settings file schedules them, never the HTTP pulse or the census. load_targets, and so db-seed, refuses a browser row with pulse_enabled or census true. Their pulse_* columns are unused. A target's version starts at "1"; from the first production try on, a judge or selector change bumps it (see "Versions" in 2a).

For each try, page(context, inputs) builds a PageSpec(url, wait_for, settle_ms) from the settings inputs; interact(driver, spec) may act on the page through a PageDriver (goto, fill, press, click, wait_for, count, text, url, title, screenshot; timeouts in milliseconds); and judge(view) returns an Assessment. 2a. What counts as success

A page answering 200 is not a success: a try is ok only when the browser shows the real content below. The code is atlas.browser.judge (shared steps) and atlas.browser.targets.pages and atlas.browser.targets.ai_types (one class per target, registered in the target registry). Every judge runs the same steps in this order and stops at the first that applies:

  1. a navigation error, already mapped by the transport (the judge never sees it);
  2. a main document answered with 407: proxy error proxy_auth;
  3. a challenge: the site's own challenge signs (below), then the shared challenge markers of outcome.py ("captcha", "just a moment", "verify you are human" and the others) on the title and the first 4 KB of visible text;
  4. a block: the site's own block signs, the shared block markers ("access denied", "you have been blocked", "rate limit" and the others), then the statuses 403, 429 and 451 and the site's own block statuses;
  5. the target's pass condition.

URL paths are matched as path prefixes of whole segments: a redirect to /login or /login/... matches /login, but a profile at /in/loginov-example/ does not. A site's own sign is checked before the shared markers of the same kind. Example: Cloudflare's "you have been blocked" page carries the title "Attention Required!", which alone would read as a challenge.

A page showing the target's own content is not read for markers. A target may say when its page shows its own content (PageTarget.shown): the LinkedIn profile's name and headline, an Instagram or X profile header with a post, a complete AI answer, or the expected text of cloudflare_challenge with no Cloudflare sign. The words on such a page are the content's own ("captcha" in a headline, a post or an answer), so they mark no challenge or block page. The step order stays the same, but the title and the visible text (only the visible text for instagram_web and x_web, whose title is still read) are blank for the site's marks, the shared markers and the rules; the statuses and the marks by path or selector still count. The AI sources and cloudflare_challenge go one step further: such a page is ok right after the 407 step, before every other shared step, since their try's status is the first response's (see below and the cloudflare_challenge row).

A complete AI answer is ok before the page's words. For the three AI sources the order above has one more step: right after the 407, a complete answer (each row's success condition) is ok, before the challenge, block and status steps. The visible text head holds the answer's own words ("captcha", "rate limit", "too many requests", "unusual traffic"), and the try's status is the first response's, so a challenge that cleared by itself before the answer was a 403; neither undoes an answer that was read. The stop signs ("Too many requests", Cloudflare's challenge form, a sign-in dialog or redirect, "unusual traffic") end only a wait in which no answer has appeared yet: once an answer is growing, the wait runs until it stops growing or the wait ends, because a text stop matches the whole body, answer included.

AI answers are never stored. An AI source reads the answer's length and sentence count through the driver inside interact() and keeps only those numbers. The answer text is not logged, not put in the try record (which has no field for it) and not returned. A try of an AI source gets no screenshot once any answer text was shown (answer_chars above 0), whether it is ok or not and whatever [browser] screenshots says, so no screenshot holds an answer either. The questions are fixed, neutral and hold no personal data; the sources are used logged out, from the network's exit. No captcha or challenge is ever solved: a challenge is recorded as one. "Stops growing" means the reply's length is unchanged for 2 seconds, read every half second.

Each failure also records a short reason in the try (captcha_page, dogs_page, no_price, no_title, no_product, not_found, empty_page, sorry_page, consent_page, few_results, authwall_redirect, authwall_page, profile_unavailable, no_name, no_headline, login_dialog, login_redirect, no_profile, no_posts, checkpoint_page, wait_page, challenge_page, cf_block, cf_error_page, no_expect, no_overview, short_overview, no_results, no_prompt, short_answer, no_reply, send_failed, too_many_requests, unusual_traffic, or for the shared steps proxy_auth_status, challenge_marker, block_marker, block_status). A judge returns a PageAssessment: an Assessment plus that reason, whose verdict is always the one its error code implies, so a try is never ok with an error.

For the transport

  • Inputs. Try i of a run uses inputs[i % n] of the target's settings inputs, so a run rotates its list deterministically. target.try_fields(context, inputs) gives the try record's input (as the settings give it) and source (null for the five page targets, the target's own id for an AI source).
  • Selectors. PageSpec.wait_for is a CSS selector list. The transport waits for it, then counts each selector that judge.selectors(wait_for) returns (split at its top-level commas) into PageView.found under the selector's own text. A selector the page lacks counts 0. A judge reads only these counts, the final URL, the status, the title and the visible text head.
  • Expected text. cloudflare_challenge puts its input's expect into the list as body:has-text("..."), so the judge reads it from found. Its interact() waits up to challenge_wait_s for that text or a Cloudflare error page. The host binds the setting with dataclasses.replace(target, challenge_wait_s=...).
  • AI sources. interact() may return named numbers; the transport adds them to PageView.found after the selector counts. The AI sources return answer_chars, answer_sentences and, when an answer appeared, answer_ms (from the question, or for ai_overview the start of the wait, to its last growth). The chat sources' page() returns an AskSpec, a PageSpec that also carries the question. A dismissible cookie or consent dialog shown at load is closed with one click. The wait ends at answer_wait_s or the try's page timeout, whichever is first: the host binds each one that is set with dataclasses.replace(target, answer_wait_s=..., page_timeout_s=...) (the page timeout is the target's timeout_s, else [browser] page_timeout_s); an unset answer_wait_s keeps the default 30 seconds. driver.text(selector) returns the visible text of the selector's first match. The transport never takes a screenshot of a try of a target in contracts.AI_SOURCES whose found holds answer_chars above 0. The visible text head can hold the answer and nothing records it; a complete answer is judged before any marker in it is read (see "A complete AI answer is ok before the page's words").
  • Versions. Every target started at version = "1" and stayed so while no production try has been recorded (owner decision, 2026-11-04): the rule changes made before then, and the live checks that run before the production run (BP-VERIFY-1, BP-TGT-LIVE-1), keep "1", since their tries are no production data. From the first production try on (the 24-hour production run, BP-VERIFY-3), a change to a selector, a sign or a rule bumps the target's version, so tries judged by different rules never share one: ai_overview and ai_chatgpt are at "2", and linkedin_public is at "2" since it also waits for the authwall's heading (BROWSER-BYTES-2).

Engines in the published figures (K-BP6). The calculator never adds Chrome and Camoufox together (calculated/browser.py, BROWSER-ENGINE-FIGURES-1): each browser bucket row carries its run's browser_engine (a run that names none is Camoufox), a target's own figures in a window (its window metrics, outcome_rates and page_load_ms) are those of the engine with the most completed tries there (ties go to Camoufox), named in browser.engine, and browser.engines holds every engine's own figures; see the calculator. Deploy the manager with that calculator before any production target selects engine = "chrome"; an older calculator would add both engines together.

Whole runs in a window (BROWSER-WHOLE-RUN-1, #1266). A browser run counts whole, by its finish time, in the window (24h, 7d, 30d, a day) that holds its end: all its tries, outcomes and page loads, or none, for every browser target and group (calculated/browser.py, the methodology's browser_window_rule = "whole_run"). A run that finishes after the window's end is out of it; one that started before the build's 30 days of raw rows is in no window. See the methodology guide.

Target scores (K-BP6, TARGET-SCORES-1). Each engine's figures, targets.<id>.browser.engines.<engine>.scores, and the main engine's copy, targets.<id>.browser.scores, are {"success": S, "challenge": S, "block": S} with S = {"rate": number|null, "score": number|null, "rank": number|null, "ranked_of": int|null, "status": "ranked"|"not_enough_data"|"too_few_networks"|"all_similar"}: rank-based 1–10 scores among every network of the window label with that engine, score = 1 + 9 × (M − rank) / (M − 1) (ties share the average rank), from at least 100 completed tries (the methodology's browser_min_requests, SCORE-BROWSER-MIN-1, BROWSER-MIN-100-1; a network under it is not_enough_data, left out of every overall and of the ranking), at least 3 ranked networks (MIN_RANKED), and a spread between the best and worst rate of at least the larger of 3 points (TIGHT_RACE_MIN_PTS) and 1.96 (TIGHT_RACE_Z) standard errors of their difference, else every score is null with that status. windows.<label>.browser_overall.<engine> = {"success": {"score", "rank", "ranked_of", "status"}, "targets": [ids used], "weights": {id: difficulty}} weights each ranked page and group target's success score by its methodology difficulty ([browser_difficulty], 1–5; a group without one takes its hardest source's); status ranked or no_ranked_targets. Chrome and Camoufox are ranked apart. The formula and an example are in the calculator reference.

4. Run bundle (K-BP4)

One bundle per run (network × target × country × slot): the node's usual run directory (summary.json, buckets) plus browser/manifest.json, browser/tries.jsonl, browser/samples.jsonl and browser/screenshots/NNNN.jpg (NNNN is the try index; JPEG quality 60, the viewport only, failures only by default). It is packed into outbox/<run_id>.tar.gz with outbox/<run_id>.json beside it (batch id, sha256, bytes, network, target, slot): outbox_paths(root, run_id). The tar is deterministic: sorted members, uid and gid 0, mtime the slot start, gzip level 6.

browser/manifest.json

Format atlas-browser-raw, version 2, built with manifest(...) and checked when read back with check_manifest(document), which also reads version 1 (a Camoufox bundle with no engine block; manifest_engine(document) is camoufox for it):

  • run_id, batch_id, network {provider, product}, target, host (the logical name);
  • country (the batch's), requested_country (null when untargeted) and geo_targeting: they must agree, and a targeted run requests its batch's country;
  • slot, started_at, finished_at: UTC, ISO 8601;
  • tries and outcomes {verdicts, errors}: every verdict and every browser error code, zeros included; each failed try has exactly one code;
  • settings_sha256;
  • engine {name, version, user_agent} (version 2): name camoufox or chrome, the engine of the run's config (browser_engine); the user agent claims the version's major (Firefox/ for Camoufox, Chrome/ for Chrome). Its browsers' identity: the last one the host launched of that engine, else the pinned Camoufox release, or the Chrome [chrome] executable reports (--version);
  • camoufox {release, engine_version, user_agent}, a Camoufox bundle's only (required in version 1, absent from a Chrome bundle): its user agent's Firefox version equals the engine's major version, and the engine block's version and user agent are its own;
  • files [{name, bytes, sha256}]: each member once, browser/tries.jsonl always, never the manifest itself.

browser/tries.jsonl

One line per try, built with try_record(...): i (zero-based), input (the settings input exactly as given: a string, or for instagram_web and cloudflare_challenge the {site, handle} or {url, expect} object; each string at most 2048 characters), source, verdict, error (the verdict must be the one the code implies), status (main document: any three-digit status, 100 to 999, so LinkedIn's 999 is kept), final_url (scheme, host and path: no credentials, query or fragment), timings_ms {queue, context, navigate, settle, total}, bytes_down_est, reason (a lower-case enum from the judge) and screenshot (this try's member or null). A Chrome try also has fingerprint {values, sha256}: the try's fingerprint values (contracts.FINGERPRINT_FIELDS) and the SHA-256 of their sorted, compact JSON, which must match. A Camoufox try has no such field. From version 2 each try also has engine, its run's engine (optional, so the tries of a version 1 bundle still validate). Records never hold page text, answer text, cookies, credentials or proxy user names: fields named text, answer, cookies, username, password, credentials, proxy or token are refused, as is any unknown field.

browser/samples.jsonl

The CPU and memory of the host's browsers while the run ran: one procstats.TreeSampler line a second (at, processes, rss_bytes, cpu_seconds, cpu_percent; PROCSTATS-1) of the host process's whole tree, from the run's start to its end, then one line {"summary": ...} with procstats.summary() of them (samples, RSS average and peak, CPU % average, p95 and peak). The host runs several runs at once on one pool, so a run's samples are the host's, not the run's own browsers'. A run that never started, or whose samples could not be written, has no such member.

Storage object

Only the manager writes it: object_key(prefix, network, target, country, slot) is <prefix>/<network>/<target>/<cc>/<YYYY-MM-DDTHHMMZ>.tar.gz.

  • prefix is the database setting browser.archive_prefix (default browser-files) and never shares the top level of another archive (raw, raw-files, inputs);
  • network is network_slug(provider, product): <provider>.<product> in lower case;
  • cc is the lower-case requested country, or untargeted when the run requested none;
  • the time is the slot start (slot_stamp: UTC, whole minutes; a naive time is refused).

The object holds the exact bytes the host sent; its metadata carries sha256, run-id and batch-id.

5. Scheduling and region (K-BP5)

Browser runs are batches of kind browser. All browser hosts share one runner region: slug browser, region id 20, cloud local, pattern browser(-[a-z0-9]+)?; it is not one of the cloud regions. A host's node tokens are bound to its logical name, and the manager refuses a browser token presenting another host. Per settings target (index i of n) and country, the planner opens one batch per slot of that target's own interval, starting lead_seconds + i × interval / n into the slot; a slot opened late spreads over what is left of it, minus 10 minutes. With plan = "queue" it follows each host's queue instead (below). Hosts take tries, concurrency (browsers_per_host) and timeouts from the settings file, and no try starts after the run's deadline: the slot end minus 2 minutes, or in queue mode its start plus run_deadline_minutes minus 2 minutes. Pulse and census participants exclude browser-region nodes.

Scheduling: the orchestrator's planner

The job browser_plan (atlas.orchestrator.browser) runs every minute, on the minute. It never waits for the hourly calculation: the planners (census, pulse, the hourly pulse job and browser_plan) take their own advisory lock, batches.PLAN_LOCK, one planner at a time, and never the calculation's, which a calculation holds for its whole run (BROWSER-PLAN-LOCK-1); only a schema migration holds both. It plans only while the database setting browser.enabled is true (default false) and the settings file at the setting browser.settings_file (default none) loads with enabled = true; otherwise the job records skipped with the reason. The file is parsed again only when its SHA-256 changes. A file that cannot be read or does not validate raises the alert browser_settings_invalid (one alert whose occurrences count the ticks; it names the field, never a value) and nothing is planned; the alert is acknowledged once the file loads again. Before opening any batch it checks that every target of the settings file has its row in targets. A missing one (a database seeded before that target was added to configs/targets.toml) raises the alert browser_targets_missing (major, one alert whose occurrences count the ticks), which names the missing ids and the fix, atlas db-seed --only targets; that target is not planned, the others are planned as usual (each keeps its place in the slot), and the job result lists it under missing. The alert is acknowledged once every target is there.

  • Per-target slots. Each [[target]] has its own interval: its slot is floor(now / every_minutes) since the epoch, so an hourly target opens every hour and a 120-minute one every even UTC hour. The slot gets one batch of kind browser per [schedule] countries entry, in region 20, with scheduled_for = the slot. With the targets in file order (index i of n), target i starts lead_seconds + i × every_minutes / n into its slot, so one host's targets spread over the slot. A batch already opened for the slot is never opened again.
  • Late opening. A slot first planned more than 60 seconds after it began (a restart, the planner just switched on) spreads from now over what is left of it minus 10 minutes: target i starts now + lead_seconds + i × (slot end − 10 min − now) / n, and a target whose start would fall after the slot end minus 10 minutes waits for its next slot, which opens on time.
  • Runs. In slots mode every new batch gets a queued run for each network (product) with a node in the browser region. A batch with none closes at once as failed. Runs are handed out, reaped (not_started, stale) and reported like every other run.
  • Region. The browser region's runner_regions row (20, browser, local, its pattern) is not seeded from configs/regions.yaml; the planner and the first browser token insert it when missing. A host or region name that no cloud pattern matches but browser(-[a-z0-9]+)? does resolves to it (regions.resolve_region; regions.region_id gives the id of either kind). Census, pulse and load never plan there: a network with only browser nodes gets no census or pulse run and no no_node alert.
  • Tokens. atlas node-token --region browser --host browser-<n> --provider … --product … creates the network's browser node bound to that logical host name (kept in nodes.host) or rotates its token; without --host, or with a name not of the form browser-<n>, it is refused. One network has one browser node, on one host.

Queue mode: once a period, evenly spread (BROWSER-QUEUE-1)

With [schedule] plan = "queue" every (network, target, country) runs once per queue_period_minutes (22 hours in production since BROWSER-CYCLE-22H-1, a UTC day by default), exactly one period after its last run, and each host runs its own deterministic queue (atlas.orchestrator.browser_queue, pure): one run starts every gap, heavy runs alternate with light ones, and the hosts are offset from each other, so the hosts, the manager and the target sites see a flat load.

  • Gap and offset. Host h of H (in [[host]] order), with n networks, t targets and c countries: gap = period / (n × t × c), and the host starts h × gap / H after the period start plus lead_seconds.
  • The round. The targets sorted by browser_seconds, highest first (ties keep the settings order), then interleaved heavy and light: [1st, last, 2nd, second-to-last, …], once per country (the countries in settings order, each with the whole round).
  • Networks. A period has n rounds. Position p of round r runs network (p + s × r + c) mod n in every period and starts at period start + lead_seconds + host offset + (r × t × c + p) × gap, down to its whole minute (X-TARGET-1: a run's bundle slot is its start, and a slot is a whole minute, also when the gap is not, as with 54 runs a period). So every network meets every (target, country) exactly once a period, at the same place in each period: it is revisited exactly every period (BROWSER-CYCLE-22H-1). A period that is not a UTC day moves the hour of day at which they meet: 22 hours, 2 hours earlier each day, the same hour again after 11 days. The step s is the first of 1, n−1, 2, n−2, … that is coprime to n and runs no network twice in a row, across rounds and across periods, also in the daily queue below (with s = 1, a round of t × c ≡ 2 (mod n) positions would end and start on the same network); with n ≤ 3 there may be none, and s = 1.
  • The switch (queue_start). The periods count from queue_start, a UTC midnight, and c is the daily queue's c of the day before it. Before queue_start the daily queue it replaces runs, as before BROWSER-CYCLE-22H-1: period 1440 from the epoch and c = d, the day's index since the epoch, so each day moved every pair one round later (with 6 networks it was revisited every 28 hours, 7/6 of a day, and once every 6 days after 4 hours, and a 24h window missed it about 4 hours in every 28). A file without queue_start keeps that daily queue, so a deploy changes nothing. From queue_start each pair keeps the round of its last daily run: its first run is 22 to 24 hours after its last daily run with a 22-hour period, none runs twice and none is skipped, and no network runs twice in a row across the switch. The planner plans the daily queue's entries before queue_start and the new queue's from it, so the file can be installed at any time before queue_start; installed after it, the new queue starts at once and the entries already past in its first period are not run. A missed entry around the switch catches up on the queue in force at the time, as below.
  • Batches. Each queue entry gets its own batch: kind browser, its target and country, scheduled_for = start_at = its start, opened when its start is at most 2 minutes away, with exactly one queued run, for its host's node of its network (nodes.host); with no such node it closes at once as failed. A batch is never opened twice.
  • Catch-up. An entry whose start passed more than 60 seconds ago with no batch (an orchestrator restart, or its host was full) starts at the next whole minute when its host has a free place and no open run of its network (BROWSER-COVERAGE-1: no browser idles while a run waits; on 17 Nov 2026 a run waiting for browser-2 started 54 minutes late at the next position, another was pushed into an outage); otherwise it catches up at its host's next position from now that no other catch-up holds and whose own run is on another network: a batch keeping its scheduled_for, with start_at that position; several missed entries take one position each, in start order. Only if a run starting there can finish (start + run_deadline_minutes) before the entry's start one period later; otherwise the entry is skipped: a batch with status skipped and no run, so it is decided once, and the alert browser_run_missed (minor, one per host and day, its occurrences counting the skipped runs). Entries a period old, and those before a host's first on-time batch (queue mode just switched on, a new host), are never missed.
  • Lost runs (BROWSER-COVERAGE-1). An entry whose run the reaper failed as not_started (its host cut off from the manager, or full) is run again in the same period, once its node is online again: it catches up as above, at its host's next free position, if a run starting there can finish before the entry's next start; its batch is reopened there (status scheduled, start_at that position, the run queued again; "rerun" in the planner's result), so scheduled_for keeps the entry's own start. One that can no longer finish in time stays failed. Before, it waited a whole period: one lost run made 44 to 50 hours between two counted runs, past the coverage alert's 36 (the night of 17 to 18 Nov 2026: 9 runs never started while the three hosts were cut off for 88 minutes). A run failed as stale (its node went silent mid-run, or its upload never completed) is run again the same way once its deadline has passed with nothing uploaded (until then its node may still finish it), its start, counters and progress cleared; one failed past its deadline (slow, not lost) or by its node is not. A run queued again keeps the reaper's error until it ends: should the lost run's own bundle still arrive (its node finished it cut off from the manager), the upload is taken as the run's result, a late upload, and the new run stops (BROWSER-COVERAGE-1).
  • Deadline and slot. A queue run's deadline is start_at + run_deadline_minutes minus 2 minutes (browser/run.py run_deadline), so a run started at 23:30 has until about 02:28; slots mode keeps the slot end minus 2 minutes. Its bundle's slot (and archive key) is its own start_at, unique per network and target since a catch-up never shares a position with its own network's run.
  • Runs per host. A host runs at most browsers_per_host browser runs at once (BROWSER-HOST-LIMIT-1, atlas.orchestrator.browser_hosts). Its open runs are those of batches starting within 2 minutes or earlier: those handed to its node (running, started or not) and those queued that began at most batch.start_grace_seconds ago. The planner opens an entry, or decides its catch-up, only while its host has fewer; otherwise the entry waits for a later tick and starts as soon as a place frees (as above); one that could no longer finish before its next start is skipped even while its host is full. A catch-up decided earlier for a later start counts only from 2 minutes before it, so it can still put its host one over: the alert browser_host_over_limit (major, one per host, its occurrences counting the minutes) is raised while a host has more open runs than its limit and acknowledged once it has no more. Slots mode has no such limit.
  • Stuck runs. A run's last_progress_at moves only when its counters do (requests, successes, bytes and the rest; any kind of run), so a node that keeps posting the same counters no longer looks alive. The reaper fails a browser run whose counters have not moved for browser.stall_minutes (database setting, default 30; error stale) or, in queue mode, that is still running run_deadline_minutes after its start_at (error deadline; in slots mode, or while the settings file cannot be used, only the stall rule applies). That frees its place on the host. Its node is told to stop at its next progress post, except a run failed as stale or not_started (the node was only silent to the manager: on 18 Nov 2026 the three hosts were cut off for 88 minutes and four runs with every try done were deleted): until its deadline it may finish, its progress is kept, and its upload is ingested late (BROWSER-COVERAGE-1). Each such run raises the alert browser_run_abandoned (major, one per host and UTC day, its occurrences counting the runs, the text naming the host, batch and target). Census and pulse runs keep batch.stale_seconds.
  • Load check. A host's estimated load is Σ browser_seconds of its runs in a period ÷ (browsers_per_host × period); over 100% is refused.

The owner's numbers. 18 networks on 3 hosts (6 each), 9 targets, 1 country, 100 tries, 2 browsers per host, every 22 hours from queue_start (BROWSER-CYCLE-22H-1): 18 × 9 × 100 = 16,200 requests a period, about 17,700 a day (+9%), 54 runs per host a period. 22 hours plus the longest run (about 1.2 hours) and a start's delay fit in 24, so every 24h window holds a complete run of every (network, target), and so of every card target and of each source of social_web and ai_answers; 21 hours would be too tight (an 87% load). 6. Ingest endpoint (K-BP7)

Hosts upload a bundle through the existing node route and bearer token: POST /v1/results?batch_id=<id> with Content-Type: application/gzip, X-Content-SHA256: <64 hex> (required for kind browser, verified for any kind when present) and X-Bundle-Id: <run_id> (it must equal the bundle's summary.run_id). The manager checks the checksum while it receives the body, bounds concurrent ingests, archives the exact bytes once, ingests the run directory into the database and keeps nothing.

ReplyMeaning · what the host does
200 {"ok": true, "ingested": true, "status", "run_key", "archived": {"key", "sha256"}}Stored, or an idempotent replay. The host deletes its bundle only when archived.sha256 equals its own.
200 {"ingested": false}The run was killed or skipped. The host deletes its bundle.
400 checksum_mismatchNothing kept. The host re-hashes and retries once.
409 bundle_changedAn object with other bytes exists; it is never overwritten, and the alert browser_bundle_changed is raised. The host keeps its file, marked.
408, 429 (Retry-After), 503A body not received in time, busy, a duplicate in flight, or storage or the database unreachable. Retried with backoff.
any otherKept with a .conflict or .rejected marker and a log line.

confirmed(reply, local_sha256) is the single rule a host uses to delete a bundle: true only for a 200 with ingested: true and an equal archived.sha256, or a 200 with ingested: false; false for every other status and for a missing or malformed field. Nothing unconfirmed is ever deleted, and a host never reports an unconfirmed browser upload as failed.

What the manager does (orchestrator/browser_ingest.py)

  1. Receive. The body is streamed to a private temporary file under results.max_upload_bytes and within results.upload_timeout_seconds (default 600; past it 408 and the file is removed) while it is hashed; a different sha256 answers 400 checksum_mismatch and nothing is kept. A browser node that never registered gets 403.
  2. Bound. At most browser.ingest_concurrency bundles (default 4) are received and processed at once by the orchestrator process, checked before the body is read (503 ingest_busy, Retry-After: 30), and one per (batch, network) by any process: a PostgreSQL advisory try-lock held on a connection of its own (429, Retry-After: 10 for a duplicate already in flight).
  3. Run state, read again under the lock: killed or skipped answers 200 ingested: false; a finished run with a run_key is a replay, answered 200 only when its object holds the same sha256 (no database change); running, uploading, or failed by the reaper without a run_key (a late upload) continues; anything else is 409.
  4. Unpack with the run archive's limits (the K-BP4 browser/ members besides) and the summary's declared artifact rows within results.max_artifact_rows, then check network, target, batch, country and run id against the node, the batch, X-Bundle-Id and browser/manifest.json, validate the manifest (version 1 or 2) and the size and sha256 of every file it lists. The manifest's requested_country and geo_targeting must agree with the run's summary, and so must its engine with the summary's config.browser_engine (none in a version 1 bundle: Camoufox). The engine is part of the run's config and so of its stored scope and pool: Chrome runs and Camoufox runs of one target and network are kept in different scopes. (Camoufox runs from version 2 bundles name their engine, so they get one new scope beside that of the version 1 runs.) A mismatch answers 400, fails the run and raises results_rejected; a manifest naming another host answers 403.
  5. Archive the received bytes once to <browser.archive_prefix>/<provider>.<product>/<target>/<cc>/<slot>.tar.gz, where cc is the summary's requested country or untargeted (D11), with the metadata sha256, run-id and batch-id. ARCHIVE-1's Spaces.put_verified does HEAD, PUT when absent, HEAD again, and compares bytes, MD5 and sha256. An object already there with the same sha256 counts as stored; one with another sha256 answers 409 bundle_changed with the alert browser_bundle_changed and is never overwritten.
  6. Database: storage.ingest of the run directory without browser/, without per-IP rows (idempotent by run id), then nodework.finish_run. A late run goes back to uploading (and its batch, if the reaper closed it, back to running) first, so it becomes done with its run_key and the batch closes again with its status recomputed.
  7. Clean up: every temporary file is deleted before the reply, whatever the answer. The manager keeps nothing; the generic raw spool (raw.spool_dir) is skipped for kind browser, the bundle being archived per run.
  8. Reply 200 as in the table above. The storage or the database unreachable answers 503 at any step; a retry finds the stored object and the ingested run and finishes without duplicates.

Deploy order (manifest version 2). A manager older than CHROME-PROD-1 refuses a version 2 manifest (400, the run failed). So the manager's framework with this change goes out first, and only then the hosts' framework, which writes version 2: the new manager reads both versions, so hosts still on version 1 keep uploading meanwhile. Rolling back goes the other way round: the hosts first, then the manager.

Uploads from the three minis at once are therefore safe: each bundle has its own temporary directory, run lock and object key, and an interrupted upload is completed by the next try. Before an upload the host must have registered, and its token is bound to its host's logical name (D2): /v1/register refuses a browser token with another host (403), and so does an upload whose manifest names another host. Other kinds keep their behaviour; a pulse or census node may send X-Content-SHA256 too and then gets 400 on a mismatch.

Manager runbook

  • Settings: archive.spaces_file (the [spaces] file ARCHIVE-1 deploys; production) and optionally browser.archive_prefix (default browser-files) and browser.ingest_concurrency (default 4; each ingest holds one extra database connection). browser.archive_dir writes the same keys to a local directory instead of Spaces, with each object's metadata in <object>.meta.json: for staging (BP-VERIFY-1) and tests only, never in production. Without either, a browser upload answers 503 archive_not_configured.
  • Targets: campaign manager orchestrator-enable --apply runs atlas db-seed --only targets on the manager before it starts the orchestrator, so every browser target of configs/targets.toml has its row (operators' schedules are kept; regions and countries are not touched). On an alert browser_targets_missing, run that command with the manager's database file (--database-file /etc/atlas/database.toml) or rerun orchestrator-enable --apply; the next tick plans the targets and acknowledges the alert.
  • Browser settings (BROWSER-HOSTS-SETTINGS-1): the production file is private; its reviewed template is configs/browser-pulse.production.example.toml (the 22-hour queue from its queue_start, 2 browsers and a new profile per request on each mini, the owner's engine and browser_seconds per target, the 24-hour run's 18 networks on browser-1 to browser-3). To make the private file, copy the template outside the repository, replace every placeholder inputs with the real ones and change nothing else (a change to the rest goes through a reviewed change of the template), set enabled = true when the hosts may run, and check it with browser-node --check (it reports queue_load, 0.832). queue_start must be a coming UTC midnight when the file is installed on the manager (BROWSER-CYCLE-22H-1): set it to the switch day if the template's date has passed, and install the file before that midnight; the daily queue runs until then, so the earlier the better. Install the same file, mode 0600, on the manager at the path of the database setting browser.settings_file (the planner also needs browser.enabled true, K-BP5), and on each mini as settings.toml in the host state directory (Host): one file, so every bundle records the same settings_sha256. Never commit it.
  • Alerts: browser_bundle_changed (major; an archived bundle and a new upload of it differ: compare the two before anything is deleted, the host keeps its copy marked), results_rejected and ingest_failed (a bundle or its data was refused; the run failed).

Manager browser port (mutual TLS)

The minis' home addresses change, so the manager's firewall does not list them. The orchestrator listens for them on a second port, the browser port 8444 (HTTPS), which the firewall opens to every address (0.0.0.0/0, ::/0). There the TLS handshake requires a client certificate signed by the manager's browser CA: without one, or with one of another CA, the connection fails before any route runs. The request then needs a browser host's token (region browser), and the certificate's CN must be the logical host name that token is bound to (browser-1, ...); otherwise it answers 403 (the browser port takes only browser host tokens or the client certificate is not the token's host). Only the node API (/v1/...) is served on the browser port: the admin API and /health answer 404 there. Port 8443 serves the pulse nodes (by tag), no client certificate; it refuses a browser host's token (403), so a browser token never works without its certificate. The admin API is on neither port: it has its own loopback listener (campaign guide, cutover runbook).

Certificates. Each mini makes its own key, and the operator's Mac holds the CA that signs and revokes (steps below). The manager holds only the CA's certificate and its revocation list, installed with campaign manager browser-trust. It never holds a host key or the CA key (campaign guide: the switch from the CA an earlier version made on the manager, one mini at a time). A staging manager uses its own CA folder. Start the host with --orchestrator https://<manager>:8444 --ca-file ... --client-cert ... --client-key ... (Host, below). A certificate is valid 90 days: before it ends, make a new key and certificate in a new folder (steps 2 and 3) and restart the host on them.

Keys made on the minis, a CA on the operator's Mac (SEC-MINI-KEYS-1).

  1. The CA, once, on the operator's Mac: atlas campaign manager browser-ca --ca-dir CA_DIR makes, with the system openssl, an owner-only folder holding the CA key ca.key (EC P-256; it never leaves the folder: keep the folder backed up offline), its certificate ca.crt (CN atlas-browser-ca-<date>, 10 years, signs certificates and revocation lists), an empty revocation list ca.crl and openssl's records (index.txt, serial, crlnumber, issued/). It refuses a folder that already holds a CA.
  2. The key, on the mini: atlas browser keygen --host browser-1 --out NEW_DIR makes NEW_DIR/browser-1.key (EC P-256, mode 0600, never printed) and the signing request NEW_DIR/browser-1.csr, and prints their paths and the request's SHA-256. It never replaces a key: use a new folder, so the running host keeps its current pair until it is restarted on the new one. Copy only the .csr to the Mac.
  3. The certificate, on the Mac: atlas campaign manager browser-sign --ca-dir CA_DIR --host browser-1 --csr browser-1.csr --out DIR checks the request's signature and writes DIR/browser-1.crt (mode 0600; CN is always --host, whatever the request names; client authentication only; 90 days); compare the printed csr_sha256 with the one the mini printed. Copy only the .crt back into NEW_DIR on the mini (mode 0600) and restart the host with --client-cert NEW_DIR/browser-1.crt --client-key NEW_DIR/browser-1.key.
  4. Revoking, on the Mac: atlas campaign manager browser-revoke --ca-dir CA_DIR --host browser-1 revokes every certificate of that host that is still valid and writes a new ca.crl (next update in 10 years: the list is installed on the manager, never fetched, and an expired list would refuse every host). browser-trust --apply then installs it on the manager.
  5. The browser port loads the list with atlas orchestrator ... --client-ca CA_BUNDLE --client-crl CRL_FILE: when the file holds a list, the handshake refuses a certificate it revokes, and a certificate of a CA in the bundle that has no list in that file. An empty file checks nothing (only while the hosts of a retired CA, which has no list, are still being switched); a missing file stops the orchestrator from starting.

The reported user agent is the standard Firefox one for the engine (user_agent(engine_version, os)): its Firefox version always equals the engine's major version, and a host refuses to start otherwise.

7. Install (D7)

Only browser hosts install the browser. uv sync --locked --extra browser adds the exactly pinned Camoufox Python package and Playwright with their locked dependencies; a plain uv sync --locked (CI, the orchestrator, Linux pulse nodes) installs none of them. Browser hosts add --no-dev (uv sync --locked --no-dev --extra browser): the dev group's cryptography has no macOS x86_64 wheel, so the Intel minis cannot install it. On its first launch the camoufox package downloads its pinned fingerprint model (a SHA-256-checked GitHub release asset) once; host code imports camoufox, never fpgen directly, because import fpgen fetches an unpinned model.

The browser itself is downloaded at run time, never vendored: atlas browser fetch --dest DIR [--platform darwin-arm64|darwin-x86_64|linux-x86_64] downloads the one pinned release's build for this machine (or the named platform) over https, checks its size and SHA-256 before unpacking anything, unpacks it into DIR/<release>/ (plain relative files and directories only, no links) and moves it into place atomically. It prints JSON with the release, the engine (Firefox) version and the executable path. A second fetch of a verified install downloads nothing; any mismatch is a refusal that leaves nothing behind, and an existing DIR/<release>/ that is not the verified build is refused, never overwritten. release.executable(DIR) returns the binary of a verified install.

The pin lives in src/atlas/browser/release.py: RELEASE, ENGINE_VERSION and one BUILDS row per platform (URL, SHA-256, size, executable). The minis are Intel, so the darwin-x86_64 row is required. To bump it, open a PR that changes the release and every row to the new release's URLs, sizes and SHA-256s (from the release's published asset digests, checked against a real download), and the camoufox pin in pyproject.toml to the package version paired with that browser release (its browser-pin.json), with Playwright inside that package's range, and keep the indexed-zstd constraint ([tool.uv]) only while some platform would otherwise build it from source; regenerate uv.lock remotely and fetch the new build once on Linux and on an Intel Mac before merging.

8. Runner

A browser target runs through the ordinary runner, so it gets the same counters, buckets and summary as an HTTP run: runner.run(config, sink, RunOptions(targets=..., transport_factory=BrowserTransport.factory(pool, recorder, browser=settings.browser, settings=target_settings, deadline=...))). Four modules make the engine (src/atlas/browser/):

  • driver.py is the only module that imports Playwright or Camoufox; it also drives the second engine, the host's Google Chrome (launch_chrome, below). launch(release.executable(DIR), locale=..., headless=...) starts the pinned browser through Camoufox's own launch options: the fingerprint OS is the host's (macos or linux), locale and headless come from [browser], and geoip is off, because its lookup is a request outside the proxy. A browser host sends nothing outside the try's proxy except to localhost (background.py): Camoufox starts with its background services off (Firefox preferences: no media plug-in download, so no Widevine or OpenH264, about 18 MB a fresh profile used to fetch; no remote settings or Normandy, captive-portal or connectivity check, browser or add-on update, safe browsing or network location; no fallback from a refused proxy to a direct connection) and with a browser-wide proxy that refuses everything (localhost:9, where nothing proxies), so only a try's context reaches the network, through its own proxy. The live check (tests/test_browser_live.py) lists the browser processes' connections every second during a launch, a try and about 40 s of idle, and finds none but to localhost. Contexts are plain Playwright contexts with the launch's identity; Camoufox's per-context identity is not used, since it also looks up the proxy's exit address. context(proxy, block, timeout_ms, country=..., seed=None) takes the run's requested_country from the transport and gives the context that country's place (geo.py, below) through Playwright's own context options, which Camoufox 0.5.9 honours (an in-page check on a live try showed the time zone, offset, languages and Accept-Language follow them): locale is the country's language list (US: en-US,en, so navigator.languages is ["en-US", "en"], as at launch), timezone_id and geolocation are the drawn zone's, and Accept-Language is the country's. The place is drawn from a seed: the handle's seed and its try count, or a seed passed to context(). A run without a country (an untargeted network) keeps the launch's [browser] locale and the host's time zone. Every process serves every country, so the pool keeps none per country.
  • gate.py: Gate(limit), a budgeted network's tries and gateway connections on its host (BROWSER-BUDGET-1, Runner): tries lets one try in at a time; acquire() gives a Lease once fewer than limit are held, closing the lease idle longest while it waits; the relay marks a lease busy with every byte and releases it when the connection ends; stats() gives the limit, peak, waits and closed idle connections since the last call.
  • geo.py: the one per-country table both engines draw from, with no Playwright import. Per country: the locale, the languages (navigator.languages) and their Accept-Language (the first unweighted, then q=0.9, 0.8, ...), and the time zones a user there has, each with its main city's latitude and longitude (accuracy 100 m). US: en-US, en-US,en;q=0.9, New York, Chicago, Denver and Los Angeles. A country without an entry is refused (GeoRefused, which stops the run like a refused user agent). The geolocation permission is never granted, so a page sees the coordinates only as a real user who allowed it would. Nothing is looked up: geoip stays off on both engines.
  • pool.py: BrowserPool(size, launch, recycle_after=...), one per host and shared by every run on it (browsers_per_host processes). async with pool.browser() leases one process for one try; leases are granted first in, first out, so concurrent runs interleave. A process is launched on first use, replaced after recycle_after tries, and replaced at once when a lease ends with it disconnected (a crash; that try records browser_error), or when a lease is granted with it disconnected (it died while idle). stats() gives leases, waits, launches, recycles, crashes, closes and the resident memory of the host process's descendants. Closing the pool closes every browser and its driver; a lease still held is closed when it ends, and nothing launches after the close. Every launch ends in exactly one recycle, crash or close.
  • transport.py: BrowserTransport, the runner's Transport.
  • Hung browsers (IDLE-TIMEOUT-1). A try still running idle_timeout_s past its own longest time (the page timeout plus the target's answer or challenge wait, try_seconds), counted from its browser lease, is cancelled and recorded as a timeout with reason idle, and its browser is abandoned: the pool closes it when the lease ends and launches another, and the run goes on with its next try. Closing a try's context, and the pool closing a browser, each wait at most 30 seconds (pool.CLOSE_S); a context that does not close abandons its browser too (driver.BrowserHung), so a hung Chrome never holds a lease or a cancelled run. A run whose counters have not moved for stall_minutes is stopped by its host and reported failed with error stalled (run.StallWatch); the manager fails such a run on its own after browser.stall_minutes too.

Chrome engine

driver.launch_chrome(executable, country=..., headless=..., seed=None) returns a handle with the Camoufox handle's interface (alive(), context(proxy, block, timeout_ms, country=...), close(), identity), so the pool and the transport use it unchanged. Its Playwright-free helpers are in browser/chrome.py.

  • Detection. The executable is [chrome] executable, which defaults to /Applications/Google Chrome.app/Contents/MacOS/Google Chrome (chrome.DEFAULT_EXECUTABLE). <executable> --version must print Google Chrome <major>.<minor>.<build>.<patch>. A missing or non-executable file, other output, or a major below CHROME_MIN_MAJOR is refused with ChromeRefused. The minimum is 151, the one Chrome the Playwright 1.62.0 release notes name as tested. A major above CHROME_TESTED_MAJOR runs, with one warning per version. identity is {engine: "chrome", version, user_agent}.
  • One profile per try. Every context() starts Chrome with Playwright's launch_persistent_context on a new profile directory (mode 700, under the host's temp folder, named atlas-chrome-*), with the try's proxy, fingerprint and resource blocking. The context is closed and the directory deleted however the try ends, a crash included. A pool of N handles therefore runs at most N Chrome processes, each for one try. launch_chrome checks the user agent on a first profile, which is also deleted. That Chrome's proxy refuses everything (localhost:9): Chrome does not fall back to a direct connection, so its start-up services (Google's accounts, client services and component downloads) cannot reach the network from the host, and the check page is fulfilled locally. A try's Chrome sends all its traffic, start-up services included, through the try's proxy.
  • Fingerprint (owner's option A: Playwright's own options and a small init script, no extra dependency). Each try draws its values from a seed: the handle's seed and its try count, or a seed passed to context(). The same seed always gives the same values. They are a real macOS screen size (1440×900 or 1512×982 at scale 2; 1680×1050, 1920×1080 or 2560×1440 at scale 1), from geo.py, the country's locale and Accept-Language (US: en-US), one of the country's time zones (US: New York, Chicago, Denver or Los Angeles) and that zone's geolocation, and navigator.hardwareConcurrency (4, 6, 8, 10 or 12) and navigator.deviceMemory (8 or 16). The last two are getters on Navigator.prototype whose toString is the native getter's. The country is the run's (context(country=...)), else the launch's; one without a table entry is refused. navigator.platform, canvas, WebGL, audio and fonts are never changed. The page carries page.fingerprint: the values and the SHA-256 of their sorted JSON (the geolocation follows from the time zone, so it is not a value of its own). The transport records it in the try's fingerprint.

One try

  1. The proxy is config.proxy.resolve(context). An HTTP proxy is used with its username and password. SOCKS5 with credentials is refused before any traffic, since the browser cannot authenticate to it: the try records proxy_connect with reason socks5_auth_unsupported, and the host logs the network once (the pool keeps the logged networks).
  2. queue: wait for a lease. context: a new context through the proxy, with every request of a block_resources type or matching a block_urls pattern aborted at the route level, and cache_urls served from the host's public asset cache ([browser], or the target's own rules); navigation returns at wait_until; the context is closed however the try ends.
  3. navigate: load the page, within page_timeout_s (or the target's timeout_s). A failed navigation is mapped by classify_navigation_error; its reason is the lower-cased error name.
  4. settle: on google_search, a consent page or form that hides the results is accepted with one click; then the wait for wait_for, the target's settle_ms and its interact().
  5. The PageView (final URL, main document status, title, first 4 KB of visible text, selector counts, then the named numbers interact() returned) goes to target.judge(). A returned name that is also a selector, or a value that is not an integer, is refused as browser_error.

The Outcome's latency_ms is navigate plus settle: the wait for a browser is not latency. status is the main document's. bytes_up and bytes_down are the try's wire bytes, exact (bytes_exact true; BYTES-TRUTH-1): the context's proxy is the try's own relay (browser/relay.py), an asyncio forwarder on 127.0.0.1 and an ephemeral port that passes every connection to the real gateway byte for byte (credentials unchanged, never logged) and counts both ways, so the CONNECT or SOCKS5 exchange, TLS, headers, uploads, failed sub-requests and aborted loads all count. A try cut at its deadline or ended by a browser error keeps what crossed before, every byte the gateway delivered included: the relay counts a byte when its gateway socket receives it, and as a cut connection closes it adds what is still unread in the socket (FIONREAD), so a response tail the browser never got still counts (RELAY-TAIL-1); a gateway that refuses the connection or cannot be reached records 0, and the relay answers an HTTP proxy's 502 so the try stays proxy_connect. A network with a connection budget (daily/budget.py, proxy-cheap; the budget is the provider's, so its products would share one) has one Gate on its host (browser/gate.py, BROWSER-BUDGET-1): its tries run one at a time (the wait is in the try's queue timing; the run's recorded concurrency is unchanged), and its relays hold at most budget.browser_connections (its BROWSER_RESERVE, 8; 10 until PC-BUDGET-1) gateway connections at once, on either engine. A connection over the limit waits before its gateway side opens; while one waits, the gate closes the connection idle longest: its last byte came from the gateway (an answer ended) IDLE_S, 1 s, or more ago, so the browser's idle keep-alive tunnels cannot hold the page back, and the browser reopens a closed one when it needs it. A connection whose last byte went to the gateway is waiting for an answer (a CONNECT, a TLS handshake, a slow first byte), which a browser would not resend on a fresh connection: it is closed only after PENDING_S, 10 s (a browser's HTTP/2 window update or ping acknowledgement must not keep an idle connection open for ever). A network without a budget has no gate. bytes_down_est, the summed body sizes of every response the context saw, stays in the try record as a cross-check; a try refused before its context opened (SOCKS5 with credentials) has no relay and falls back to it, inexact. The try record carries timings_ms {queue, context, navigate, settle, total}; a step that did not run is null. Every try goes to the recorder, try_done(record, screenshot), with a validated tries.jsonl record; the default recorder keeps nothing. A screenshot (JPEG quality 60, the viewport) is taken per screenshots: failures (default), all or none, but never of a try of an AI source (contracts.AI_SOURCES) whose found holds answer_chars above 0, whatever the setting.

User agent (D7)

At launch the driver reads the engine version and navigator.userAgent. When the user agent's Firefox major is not the engine's, every context gets contracts.user_agent(engine_version, os) instead; when even that does not show, the launch is refused (UserAgentRefused) and the run fails. Browser.identity is the manifest's camoufox block.

Chrome: on every new profile, navigator.userAgent must claim Chrome/<major> and navigator.userAgentData.brands must hold "Google Chrome" at the same major, the one --version gave. A headless Chrome (HeadlessChrome) does not. Its page then gets CDP's Emulation.setUserAgentOverride with Chrome's standard user agent and the userAgentMetadata of a real Chrome of that version, from which Chrome also sends the Sec-CH-UA headers. navigator.platform is left as it is. When the user agent and the brands still disagree, the result is UserAgentRefused. The override covers the try's page only, not workers or popups.

Limits

  • Deadline: RunOptions(deadline=...) starts no try at or after it and cancels the tries still in flight when it passes. A cancelled try has no Outcome and no recorder call, so tries.jsonl holds no line for it. The transport's own deadline (BrowserTransport.factory(..., deadline=...)) is the backstop for any other caller: it cancels a try still running at the deadline plus one page timeout and records it as timeout, reason deadline.
  • Every Playwright action of a try (clicks, waits, reading the page) times out after the page timeout, never Playwright's own 30-second default. A consent page without its accept control is not clicked; the judge reads it (consent_page).
  • Refused proxy credentials: Firefox gives up with NS_ERROR_PROXY_CONNECTION_REFUSED (seen live with the pinned release), which the K-BP2 table maps to proxy_connect; proxy_auth appears only when a 407 is the page's own status.
  • Any other exception, a browser crash included, is browser_error, with the exception's class name, lower-cased, as its reason; a refused user agent ends the run.
  • Live check: sh scripts/ci/browser_live.sh, remote only (a disposable Linux server, the pool's Mac class). It installs the pinned uv when absent, uv sync --locked --no-dev --extra browser, fetches the browser and runs pytest -m browser_live with pytest at its uv.lock versions: the real browser against tests/browser_site.py, a local site with one page per outcome behind a local authenticated proxy. CI never installs a browser; there the live tests skip.

9. Host

One process per browser host runs every network the settings assign to it (src/atlas/browser/node.py; a run's slot, deadline and try timeout, its timing recorder, transport and sink, and the host's size-rotated JSON log are in browser/run.py):

atlas browser-node --settings STATE/settings.toml --state STATE --host browser-1 --orchestrator URL [--ca-file STATE/campaign-manager.orchestrator.crt] [--client-cert STATE/browser-1.crt --client-key STATE/browser-1.key]

For the orchestrator on the manager, URL is https://<manager>:8444 (the browser port, mutual TLS), --ca-file the manager's own certificate, copied from beside the inventory: the host then trusts that certificate alone, and --client-cert/--client-key the host's own key and the certificate the Mac's CA signed for it (keys), which it presents. Both client files must be regular files owned by the host's user with mode 0600, and they go together; otherwise the start is refused. Plain http:// is refused unless the orchestrator runs on the same machine; see the README, Nodes and the manager's certificate.

It loads the settings and takes that host's [[host]] view. For each network provider/product it reads STATE/networks/<provider>.<product>/{provider.toml, credentials.toml, node.token}; each must be a regular file owned by the host's user with mode 0600 (no link is followed), and a missing or readable file stops the start. Each network is one ordinary node agent (BrowserAgent, a atlas.node.NodeAgent whose registry, config_options and run_options hooks come from the host) with its own token, registered as region browser with the host's logical name, working in STATE/runs/<provider>.<product>/. All of them share one BrowserPool of browsers_per_host browsers, launched on the first try: Camoufox from STATE/camoufox/<release>/, Chrome from [chrome] executable (detected at start when a target runs on Chrome: a missing or too old Chrome stops the start). Each engine the targets use has its own pool on it (pool.engine(name)): the host never has more than browsers_per_host browsers open whatever their engines, leases are granted first in, first out across the engines, a lease takes a free browser of its engine first, then an empty slot, and else closes a free browser of the other engine and launches its own (the pool's switches). A network that cannot register (a refused token) stops the whole process, so the service manager restarts it and the failure shows. With enabled = false the process starts, runs nothing and waits for its stop signal.

One process per state directory. Before recover() (After a crash) the host takes an exclusive flock on STATE/host.lock (created mode 0600) and holds it until the process ends; the kernel releases it when the process exits, however it exits. A second browser-node on the same STATE, --check included, exits at once with status 2 and the message another browser-node holds STATE/host.lock: one process per state directory, before it deletes, seals or registers anything: its recover() would otherwise delete the first process's runs in progress, which have no summary.json yet. No PID is read and no lock file is ever deleted.

A new exit per request on each network. Every network's proxy is built with a new exit per request (node.rotating_loader, shared by the browser host and atlas node). Geonode rotates only on its rotating gateway ports: with main's configs/geonode.toml (port = 10000, the sticky endpoint for runs that ask for sessions) the proxy uses the scheme's first rotating port, 9000 for HTTP, and the start logs geonode: a new exit per request uses rotating gateway port 9000 once. The provider file is used as it is, with no hand-edited port. Proxy-Seller (the next port per request) and the other networks are unchanged.

One assignment

  • Only kind browser runs. Another kind is reported failed as node error (UnexpectedKind), a target that is not a [[target]] of the settings as node error (UnknownTarget).
  • The assignment's pulse values (requests, concurrency, timeout) are ignored. The run takes the target's tries as its request count and browsers_per_host as its concurrency (the pool, not the run, limits the browsers); its timeout_seconds is the page timeout (timeout_s or page_timeout_s) plus the answer wait of an AI source (cut to the page timeout) or the challenge wait of cloudflare_challenge.
  • The run uses its target's engine (settings.engine) and records it in its summary's config as browser_engine, in every try and in its manifest.
  • Targets come from a host registry: copies of the code targets with challenge_wait_s, answer_wait_s and the page timeout bound from the settings (dataclasses.replace, no global state).
  • Deadline: the end of the target's slot holding start_at (floor(start_at / every_minutes) + every_minutes) minus 2 minutes; in queue mode start_at + run_deadline_minutes minus 2 minutes (K-BP5). No try starts at or after it, and a run whose deadline has passed starts no try and uploads an empty run.
  • Untargeted networks ([networks] untargeted, D11) build their proxy with no country parameter and rotating sessions; their runs record requested_country = null. Every other network gets the batch country as ordinary nodes do.
  • On SIGTERM or SIGINT no new try starts; running runs end as a node's do (reported failed as node_shutdown, a run not yet started is handed out again), then the pool closes every browser.

Logs

STATE/logs/browser-node.jsonl holds JSON lines, rotated at 20 MB with 5 old files kept. Each run writes one "kind": "start" line when it starts (batch, network, target: the mini's watchdog reads it, so a long run that finishes nothing for an hour is not a late queue; the operator's browser-mini runbook) and, when it finishes, one "kind": "run" line: batch, network, target, engine, country, geo_targeting, tries_requested, tries_done, ok, latency_ms {p50, p90} (navigate plus settle), browser_seconds (time tries held a browser: each try's total minus its queue wait), queue_wait_ms_p50 (the wait for a browser from the pool, which includes a lazy browser launch or a relaunch after a recycle: the first tries of a run and those after a recycle wait longer, and that launch time is in no run's browser_seconds), deadline and finished_before_deadline. Every hour the host writes a "kind": "hour" line: browser_seconds of the runs that ended in the hour, utilization = those browser-seconds ÷ (browsers × 3600) (a run is counted whole in the hour it ends, so one over an hour boundary counts in the later hour and utilization can briefly exceed 1; tries cancelled at the deadline have no record and are not counted), the pool's stats() and the process's resident memory (rss_mb), and the outbox: outbox_pending (bundles still to send), outbox_bytes (all bundles kept, marked ones included), confirmed_last_hour, rejected, conflicts, discarded (half runs deleted at this start, see After a crash), discard_failed (half runs this start could not delete) unsealed (finished run directories kept unsealed: not sealable at start or since) and gates, per budgeted provider (such as proxy-cheap) {limit, peak, waits, closed_idle} since the last hour line (see Runner). When the disk guard refuses a screenshot it writes a "kind": "browser_outbox_full" line, at most once an hour. Ordinary log messages go to standard error (types only, never credentials). Two of them make a check possible from the log alone: each browser launch writes its identity, browser launched: Camoufox <release>, engine <engine_version>, user agent <user_agent> (the manifest's camoufox block) or browser launched: Chrome <version>, user agent <user_agent>, and each confirmed bundle the SHA-256 the manager archived, bundle <run_id> of batch <id> confirmed (sha256 <64 hex>) and deleted.

Check before installing

atlas browser-node --settings ... --state ... --host browser-1 --check [--browsers N] checks the settings and every network's files and provider configuration, opens N browsers (default 1, at most 48) at the same time, each checking the user-agent rule at launch, prints JSON with the pinned release, the engine and its version, the user agent and the resident memory each browser added and in total, and in queue mode the host's estimated load (queue_load), closes them and exits. It sends no proxy traffic and needs no orchestrator. A missing install, a bad file or a refused user agent exits with status 2.

Service templates

configs/launchd/io.atlas.browser-node.plist.example (macOS, a launchd agent) and configs/systemd/atlas-browser-node.service.example (Linux) run the command above, restart it when it exits and stop it with SIGTERM (120 s before a kill). They hold placeholders only (__CHECKOUT__, __STATE__, __HOST__, __ORCHESTRATOR__, __USER__); the real values are filled in privately on each host. Standard output and error go to STATE/logs/browser-node.{out,err}.log under launchd and to the journal under systemd.

10. Bundles and outbox (browser/rawfiles.py, browser/rawfiles_seal.py)

On the host every run becomes one K-BP4 bundle (section 4), sent to the manager's ingest endpoint (section 6) and deleted only when the manager confirms it.

Layout

  • STATE/runs/<provider>.<product>/<run_id>/: the node's run directory while the run is going. FileRecorder, the transport's recorder, appends one validated contracts.try_record(...) line per try to browser/tries.jsonl and writes each screenshot to browser/screenshots/NNNN.jpg. It also keeps the batch facts the summary does not hold (batch id, country, slot, host, settings sha256) in browser/batch.json; that file is not a bundle member and is never packed.
  • STATE/outbox/<run_id>.tar.gz and its sidecar <run_id>.json (batch_id, sha256, bytes, network, target, country, slot), both mode 0600. A kept bundle may have a marker beside it: <run_id>.conflict or <run_id>.rejected, JSON with the reply's status, its error code and the time.

Sealing

When a run ends, seal(run_dir, batch, summary, settings_sha256, camoufox, outbox=..., engine=None) writes browser/manifest.json (counts from the tries, requested_country and geo_targeting from the run's config, so an untargeted run says so, D11; for a Camoufox run the camoufox block of the last Camoufox the host launched, else the pinned release's, and the engine block from it; for a Chrome run camoufox None and engine the Chrome block; an engine other than the run's config names is refused), packs the directory with orchestrator.archive.pack(..., nested=..., mtime=slot start) (sorted members, uid and gid 0, mode 0600, gzip level 6: identical inputs give identical bytes), fsyncs the tar.gz, writes and fsyncs the sidecar, re-hashes the tar.gz against it and only then removes the run directory. A run that cannot be sealed keeps its directory and is sealed at the next start. A run the orchestrator killed, and one stopped by a shutdown, is removed without upload, as on any node.

Sending and the confirmation rule

Outbox.send(bundle, agent) posts the tar.gz through the network's own node agent (its session, token and POST /v1/results?batch_id=) with Content-Type: application/gzip, X-Content-SHA256 (the file's sha256) and X-Bundle-Id (the run id). The reply decides, through contracts.confirmed(reply, local_sha256) and nothing else:

  • 200 with ingested: true and archived.sha256 equal to the file's, or 200 with ingested: false (run killed or skipped): the tar.gz, then the sidecar, are deleted.
  • 408, 429, 503, any other 5xx and network errors: kept, sent again later with backoff (30 s, doubling, at most 5 minutes; a longer Retry-After wins).
  • 400 checksum_mismatch: the file is re-hashed and sent once more; a second mismatch marks it .rejected.
  • 409, and a 200 that does not confirm (another sha256, missing fields): kept with .conflict. Any other 4xx: kept with .rejected. Both are logged once and not sent again until the marker is removed.

An unconfirmed upload never fails the run and never calls /v1/failed: the manager accepts a late upload (K-BP7). A loop sends the pending bundles, oldest slot first and at most 2 at a time per host, after every run end, when a network registers (host start) and every 5 minutes, with no time limit. Each bundle goes through the agent of its sidecar's network.

Disk guard

When runs/ plus the outbox hold more than [outbox] max_pending_gb (measured at most once a minute), the recorder writes no screenshot and records the try with screenshot = null; tries go on, and nothing is deleted to make room. The first refused screenshot of each hour logs browser_outbox_full.

After a crash

At start, before any network registers, recover() seals every run directory a killed process left with its summary.json (a tar.gz without its sidecar is rebuilt), removes a run directory whose bundle is already sealed and verified, and removes half-written sidecars and those of bundles already confirmed. A directory without summary.json was killed during its run: it is half a run, which the manager cannot ingest, so it is deleted, never sealed or uploaded, logged once with its run id (browser_run_discarded) and counted as discarded; the disk guard no longer counts it. Only full runs are uploaded. A half run that cannot be deleted (an OSError such as a permission error) is logged by error type (browser_run_discard_failed), counted as discard_failed, not unsealed, and deleted at the next start. The start logs one line with the counts (browser_recover: sealed=.. discarded=.. kept=.. discard_failed=..). A finished directory whose files cannot be read or sealed (an unreadable sidecar beside it, say) is kept with its files, logged by error type and counted as unsealed, and the start goes on. A run whose seal fails while the host runs is counted the same way and sealed at the next start. Nothing finished or unconfirmed is deleted: a run with summary.json and every bundle in the outbox stay. An outbox pass never sends a bundle whose seal has not ended.

Inspecting a pending bundle on a host

ls -l STATE/outbox/                          # bundles, sidecars, markers
cat STATE/outbox/RUN_ID.json                 # batch, network, target, slot, sha256
shasum -a 256 STATE/outbox/RUN_ID.tar.gz     # must equal the sidecar's sha256
tar -tzvf STATE/outbox/RUN_ID.tar.gz         # members: summary.json, buckets, browser/...
tar -xzOf STATE/outbox/RUN_ID.tar.gz browser/manifest.json
cat STATE/outbox/RUN_ID.conflict             # why a bundle is held: status and error

To send a marked bundle again, remove its marker; the next pass sends it. Never delete a bundle the manager has not confirmed.

11. Capturing real pages (live checks only)

scripts/browser_capture.py records what the judge read on real pages, for the owner's approved live checks of a target and for writing real fixtures from them. It runs on a browser host, from its installed checkout, beside the host process and with the host's own files:

uv run python scripts/browser_capture.py --settings STATE/settings.toml --state STATE --host browser-1 \
  --network provider/product --target amazon_pdp --tries 20 --country us --out DIR
  • Each try is the host's try: the settings' [[host]] view, the network's files (load_network), the target bound from its [[target]] (inputs, timeout, waits, blocked resources), a BrowserPool and BrowserTransport. The tries run one after another on one browser (browsers_per_host is ignored), with screenshots on for every try. The tool reads the files only: it registers no node, uses no token or orchestrator, writes no database and uploads nothing, and it is not a service or a scheduler.
  • Caps: --tries is 1 to 50 (the owner's cap per target per network); --country is us unless --allow-country names the other one (not used in this phase); the network must be one of the host's and the target a [[target]] of the settings. The output directory DIR/<provider>/<product>/<target>/ must not exist: a second capture into it is refused. A refusal exits with status 2 before any try.
  • Per try NNNN.json: view in the fixture shape (final_url, status, title, text_head, found; null when no page was read, a navigation error), judged (verdict, error, reason), input, timings_ms and bytes_down_est; and NNNN.jpg, the try's screenshot. Then tries.jsonl, the host's try records (their screenshot keeps the bundle's member name, browser/screenshots/NNNN.jpg, for the NNNN.jpg beside it), and summary.md: the tries per verdict, error and reason and the page loads used.
  • Privacy: an answered try of an AI source (ai_overview, ai_chatgpt, ai_gemini) keeps the host's rule, no screenshot, and its text_head becomes <answer: N chars> (N is found.answer_chars). Such a view replays to its verdict through the found rules (answer_chars, answer_sentences, the selector counts) but not through the text markers the shared judge reads in the title and text, so a fixture written from it keeps the recorded verdict. The view's final_url keeps only the scheme, host and path, as the host's records do (contracts.page_url): no credentials, query or fragment, which can hold challenge tokens issued to the exit. A non-web page such as about:blank is kept as it is, any other URL as its scheme alone. Addresses a page shows in its title, text or final URL (a block page's "your IP") become <ip>. No cookie, header, credential, proxy username or exit IP is written. A screenshot shows the page as the host's failure screenshots do.
  • A capture is private data: copy it to the private repository's browser/captures/. It never goes into a product repository as it is; a fixture written from it holds only the view and the expected outcome.

The transport's one hook for it is BrowserTransport(view_sink=...): it receives (request index, the PageView the judge got) after the try is recorded, once per try that read a page. The host never passes one, so its records, bundles and timings do not change.

Bench: comparing the engines

scripts/browser_bench.py measures what one engine costs a browser host, for the owner's approved Camoufox and Chrome comparison. It runs on the host, from its installed checkout, like the capture:

uv run python scripts/browser_bench.py --settings STATE/settings.toml --state STATE --host browser-1 \
  --network provider/product --target amazon_pdp --tries 100 --engine camoufox|chrome --browsers 8 \
  --country us --out DIR
  • Each try is the host's try, built with the capture's helpers (the [[host]] view, the network's files, the bound target, BrowserPool(size=--browsers) and BrowserTransport), with the settings' traffic rules (block_resources, block_urls, cache_urls, wait_until); each try record also holds the relay's exact wire bytes (wire_up, wire_down, wire_exact), and summary.json their totals under wire. --engine camoufox launches the pinned Camoufox (driver.launch), recycled after --recycle-after tries (default: the settings' recycle_after); --engine chrome launches the host's Chrome from [chrome] executable (driver.launch_chrome: a new process, profile and fingerprint per try), refused before any try when it is missing or too old. Like the capture, it uses no orchestrator, token or database, so nothing reaches production figures.
  • Up to --browsers tries run at once (1 to 48, default 8), each on a new context or profile; the next starts as soon as one ends. Caps: --tries 1 to 500, the capture's country, network and target checks, and one bench per output directory. A refusal exits with status 2 before any try; an engine refused during the run (the user agent check) stops it with status 1.
  • Into DIR/<engine>/<target>/ (folders mode 700, files 600): tries.jsonl, the host's try records (Chrome's with their fingerprint) plus engine, started_at, ended_at and duration_ms (the try's timings_ms.total: the browser lease, the context or Chrome start, the page and its settling); samples.jsonl, the per-second samples below; and summary.json: the engine and its identity (Camoufox's release, Chrome's version, the user agent), the outcome counts (ok, challenge, block, timeout, proxy_error, other with other_errors by error code), request time (average, median, p95, max), bytes (total and per try), CPU % (average, p95, peak), RSS (average, peak), the CPU seconds used, the wall time and the browsers. No screenshot, cookie, header, credential, proxy username or exit IP is written; final URLs are scrubbed as the capture's are.
  • What the samples measure (browser/procstats.py): once a second, one ps listing of every process below the bench's own process, that is the browsers and their Playwright drivers. Each line has processes, rss_bytes (their summed resident memory), cpu_seconds (their cumulative CPU time; a process that ended keeps its last reading) and cpu_percent (the CPU seconds used since the previous line over the time between them, x 100: 100 is one core busy; null on the first line). A process born and ended between two samples is not seen. The host process and any other program on the mini are not counted, so run nothing else beside a bench.
  • scripts/browser_bench_report.py DIR... --out report.md merges the minis' bench folders: one table per target and engine (all minis' tries together: success, challenge, block, timeout, proxy error, other, the average, median and p95 request time, bytes per try), one table per mini and engine (all its targets' samples together: CPU % average and peak, RAM average and peak, CPU seconds per try) and a plain-words verdict. CPU is compared per try, because a slower engine shows a lower CPU % while doing less work; RAM by its average. Minis are named by their logical host name (browser-<n>); the report holds no host names, IPs or local paths.
