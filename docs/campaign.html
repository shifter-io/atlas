Proxy Index · Private operator workflow

Hourly droplet campaign

Every hour, one fresh worker droplet per network and region runs one onboarding round to its natural end, hands its data to a manager droplet and is destroyed. The account also holds production droplets of other projects, so every destructive step is provably scoped to resources this campaign created.

Overview

A manager droplet launches 16 networks × 8 regions = 128 workers per hour from a prepared snapshot, starts onboarding round on each at the whole hour, collects and verifies each finished round, and destroys the worker through the scope guard. Hours overlap freely; there is no request cap and no round deadline. A per-hour traffic report per network goes to the owner.

The only delete path

scope.guarded_delete(cloud, kind, id, scope, ledger, audit_path, role) deletes one resource by id. The Ledger holds the recorded ids per kind (an SSH key id never matches a droplet record) and the droplet records. role says which droplet the caller means: a worker, the recorded manager, a builder or a pulse node. For a droplet it takes a fresh GET immediately before the DELETE and requires every check:

  1. recorded: the id is in the campaign's ledger (or the recorded manager or builder id);
  2. tags: the role's tags are present (a worker also needs its campaign tag) and no other role's tag is;
  3. name: the role's exact name pattern, and for workers the campaign's short id;
  4. project_id and project: the scope's project id is the project named Proxy Index (checked once per client), and the droplet is in it (membership cached for at most 60 s and always re-read on a miss). Only the own-unassigned path may replace the membership check, and only when all of these hold: the ledger record for this exact id carries the mark assign_failed_at, which only assign_and_verify_project writes, after checking the id against its own client's create (a static scan refuses any other writer); the id came back from this client's own create, or carries that mark (a restarted collector or harvester has no other proof); the droplet's name is exactly the record's; and the droplet is at most 30 minutes old. Its audit lines carry path: own_unassigned;
  5. not_manager: a worker or builder delete never targets the recorded manager id; a manager delete targets only it;
  6. created_after: created at or after the scope's time (the spec, or the inventory time for manager and builder).

A campaign role refuses every droplet that carries pi-pulse-node, so no campaign janitor, harvest or teardown can remove a pulse node, and teardown's tag proof counts only the campaign tags. A pulse node is removed only by scope.retire_pulse_node(cloud, id, project_id, ledger, audit_path): guarded_delete with role pulse and the pulse scope (the two go only together, for droplets only), which requires recorded, tags (pi-pulse-node and only pi-pulse- tags), name, and project_id and project for project Dev Resources, with no own-unassigned path. Creates with pi-pulse-node carry only pi-pulse- tags and pulse names; droplets are listed by a pi-camp- tag or exactly pi-pulse-node.

Keys and snapshots need a recorded id and a pi-camp- name; firewalls also must reference only pi-camp- tags and recorded droplet ids. Every attempt appends to ledger/delete-audit.jsonl (0600): one attempt line just before the DELETE, then deleted, or a single refused, absent or failed line (any error, with its type). A refusal raises OwnershipError and never falls back to another path.

Enforcement

  • The client sends only the calls in its allowlist (do_api.ALLOWED): an exact method (any letter case is normalized first), a path pattern and the query keys allowed. Droplets are listed only by a pi-camp- tag or exactly pi-pulse-node. Everything else (droplet actions such as rebuild or restore, putting a tag on or off a resource, listing tags, PATCH, listing all droplets) is refused before the network. The operations calls also have a checked body (do_api.BODIES): a droplet action is only shutdown, power_off or a snapshot named pi-camp-worker-…; an image action is only a transfer to one of the 8 regions; a new SSH key and every firewall need a pi-camp- name, and a firewall may name only the campaign role tags; a new tag is only {"name": "pi-camp-…"}. DELETE (one resource, no query) and project assignment also need the token only scope.py holds (require_guard). Later tasks add their own endpoints to the allowlist under scope review.
  • Writes that could touch a droplet or firewall we may not own (droplet actions, firewall create and replace; do_api.OWNED_WRITES, which also holds the two tag calls) are refused by the HTTP layer unless they carry a token private to do_api.py, the same way DELETE needs the scope guard's token. Only the client's own methods pass it, and only after an ownership check on a fresh GET: droplet actions run only on a builder this client created (builder tag and name) that is in project Proxy Index; a firewall is created or replaced only when it, and the firewall it replaces, has a pi-camp- name, only role tags, and only droplets that show a role's tag and name and are in project Proxy Index. A transfer only copies a snapshot whose name is a campaign worker snapshot. A power-off or a firewall can therefore not reach a production droplet, through the methods or through request().
  • Neither the Cloud protocol nor the client has a delete method.
  • tests/test_campaign_scope.py runs every destructive path against a fake account seeded with 1,125 production-like droplets and every near-miss of the markers, even with a ledger that lists every droplet, and proves only ours are deleted. A static scan of every file in src/proxy_index/campaign/, including later ones, allows the word delete (any case), raw client access and assign_project calls only in scope.py and do_api.py; a second scan of all of src/ and scripts/ finds no direct API host, no doctl and no import of the client's private names. A gate test keeps scope.py and do_api.py at 100% line and branch coverage.

Project assignment fails closed

scope.assign_and_verify_project(cloud, scope, droplet_ids, records, audit_path, role) is the only assignment path and returns (confirmed, failed). Before any assignment, each id must have its ledger record, have come from this client's own create, and show every marker on a fresh GET; an id that is not ours and fails a check raises OwnershipError at once, with no wait, and so does a project that is not Proxy Index. Just after a create, DigitalOcean may answer a GET without the droplet, its tags, its name or its creation time, so our own new droplet is read again, 1, 2, 4, 8 and 15 s apart (about 30 s, scope.SETTLE_DELAYS), while only those checks fail; no check is ever relaxed, and nobody else's droplet is ever read again. The project check, the assignment and the project re-read are each retried, up to 3 tries 5 s apart; an error or a droplet not shown yet never escapes. A confirmed droplet becomes assigned. A droplet that is not confirmed for any other reason fails closed through scope.remove_unassigned: it becomes assign_failed (error_class project_assign_failed, ledger mark assign_failed_at), must never be pushed or started, and is deleted at once through the guard (the own-unassigned path, or the normal path if the assignment landed late). The caller's ledger save (Retry.save, or save of remove_unassigned) runs right after the mark and before the delete, so a crash between them cannot leave an unmarked worker. Its record ends as destroyed, or destroy_refused / destroy_failed for the caller to flag. The record's error_detail keeps why: the exception class (Unconfirmed when nothing was raised), its message with tokens and addresses removed, the failed checks and the HTTP statuses of the latest create, assignment and GET calls about the droplet; every guard audit line for that droplet carries it as cause.

Contracts

contracts.py is frozen: a change is its own reviewed task, merged first and re-run against the scope suite. It defines the tags and name patterns above, the accounts (leftclick, proxy-index, both with project Proxy Index), CampaignSpec (validated; JSON round-trip; concurrency per worker, default 2,000, 1–5,000; every size_by_region value matches SIZE_RE, the CPU-Optimized or Basic droplet slugs plan --size accepts), DropletRecord (with per-worker concurrency and CPU, steal, load and memory samples) and HourRecord (no IP addresses; paused_networks lists the networks paused when the hour launched, empty in older records), Droplet and Scope, the Cloud and Remote protocols and the campaign-root paths (campaign-spec.json, ledger/HH/hour.json, ledger/delete-audit.jsonl, networks/<net>/residential/<mcid>, logs/HH, reports, status.json, alerts.jsonl, .runtime).

Client and limits

do_api.DigitalOcean(token_source) reads the token from the keychain (keychain_token(account)) or from a 0600 file owned by the current user (file_token(path)). The token lives in memory only and never appears in repr, errors or logs.

  • create refuses names or tags without every marker and sends at most 10 names per call, always with ssh_keys, monitoring, with_droplet_agent and ipv6 as given.
  • Listing pages hold 200 items; a page without meta.total is an error, so a listing never ends early.
  • A 429 waits for Retry-After or the rate-limit reset (at most 60 s); 5xx and connection errors back off 1, 2, 4, 8 s; other errors raise ApiError with method, path and status only. A droplet create is never retried after a 5xx or a lost answer, because it may already exist: create raises CreateError with the droplets already created and the names still pending (uncertain when the outcome is unknown). Resolve an uncertain create with adopt_uncertain(names, hour_tag), which finds exactly those names under our tag, before any re-create.
  • A limiter allows at most 200 requests per minute; ratelimit_remaining shows the API's count.

project_id(name) resolves project Proxy Index by its exact name; account() returns only the droplet limit and account status; sizes() lists the available sizes and their regions.

proxy-index campaign limits --account leftclick|proxy-index [--sizes …] is read-only and prints counts only: the droplet limit and account status, the number of droplets under each role tag, the number of droplets in project Proxy Index, the rate-limit remaining, and the regions (of the 8) that offer each size (default c-2, s-8vcpu-16gb, s-1vcpu-1gb). It never lists production droplets and prints no IP address and no token.

Launch

launch.launch_hour(spec, record, root, cloud=…, remote_factory=…, clock=…) brings one hour from planned to running under the hour's lock (ledger/HH/.lock); the launcher owns hour.json until then, and saves it after every step.

  1. Plan. One DropletRecord per network and region (name pic-<sid>-hNN-<region>-<network>, size, image, its network's manifest concurrency (the spec's, or lower when the plan capped the network; a manifest above the spec stops the launch), and overlap: the network and region's workers of earlier hours that are still armed or running). Cells start pending; traffic gets each network's countries_total. Names are on disk before any create. The recorded concurrency is therefore the one the worker runs.
  2. Wait for the lead. A launch earlier than scheduled_at − create_lead_seconds (HH:58:30) waits; onboarding round itself waits for HH:00:00.
  3. Adopt first. Before any create, recorded names without an id (or whose id this process did not create) are resolved with adopt_uncertain(names, hour_tag); ids another record already holds are never taken. A crashed launch therefore never creates a name twice.
  4. Create per region (at most 10 names per call) with the tags pi-camp-worker, pi-camp-<sid>, pi-camp-<sid>-hNN, the spec's SSH key, and monitoring, agent and IPv6 off. Ids are saved right after the answer. An uncertain answer is adopted by name; names still missing are looked up once more (a create still in flight may be listed only now) and then retried once after 15 s, then create_failed.
  5. Assign every new id of the region through scope.assign_and_verify_project (one POST per region, 3 checks 5 s apart). An unconfirmed worker is never pushed; the guard removes it on the own-unassigned path and the hour gets a project_assign_failed alert. Any other failure of our own new worker before its membership is confirmed (an exception in the create or assignment step) also goes through scope.remove_unassigned, never through the plain guarded delete, which needs project membership and would refuse it. Its replacement runs alongside the region's confirmed workers, never before them.
  6. Ready. One GET /v2/droplets?tag_name=pi-camp-<sid>-hNN per 2 s, shared by every waiting worker, until the droplet is active with a public IPv4 (written only to .runtime/hosts-HH.json, 0600), then SSH; both within 180 s of the create.
  7. Push and arm. One tar on SSH stdin: the network's manifest, provider.toml (next to the manifest on the manager), assignment.json, the wheel whose SHA-256 the spec binds (from <base>/wheels/) and that network's credentials (from <base>/.secrets/credentials/<network>.toml), where <base> holds campaigns/<cid>. A push error is retried once on the same worker. After a failed push, and for a resumed worker, the worker is inspected first: a round unit in any state but inactive, or the fleet marker, means the round started, and the worker is armed, never pushed twice. start_failed is written only when the round provably never started: when the worker cannot be read after a failed push, it is armed with error_class start_unconfirmed and harvest decides. An error after arming never turns an armed worker into start_failed. A pull of a round directory that was never created returns it empty.

No region loses its hourly test to a failed worker. A create, assignment, boot, SSH, push or start failure removes the worker through scope.guarded_delete (a refusal is destroy_refused with a high alert and no fallback; an error is destroy_failed and retried by the next harvest pass), and the launch creates a replacement for that network and region in the same hour: up to REPLACEMENTS_PER_CELL (3) per cell, each only within replace_until_minutes of HH:00 or of the launch, whichever is later (a tick --now or a late timer still gets its replacements). A replacement first adopts any droplet with its exact name under the hour tag that no record holds (a create that landed late), so nothing is created twice. It is assigned, booted and pushed like any worker, and its round starts as soon as it is armed (a round armed after HH:00 starts at once). The replacement record carries replaced_from (the index of the worker it replaces in the hour's droplets), and the hour's replacements[<network>/<region>] records replaced_from (each failed worker's droplet id, status and error class) and extra_delay_seconds (how far past HH:00 the replacement armed; 0 when it armed in time, null when none did). Only when the budget or the cutoff is spent does the cell become failed_ours, with the high alert cell_failed. An unexpected error fails only its own worker, no task outlives the launch, and every worker leaves it armed or in a final status: without a droplet create_failed, with one removed through the guard (which refuses an unassigned droplet it cannot prove ours); error_class keeps the cause. Synthetic specs make no cloud or SSH calls and arm every worker at once.

Worker start (fanout.START_SCRIPT, run by the worker's system Python with public arguments only): it writes the credentials to /run/proxy-index-worker/credentials.toml (0600, never under the worker root), extracts the rest with the data filter, installs the wheel with uv pip install --no-deps --offline only when its SHA-256 differs from the installed one, waits up to 10 s for NTPSynchronized, records both in worker-start.json in the round directory, writes active-run.json (the fleet marker), and starts systemd-run --unit=pi-camp-round (with --mmdb when /opt/proxy-index-worker/db-ip/ holds exactly one *.mmdb, so the round applies the country check; LimitNOFILE=65536, UMask=0077, Restart=no, RemainAfterExit=yes so the exit status stays readable; no run-time limit) and the sampler unit pi-camp-sampler.

SSH. fanout.OpenSSHRemote(identity, runtime, hour) runs ssh with BatchMode=yes, IdentitiesOnly=yes, User=root, a per-hour UserKnownHostsFile with accept-new, ConnectTimeout=5, ServerAliveInterval=10, ServerAliveCountMax=3 and ControlMaster=auto, ControlPersist=4h. The control socket is .runtime/cm-%C when that path fits the socket-path limit; under the manager's campaign root it does not, so sockets go to a private /tmp/pi-camp-cm-<uid>/; a directory owned by another user is refused. inspect runs fleet.REMOTE_INSPECT; stop sends SIGTERM to the round unit; pull streams the round directory only once its checkpoint is terminal or the round unit has ended (a killed round never writes a terminal checkpoint); while the unit runs, or when its state cannot be read, the pull is refused. It extracts it only when every entry lies under that directory, with no absolute path, .., link or device; journal keeps the last 5 MB of both units. Errors are fixed text with the exit code, never the host or its output. What a worker may send is capped: 16 MiB per command, 5 MB of journal, 8 GiB per pulled round, streamed to disk; past the cap the command is killed and fails.

Sampler (python -m proxy_index.campaign.sampler --interval 1 --output <round dir>/host-samples.jsonl): every second it appends total and per-core CPU busy, steal, load1, used memory and the RSS of the round unit's processes, and stops when the round unit has no process left. The file is pulled with the round; verify_round does not read it. sampler.summarize(path, since) ignores samples before the round's first start (the idle wait for HH:00) and gives the record's cpu_p50_pct, cpu_p95_pct, cpu_max_pct, cpu_core_max_pct, steal_p95_pct, load1_p95, mem_used_max_pct, cpu_peak_pct and rss_peak_mb.

Harvest

harvest.harvest_hour(spec, record, root, cloud=…, remote_factory=…, clock=…) is one idempotent pass over a launched hour (state running or harvesting), under the same hour lock as the launcher; the collector runs it every 30 s. It saves hour.json after each worker. Retry clocks (unreachable since, last pull) live in .runtime/harvest-HH.json, which is never downloaded.

  1. Inspect each armed or running worker with fleet.REMOTE_INSPECT. The first country's started_at sets running, started_at and start_lateness_seconds. The round has ended when the round unit is no longer running (RemainAfterExit keeps its exit status); a unit that vanished mid-round counts as exit 1. Rounds are never stopped: an info alert at 3 h and a high alert at 12 h. An unreachable worker is kept and retried, with a high alert after 30 minutes.
  2. Collect a finished worker: pull regions/<R>/rounds/<NN>/ into the network's campaign directory, run rounds.verify_round (it reads only the checkpoint and the country folders, so host-samples.jsonl and worker-start.json travel with the round without affecting it), save the journal to logs/HH/<net>-<R>.journal.txt (a journal error is an info alert), and record counters, CPU samples, the cell and the network's traffic. For exit 0 or 130, a pull error, a missing checkpoint or a data defect (anything other than a country's own status) is collect_failed. The worker is then kept and re-pulled every 5 minutes, with a high alert after 30 minutes; it is never removed while its data is uncollected. A failed unit (any other exit) is collected as far as it goes and its cell is failed_ours (round_failed). This includes a round killed by SIGKILL (the OOM killer, a reboot), whose checkpoint never became terminal: the pull accepts it once the unit has ended. CPU fields count only samples from the round's first start on.
  3. Remove a collected worker only through scope.guarded_delete. A refusal is destroy_refused with a high alert and no fallback; an error is destroy_failed and retried on the next pass. The worker's lifetime is added to worker_hours.

Cells: complete (exit 0 and every country completed and verified), partial (exit 0 or 130 otherwise), failed_ours. traffic[network] accumulates requests, successes, errors, bytes up and down, and completed countries. The hour is done when every worker is removed or was never created (the launcher leaves no worker in a launch status), and failed when a removal was refused; it is harvesting while collection is under way. Synthetic workers finish 5 minutes after HH:00 with no calls.

Scheduling and alarms

Every slot k of the campaign is due at starts_at + k × slot_minutes − create_lead_seconds (HH:58:30 for the default hourly slots; :13:30, :28:30, :43:30 and :58:30 for 15-minute slots) and its rounds start at the slot's time, whatever earlier hours are doing: hours overlap freely and nothing is ever stopped automatically.

  • campaign tick --root R (timer *:58:30) takes flock(ledger/.lock), then launches every due slot still planned at once, records fired_at and launch_delay_seconds, and raises late_launch when a slot fires more than 60 s late. A slot is never skipped and never relaunched; a slot left launching by a crashed tick is resumed from its record by the launcher, which never re-creates existing names. A timer tick disables its own timer once no slot is left planned or launching (a failed disable is an info alert). --slot N --now launches one slot immediately (the dry run) and never touches the timer.
  • campaign collector --root R (always on) runs one pass every 30 s: it harvests every hour in running or harvesting, writes the traffic report of every newly final hour, reconciles orphans every 5 minutes, raises alerts and writes status.json. A failed reconcile (an API error) is alerted (reconcile_error, high after 3 in a row) and never stops the rest of the pass. It exits when all hours are final and no worker is alive; with --until-done it exits as soon as every launched hour is final (the dry run).
  • Orphan reconcile lists only tag_name=pi-camp-<sid>. A droplet of an hour that is still planned or launching belongs to the tick and is skipped. A droplet that fails the name, tag, manager, age or project checks is never touched and raises foreign_tagged; the one exception to the project check is a recorded worker with the ledger mark assign_failed_at, which is handed to the guard (own-unassigned path) so an unconfirmed worker is removed even after a restart: in assign_failed, destroy_failed or destroyed, and in destroy_refused only while it is at most 30 minutes old and its latest audit line is a refusal on checks that settle after a create (scope.settling_refusal: tags, name or creation time, with project), as when DigitalOcean lags for more than the 30 s settle. Any other marked destroy_refused worker stays with the operator. An unrecorded owned droplet is adopted into its hour's record and inspected: with an active-run marker it is harvested normally; its address goes into CAMP-1c's host map (.runtime/hosts-HH.json) so the harvester can reach it; without one it is destroyed through scope.guarded_delete. An orphan that cannot be inspected is retried at the next reconcile and counts as a live worker until then, so the collector does not finish while it exists. A recorded destroyed droplet that still exists, or a destroy_failed one in a final hour, goes through the guard again (the harvester retries destroy_failed while its hour is not final). A refusal sets destroy_refused and raises a high alert, with no fallback.
  • campaign watchdog --root R --check armed|fired (timer *:00:30 with armed, *:02:00 with fired; 30 s and 120 s after each slot for other slot lengths) checks the current slot. With armed the hour is on time when it is running, or still launching with at least one worker armed (a slow or replaced worker may keep a healthy hour launching past HH:00:30). If not, it raises missed_launch and, while the tick timer is enabled, starts the tick service. When the timer is disabled and the due slot is still planned, it raises the alarm only and never launches by itself. The watchdog runs only for the enabled campaign.
  • campaign network pause|resume NET --root R writes network-overlay.json; later hours launch without the paused networks (recorded as network_paused and in the hour record's paused_networks), and running rounds go on. Only on the owner's request.

Alerts go to alerts.jsonl, once per code and key, with level info or high: late_launch, missed_launch, timer_disable_failed, reconcile_error, foreign_tagged, destroy_refused, destroy_failed, orphan_adopted, orphan_unreachable, harvest_error, create_failures (over 10% of an hour's creates), disk_low (under 20% free), ratelimit_low (under 500), clock_unsynced (NTP not synchronized once the manager has been up 300 s; no grace when the uptime cannot be read), and every alert the launcher or harvester adds to an hour record, under its kind and with the worker name (such as auth_failed, collect_failed, worker_unreachable and the long-round alerts round_long_3h and round_long_12h, which the harvester owns). status.json holds campaign_id, now, next_launch_at, per-hour state, launch delay, cell counts and live workers, live_workers, alerts_open (the count of high alerts), traffic_latest, ratelimit_remaining, disk_free_pct, clock_synced and finished. None of these files holds an IP address.

Traffic reports

When an hour becomes final, the collector writes reports/traffic/hour-NN.md and rebuilds reports/traffic.tsv from every final hour. The report has one row per network: GB up, down and total, requests, successes, error %, countries completed of the total, regions done, the slowest region and its round duration, worker-hours (the harvest's per-network count, droplet create to destruction) and cumulative GB; then a total row with the summed countries and regions, the start-lateness range, the concurrency per worker and the launch delay. A second table gives, per region, the worst worker's CPU p50, p95 and max, load1 p95 and memory max. Bytes, requests and outcomes are summed from the hour's worker records, which are the framework's client-side wire counts, so a provider's own billing may differ slightly; countries and worker-hours come from the harvest's per-network totals. Cumulative GB is every worker collected so far, in all hours, when the report is written, because overlapping hours finish out of order. An hour that goes back to harvesting (an adopted active orphan) gets its report rewritten under the same name when it is final again. The dry run's hour-00 report is the same report.

Delivery to the Mac. campaign watch --inventory I --status-file F --traffic-dir D [--interval 60] [--once|--ack] runs under launchd on the Mac. Every minute it makes one SSH call to the manager (the Mac key, BatchMode, a required known host) that returns status.json, the alerts appended since its last offset, the reports it has not seen (by name and SHA-256, so a rewritten report comes again) and traffic.tsv. It copies each new or rewritten report into D, shows a macOS notification per new report ("CAMP-1 hour NN: X GB; top network …") and per new high alert, and atomically rewrites the header of F (State: active|blocked|finished, Updated UTC, Hours, Live workers, Traffic-Latest: hour NN <path> with the path relative to the folder of F, Alerts: N high (M new)), keeping anything below the first blank line. State: blocked means an unacknowledged high alert (M > 0) or manager_stale (no fresh status.json for 3 minutes). Once the operator has handled the alerts, campaign watch --status-file F --ack … acknowledges every high alert seen so far in its own file (.<name>.watch-ack.json, written only by --ack, so the running watch never overwrites it), and the next poll clears blocked; a later high alert blocks again. A malformed alert line is skipped with one local watch_parse_error notification, and the state is saved after each copied report, so a crash never repeats a notification. Its offset and seen reports live in a hidden .<name>.watch.json beside F. The inventory is a JSON object with host, identity, known_hosts, campaign_id and optionally campaign_root. The watch never deletes anything and writes no IP address.

Data and completeness

A cell is one network, region and hour: 24 per network and region, 3,072 for 16 networks in 8 regions. Its data is the round the harvest pulled into networks/<net>/residential/<mcid>/regions/<R>/rounds/<NN>/. Its status comes from that round and the droplet records and paused networks in ledger/<HH>/hour.json (merge.cell_status, shared by merge and completeness):

  • a pulled, closed round is judged by its data; a round whose own status is failed is failed_ours;
  • a pulled round that is not closed is running while a worker of the cell is still requested, assigned, booting, starting, armed, running or finished; with no live worker it ended without closing (killed, out of memory, host lost) and is failed_ours, with its measured countries kept;
  • without a pulled round: no record is pending, or paused when the network was paused as that hour launched (final: merge proceeds and the cell brings no data); a live worker is running; a collect_failed worker means the data waits on a kept worker (uncollected); failed_ours only when no worker ever started (create, assign, boot or start failed, or destroyed with no armed or start time); any other worker started a round whose data is not in the root (uncollected, "round ran; data not collected").
  • campaign merge --root R [--network N] (merge.merge_network) writes each spec region's state.json and summary.json: a closed onboarding checkpoint with all 24 rounds, the rounds' own jobs, and not_started_deadline jobs at the manifest's scheduled_at for a failed_ours or paused cell. A round that ended without closing keeps its jobs, closed by the round executor's own rule (pending → not_started_deadline, running → failed). It checks every cell of every requested network first and writes nothing while any is pending, running or waiting on a kept worker (CampaignNotFinished), or when a started round is missing from the root (RoundDataMissing); the command prints the blocking cell and exits 3. validate_state and the unchanged onboarding export read the result.
  • campaign completeness --root R (completeness.build) checks every pulled, finished round with verify_round (chunk SHA-256, rows, time bounds, counters) and writes completeness/completeness.json (rows, issues, status counts per network and in total), per-hour-completeness.tsv, per-country.tsv and per-hour-tables.md (one table per network, regions × h00–h23, each cell's mark followed by its real-error rate of answered requests, then a table "Answer classes per network and region" summed over the slots). It only reads the data, exits 0 when every cell is complete and 3 otherwise. Cells: complete (every country completed and verified), partial (a country interrupted, failed, or a verification issue), failed_ours (verified too when a round was pulled), uncollected, running, pending, paused (‖ paused); the issues name the reason ("round ended without closing", "data waits on a kept worker", "round ran; data not collected").
  • Answer classes. Each row also has rate_limited, no_inventory (no-IP answers such as Geonode's 465), other_country (successes from another country than requested), duplicates (in-country successes beyond the unique IPs) and real_errors (errors that are neither rate limits nor no-IP answers), summed over its countries; completeness.json keeps each row's countries under per_country and per-country.tsv lists them (net, region, round, country, status, stop_reason, requests, rate_limited, answered, successes, unique_ips, duplicates, other_country, no_inventory, real_errors), with no addresses. A round measured before the classes counts 0 for each; other_country stays 0 until the census rounds run with an exit-country lookup on the workers.
  • The TSV keeps DATA-1's columns (net region round scheduled started finished completed delay duration countries jobs_ok missing dup badchunk no_success requests errors observations) and adds cell size start_lateness_s create_to_ready_s overlap bytes_up bytes_down protocol. jobs_ok counts measured countries and missing countries never run (a no_list country, one the provider has no login or exits for, is neither and leaves the cell complete), badchunk countries with a data finding, the droplet columns come from the cell's last worker (create_to_ready_s = SSH ready − create request) and protocol is the network grammar's echo-test protocol.

Verified collect. campaign collect --inventory I --campaign-id CID --dest D (collect.collect) reads the manager's host, identity_file, optional user (root), known_hosts and campaigns_root (/opt/proxy-index-campaign/campaigns) from the private local inventory. With known_hosts (written by manager deploy) SSH checks the manager's key strictly against that file (StrictHostKeyChecking=yes); without it the user's own known-hosts file applies. Then:

  1. the manager writes, with its system python3 (3.11 or newer, a manager image requirement), ARCHIVE-MANIFEST.sha256 (SHA-256 of every regular file except .runtime/; a symbolic link aborts) and reports the total size;
  2. it checks local free space: at least 1.25 × the size, keeping 20% of the disk free;
  3. one tar stream without .runtime/ is extracted with the data filter (no absolute paths, .., outside links or devices) into D, which must be new or empty;
  4. every file is verified against the manifest and collect-report.json lists mismatches, missing and extra files. The command exits 0 only when all three are empty, 3 otherwise.

The host appears only in the SSH command line; no output of these commands holds an IP address.

Image and watch

Worker image

Build the inputs on the exact main head, then the image (about 30 minutes, once per framework version):

uv build --wheel --out-dir dist
uv export --frozen --no-dev --no-emit-project --format requirements-txt > dist/requirements.txt
proxy-index campaign image build --account leftclick --wheel dist/proxy_index-<version>-py3-none-any.whl --requirements dist/requirements.txt --mmdb db-ip/<release>.mmdb

--mmdb puts the licensed DB-IP Location + ISP database (the release the framework uses for enrichment) into the image, so every worker applies the run-time country check (other-country exits). Before any cloud write the build opens the file, refuses one that is not a .mmdb or not a DB-IP database, and records mmdb_file and mmdb_sha256 in the build's inventory entry. The file travels in the provision tar (streamed from disk, about 1.35 GB) and ends at /opt/proxy-index-worker/db-ip/<file> (root-owned, 0644); each regional snapshot grows by about that size. A plan for a real campaign refuses an image whose build has no mmdb_sha256; only --synthetic plans (probe, shot, dry runs) may use one built without it.

image.build runs these steps; every id goes into the inventory .secrets/campaign-images.json (0600) before the next step:

  1. The Mac campaign key ~/.ssh/proxy-index-campaign (ed25519, created if absent, comment pi-camp-mac) is reused when its public part is already registered under a pi-camp- name, otherwise registered as pi-camp-mac-<yyyymmdd>.
  2. The builder pi-camp-builder-<yyyymmdd>-<hex4> (s-1vcpu-1gb, lon1, ubuntu-24-04-x64, tag pi-camp-builder, no monitoring, no droplet agent, no IPv6) is created and moved into project Proxy Index through scope.assign_and_verify_project (fail closed). After a lost create answer it is adopted by its exact name and tag.
  3. Over SSH (key only, a fresh known-hosts file), one tar on stdin carries assets/worker-provision.sh, the requirements, the wheel and, with --mmdb, the database. The script installs python3.12-venv, the pinned uv 0.12.10 (download checked against its SHA-256), the venv with --require-hashes requirements and the wheel (its SHA-256 in wheel.sha256); moves the database, if any (at most one), to /opt/proxy-index-worker/db-ip/; masks snapd, apt-daily*, unattended-upgrades and motd-news; keeps systemd-timesyncd on; limits cloud-init to datasource_list: [ DigitalOcean ]; sets key-only sshd in sshd_config.d/01-pi-camp.conf (read before cloud-init's 50-cloud-init.conf); locks the root password; removes host keys, authorized keys and the build inputs; runs cloud-init clean --logs --machine-id; empties the login logs (auth.log, wtmp, btmp, lastlog, syslog). Its last line is a hygiene check (including the effective sshd -T settings and empty login logs) that must print clean; anything else stops the build before any snapshot.

A resource the guard did not remove is listed under leftovers and the command fails. After a lost create answer that found no builder, leftovers holds builder_unresolved: <name>: check the builder count with campaign limits before building again.
  6. The inventory entry ends built (with snapshot_id, snapshot_name and regions) or failed with the error. The snapshot is kept for the campaign and removed at teardown.

Firewalls and keys

ops_api.worker_firewall(manager_ipv4) admits TCP 22 only from the manager, attached by the tag pi-camp-worker; ops_api.manager_firewall(mac_ipv4, manager_id) admits TCP 22 only from the Mac's public IPv4, attached by droplet id. Both allow all outbound traffic. apply_firewall creates one, or replaces the recorded one. DigitalOcean refuses (422) a firewall naming a tag that does not exist yet, as pi-camp-worker does before the first worker, so the client first reads each of the firewall's tags (GET /v2/tags/pi-camp-…) and creates a missing one (POST /v2/tags); it never puts a tag on or off a resource. A deploy that stopped there continues on a rerun. ensure_ssh_key registers a key once; release removes a recorded key, snapshot, droplet or droplet-free firewall through the guard. A firewall that names droplets (the manager's) needs a ledger that also records those droplet ids, which teardown passes to guarded_delete.

Deploy and operating guide

Every command runs on the Mac from the framework checkout; the private inventories live in .secrets/ (0600, gitignored): campaign-images.json (image build), campaign-manager.json (manager deploy), the manager's own known-hosts file campaign-manager.known_hosts (an inventory X.json gets its own X.known_hosts beside it, so retiring one manager never removes another's) and the audit campaign-ops-audit.jsonl. Live DigitalOcean writes happen only in the operator stages, only through these commands, and every removal goes through scope.guarded_delete.

Which account each command acts on. The manager inventory records the account and its project Proxy Index id (each team has its own). deploy and plan take --account and refuse it when it differs from the recorded account or the client's project id differs from the recorded one; deploy checks this before any write. allow-me and teardown have no --account: they use the recorded account and refuse a client whose project id differs. upload-spec refuses a spec for another account, project, manager or wheel. A campaign on another account needs its own manager and inventory (--inventory).

1. Manager deploy

  2. The script: keeps unattended security updates on with automatic reboot off; purges the droplet agent if present; writes the sshd drop-in 01-pi-camp.conf (PasswordAuthentication no, KbdInteractiveAuthentication no, PermitRootLogin prohibit-password, AuthenticationMethods publickey), replaces authorized_keys with the Mac key alone and locks the root password; creates /opt/proxy-index-campaign/ with venv/ (--require-hashes requirements, then the wheel), wheels/ (the wheel the workers receive), campaigns/ and .secrets/ (0700); generates the worker key .secrets/worker-key on the manager (it never leaves it); installs the units without enabling them. Anything else stops the deploy.

For the dry run and then the campaign: --networks all16,shifter,geonode once, or shifter first and the rest before the campaign.

The manager inventory holds host, user, identity and identity_file (the Mac key), known_hosts, campaigns_root and campaign_id (read by collect and watch), and the ids of the manager, firewalls and keys, the project, the wheel's SHA-256 and version, and the uploaded campaigns. A relative known_hosts is found beside the inventory, never in the current directory, and every SSH call to the manager (deploy, upload-spec, enable, disable, teardown, collect, watch) passes it as one quoted UserKnownHostsFile value (hostkeys.py), so the commands work from any directory and in a checkout whose path holds a space. The output holds ids only, never an address. The manager's system Python is 3.12, which collect's archive manifest needs (3.11 or newer).

2. Plan and upload

proxy-index campaign plan --account leftclick --start now-hour|2027-01-02T05:00:00+00:00 --networks shifter|all16|a,b [--regions …] [--concurrency 2000] [--size c-2] --image pi-camp-worker-… [--grace-hours 48] [--slot-minutes 60] [--slots 24] [--ssh-key-name …] [--synthetic] --output <dir>
proxy-index campaign manager upload-spec <dir>/<campaign id>

plan checks, before writing anything: each network's census config (configs/<net>-onboarding.toml when it exists, else configs/<net>.toml) names that provider and loads with .secrets/credentials.toml (load_provider, no network I/O, no values printed), and sets strict = false when the provider's grammar has a strict flag (Shifter, Geonode; owner decision 2026-10-25): the country is still sent, and a country with no exits is answered from another country (Shifter) or with a no-IP status (Geonode's 465 with strict targeting on), which the runner's answer classes count like duplicates toward the 50% rule instead of as errors (strict targeting). Telling an other-country exit apart needs the exit-country lookup on the workers: unless --synthetic, the image's build record must hold mmdb_sha256 (image build --mmdb), so a campaign never runs without the country check; the worker size (--size, default c-2; a CPU-Optimized c-… or Basic s-… slug) is offered in every region and is recorded per region in the spec's size_by_region; the snapshot recorded under that name exists in every region; exactly one key has the worker key's name; the project Proxy Index id; and the manager inventory (manager id, wheel). It then writes <dir>/<campaign id>/: one v3 ephemeral manifest per network under networks/<net>/residential/<mcid>/ with concurrency in its settings (the spec's --concurrency, capped at the network's grammar [testing] max_concurrency when it records one; the output lists concurrency_by_network) and that census config beside it as provider.toml (SHA-256 bound in the manifest), then campaign-spec.json. The campaign's network set is --networks all16,shifter,geonode: Geonode runs at 500, its grammar's max_concurrency. now-hour is the current whole UTC hour (the dry run); otherwise the start must be a future whole hour. --slot-minutes N (default 60; one of 5, 6, 10, 12, 15, 20, 30, 60) spaces the slots N minutes apart and --slots K (default 24, 1–24) limits the campaign to its first K slots: --slot-minutes 15 --slots 4 is one test hour with slots at :00, :15, :30 and :45, so consecutive slots overlap. Nothing changes for the default 60. upload-spec refuses a spec that names another manager or wheel and never writes over an existing campaign on the manager.

6. Collect and teardown (O3, teardown only on the owner's second go)

proxy-index campaign collect --inventory .secrets/campaign-manager.json --campaign-id <cid> --dest ~/Developer/Cursor/proxy-index-archive/campaign-<cid>/
proxy-index campaign manager teardown [--after-collect <dest>/collect-report.json …] [--keep-worker-assets]
  1. Refuses unless the client is the recorded account, every given collect report is clean (0 mismatches, 0 missing, 0 extra) and for a campaign uploaded to this manager, every such campaign has one, and no droplet carries pi-camp-worker. A manager that never recorded a campaign needs no --after-collect, and refuses any report given (it would prove nothing about this manager).
  2. While the manager exists and its secrets were not shredded yet: disables every campaign's units, then shreds every file under .secrets/ (shred -u: the token, the credentials and the worker key) and must read back shredded; otherwise nothing is removed. Before the shred it asks the manager whether /opt/proxy-index-campaign exists: a manager whose deploy stopped before making it holds no secrets, so only its own absent answer skips the shred (a failed probe refuses, any other answer goes on to the shred, and a failed shred still refuses). What this step found is recorded as secrets in the teardown result: shredded, none: … does not exist, shredded earlier or manager gone.
  3. Removes, each through scope.guarded_delete with its recorded id and its pi-camp- name on a fresh read, in this order: the manager (manager tag, name pattern, recorded id, project Proxy Index), pi-camp-manager-fw (the ledger records the manager's id, so a firewall naming it passes), pi-camp-worker-fw, the worker key, the Mac key, and every snapshot recorded in campaign-images.json. A refusal or failure is listed and the rest still go; the command then exits 3. While the manager remains, pi-camp-manager-fw is kept (kept: the manager remains), so SSH never opens on a live manager.
  4. Removes the Mac watch agent, and prints the count of droplets under every role tag and campaign tag as proof (all 0 for a clean teardown), and unassigned_managers: managers that failed their project assignment at deploy time and still exist (the guard refused or failed to remove them). Any of these keeps the teardown unclean; they go to the owner. The result is also recorded in the inventory.

Replace only the manager. --keep-worker-assets runs the same refusals, units and shred step, but removes only the manager and pi-camp-manager-fw; pi-camp-worker-fw, the worker key, the Mac key and the snapshots stay. Once clean, the manager is retired: its ids, campaigns and teardown result move to retired_managers, its worker key id to kept_worker_key_ids, and its host key file is removed. The inventory records that file beside itself; a relative record is read from the inventory's folder, never from the current directory, so a run from another folder cannot remove another manager's host keys. The next deploy (for example with --size s-2vcpu-4gb) then creates a new manager, points pi-camp-worker-fw at it and registers its own new worker key (the old one's private part was shredded with the old manager; a dated name already held gets a -<hex4> suffix so the plan finds one key). A later full teardown also removes the kept worker keys. After a retirement no manager is recorded, so teardown refuses (no manager is recorded) until the next deploy: the kept snapshots, worker firewall and keys are removed only by a full teardown of that next manager. A deploy that failed before its manager was recorded keeps the size it asked for on a rerun without --size. Plan the campaigns again for the new manager.

Rerun after a partial failure. Teardown is meant to be run again after a failed or refused removal (once the cause is fixed or the owner has decided): it skips the units and shred step once the secrets are shredded or the manager is gone, retries only the resources whose last result was not deleted or absent, and recomputes the proof. Never remove anything by hand.

Concurrency probe

Before the campaign, each network's highest safe concurrency is measured from one worker and recorded in its grammar as [testing] max_concurrency = N (provider grammars); campaign plan then runs each network at min(--concurrency, its maximum). Recorded from the 2026-10-24 probe: 2,000 for Shifter and 13 other networks, 500 for Proxy-Cheap and SOAX; Proxy-Seller was re-probed on 2026-10-25 with its port rotation and records 2,000; Geonode records 500 (owner decision 2026-10-25, to be confirmed by a probe at 500).

It:

  1. Refuses, before creating anything, a region the plan does not cover, a network it does not plan, a network without credentials on the manager, a census config that does not load with its credentials and the step's parameters (load_provider, no network I/O), or a start, floor or step out of range.
  2. Creates one worker with every worker marker under its own probe id (<yyyymmdd>t<hhmmss>z-<hex12>, like a campaign id): name pic-<sid>-h00-nyc3-probe, tags pi-camp-worker, pi-camp-<sid> and pi-camp-<sid>-h00, size c-4, the plan's snapshot and worker key, no monitoring, agent or IPv6. It is moved into project Proxy Index through scope.assign_and_verify_project (fail closed: a worker that is not confirmed is removed on the own-unassigned path and never used).
  3. Sends, on SSH stdin only, the wheel, each network's census config (provider.toml beside its manifest) and its credentials (written 0600 under /run/proxy-index-worker/probe/), and installs the wheel into the image's venv.
  4. For each network in turn: proxy-index run --target generic_http --requests 25000 --timeout 10 --answer-classes --param country=US (the country only for a network whose grammar has a country flag; a preset country flag accepts only its configured country, so another is refused when the probe is checked; --mmdb is added when the image holds exactly one database in /opt/proxy-index-worker/db-ip/, so the step and the shot report other-country %) at the floor (500) as the baseline, then at 2,000, 1,500 and 1,000 until a step passes the rule below. The first passing step is the network's maximum; if none passes, the floor. The baseline runs first because every relative limit below compares with it; it costs one more 25,000-request run per network (400,000 requests for 16) when 2,000 passes at once, and gives the 500 step the owner's ladder ends with anyway. A network below 50% success at the floor is not probed further (unusable at the floor; run failed at the floor when the run itself failed; no maximum); a floor that itself breaks the rule keeps 500 with floor also fails: …, which the table shows instead of a grammar line. A step's SSH run is limited to 30 minutes; a failed or unreadable run counts as run_failed.
  5. Removes the worker through scope.guarded_delete whatever happened, also when SIGTERM, SIGHUP or SIGINT stops the run (the first one cancels it; later ones are ignored until the removal is done): the plain path once its project membership was confirmed, the own-unassigned path when a failed assignment marked it, and otherwise after confirming it in the project first, as a resumed launch does. A refusal is destroy_refused, an error destroy_failed; both, or any error, make the command exit 3. Every attempt is in the probe's ledger/delete-audit.jsonl.

Worker saturation. The probe measures the network and this one c-4 worker together, and records no worker CPU or load per step: a step that fails at 2,000 with CPU-bound symptoms (latency rising for every class, low RPS at high concurrency) may be the worker's limit rather than the network's. The campaign's c-4 workers run the same load, so the maximum still holds for them; for a larger worker size, probe again with --size.

A worker left behind. A lost create answer is looked up again by exact name 15 seconds later, as a launch does; a worker still not listed, a removal that failed, or a probe process that died (OOM, reboot, kill -9) leaves the worker alive, and manager teardown refuses while any pi-camp-worker droplet exists. The probe's record (probe-result.json: probe id, the scope's project, manager and creation time, and the worker's name, id and assignment marks, written before the create and after every step) is enough to remove it; the result names the command under recover:

/opt/proxy-index-campaign/venv/bin/proxy-index campaign probe --remove /opt/proxy-index-campaign/probes/<probe id>

It finds the worker by its exact name under the probe's hour tag (only the recorded id when one is recorded) and removes it through release as above; absent means a listing that answered found nothing (never created, or already gone); when the listing or the read cannot be done, it stops with an error, changes nothing and can simply be run again. A probe stopped during its create (also by a signal) still names the command. A guard refusal (destroy_refused) goes to the owner; never remove a worker by hand. It is safe to run again.

Answered requests. Every step runs with --answer-classes, so a rate-limited request (HTTP 429 on every network, Geonode's 469, DataImpulse's refused or dropped gateway connections while the run is still succeeding) is replaced and does not count toward the 25,000: the step ends at 25,000 answered requests (completed minus rate-limited), or on the runner's two-minute rate-limit safety stop (answer classes).

The step-down rule. Each class is a share of the step's completed requests. A step fails for concurrency, and the next lower one is tried, when any of these holds:

  • rate_limited: the run's rate-limit signals above 2% (HTTP 429 and Geonode's 469 for a result written before the answer classes): rate limits are not failures, but they still mean the concurrency is above what the account accepts;
  • proxy_connect: the gateway refused or could not be reached (proxy_connect, connection, proxy_auth, dns: CONNECT refused, reset, a 407, which some gateways send at a connection or thread limit, an unresolvable gateway; refused or dropped connections (proxy_connect, connection) the run counted as rate limits are under rate_limited instead) above 2%;
  • timeouts_5xx: timeouts plus 502/503/504 above both twice the baseline's rate and the baseline's rate plus one point (0.4% at 500 allows up to 1.4%);
  • other_errors: every other failure (TLS, protocol and body errors, other HTTP statuses such as 403 or 500, challenges and blocks; not the no-IP answers, which are their own class) above both twice the baseline's rate and the baseline's rate plus one point;
  • success_drop: success more than 3 points below the baseline's, whatever the classes (it catches several classes each just under its own limit, and a high baseline rate that doubles);
  • incomplete: fewer than 95% of the requests answered (a stop rule, such as the rate-limit safety stop, ended the run; completed for a result written before the answer classes), or run_failed.

The absolute 2% limits catch a gateway that refuses extra connections or rate-limits the account; the relative limits separate load from a network's normal timeout, 5xx and other error rates, which differ widely between networks; the success drop bounds the sum. A CONNECT answered with 429 or a 5xx (HTTPS-only networks) counts under its status and under connect errors.

The output (the journal, and probe-result.json and probe-result.md under /opt/proxy-index-campaign/probes/<probe id>/) holds, per network and step: concurrency, requested, completed and answered requests, success %, rate-limited %, 5xx %, connect %, timeout %, no-IP % and other error % (shares of completed requests), other-country % (only when the run had an exit-country lookup), duplicates % (successes beyond the unique IPs, of completed), real errors % (errors that are neither rate limits nor no-IP answers, of answered requests), requests per second, p50 and p95 success latency, the step-down reasons, and the maximum with its grammar line. It holds the worker's id, never an address; the run's IP data stays on the worker and goes with it. Copy each maximum into src/proxy_index/providers/grammars/<net>.toml in a reviewed pull request before the campaign is planned.

Synchronized shot

The probe measures each network from one worker; the shot checks that the recorded max_concurrency holds when every network runs in every region at the same time. It reuses the probe's setup, step command, result classes and guarded removal, and runs on the manager from the same kind of uploaded plan (one that covers the shot's networks and regions):

systemd-run --unit=pi-camp-shot --property=UMask=0077 --property=TimeoutStopSec=20min /opt/proxy-index-campaign/venv/bin/proxy-index campaign shot --root /opt/proxy-index-campaign/campaigns/<campaign id> --size c-4 --size-by-network soax=c-2,proxy-cheap=c-2
journalctl -u pi-camp-shot -f        # the summary, also in /opt/proxy-index-campaign/shots/<shot id>/
systemctl stop pi-camp-shot          # stops it early; every worker is still removed
grep -E '"(workers_left|recover)"' /opt/proxy-index-campaign/shots/<shot id>/shot-result.json
/opt/proxy-index-campaign/venv/bin/proxy-index campaign shot --remove /opt/proxy-index-campaign/shots/<shot id>   # while recover is present

Stop timeout. The removal makes about three guarded calls per worker (a fresh read, the project listing, the delete), and the client sends at most 200 calls a minute: 136 workers take about 2–3 minutes, longer than systemd's default 90-second stop timeout, after which the unit would be killed mid-removal. TimeoutStopSec=20min lets systemctl stop finish it. A shot that is killed or crashes anyway keeps its record: shot-result.json names recover from its first write, and only a removal that ends with workers_left: 0 drops it. After any stop or failure, read workers_left and recover, run --remove until it reports 0, and finish with the worker count of campaign limits (0 under pi-camp-worker).

  1. Refuses, before any call, a repeated region or network, a region or network the plan does not cover, a network whose country flag is a preset (only its list's country loads) unless --country-by-network names it, a region with no country, a per-network setting for a network outside the shot, a size that is not a worker slug, and a network whose census config does not load with its credentials and each region's country. Then checks that every worker's size is offered in its region (read-only).
  2. Records the start time, --lead-minutes (default 10) after the shot begins, before anything is created.
  3. Creates one worker per network and region (pic-<sid>-h00-<region>-<network>, the probe's markers and tags under its own shot id), at most 10 names per create call per region and size; a lost answer is adopted by exact name, again 15 seconds later. A second droplet with a worker's name (one the create or adoption returned that no record holds) is recorded under unrecorded, removed through the guard and counted in workers_left. Every created droplet is confirmed in project Proxy Index in one call; an unconfirmed one is removed on the own-unassigned path and never used.
  4. Waits for every worker to be active (one listing by the shot's tag per poll), ready over SSH and set up with only its own network's census config and credentials. A worker with no time left before the start gets no setup and no credentials.
  5. At the start time, every worker that is set up runs one proxy-index run --target generic_http --requests 25000 --timeout 10 --answer-classes (25,000 answered requests) at its network's concurrency (the plan's value, capped at the grammar's max_concurrency), with the region's country: lon1 GB, fra1 DE, ams3 NL, nyc3 US, tor1 CA, sgp1 SG, blr1 IN, syd1 AU, unless --country-by-network names one (a network whose list holds one country). A worker that is not set up by the start time is late and is never started late; a failed setup is setup_failed.
  6. Removes every worker through the guard whatever happened, also on SIGTERM, SIGHUP or SIGINT, as the probe does. A worker left behind is reported with workers_left and the recovery command campaign shot --remove /opt/proxy-index-campaign/shots/<shot id>, which looks up each recorded worker by exact name under the shot's hour tag and removes it as campaign probe --remove does.

The output (shot-result.json and shot-result.md) holds per network and region: country, size, concurrency, outcome (measured; late, never started; setup_failed; run_failed, an unreadable step; failed, an error after the start; create_failed; unconfirmed, removed before use; not_created, the shot stopped before its create; cancelled, stopped mid-way by a signal or the shot's own error), the probe's step classes (rate limits in their own column; no-IP, other-country, duplicates and real errors of answered requests beside them, "-" in a result written before them), RPS, p50/p95 success latency, unique exit IPs, the start lag in seconds and the step-down rules that need no baseline (incomplete, rate_limited, proxy_connect, run_failed). The relative rules are applied afterwards against the probe's step at the same concurrency. No address is written.

A shot of 17 networks in 8 regions creates 136 workers at once: check the account's droplet limit first (campaign limits).

Daily tests

Each network's formula (formulas/<network>.json) gives every country one UTC test hour (schedule). In hour H the planner takes every (network, country) pair due at H and groups each network's countries by the runner region that serves them (configs/regions.yaml): one droplet per network and region with something due, none elsewhere. Nothing new launches or deletes droplets: the hour runs through this campaign's tick, launch, harvest and guard.

proxy-index daily plan --formulas formulas [--template <planned root>] [--start now-hour|next-hour|<ISO hour>]   # prints the droplet plan, writes nothing
proxy-index daily run --formulas formulas --template /opt/proxy-index-campaign/campaigns/<template id> [--start next-hour]   # on the manager
proxy-index daily ingest --inventory <inventory> --campaign-id <hour campaign id> --dest <dir> --database-file <credentials> [--mmdb <DB-IP mmdb>] [--formulas formulas]   # on the Mac
  1. Template. One planned ephemeral campaign (campaign plan with the networks and regions to test, uploaded with manager upload-spec) supplies the account, project, images, worker key, wheel and each network's manifest settings: the same concurrency and stop rule as the 24-hour rounds, the target http://ip-info.com/myip and each network's HTTPS redirect. daily plan --template also names the due networks the template cannot test (skipped) and refuses a due region it does not cover.
  2. Run. daily run writes a fresh one-slot campaign beside the template (new campaign id; per network a manifest re-created for the hour with the template's settings and the optional v3 key due_countries, {region: [codes]}, a subset of the region's list in manifest order). The launch creates no worker for a network and region with nothing due, and each round measures only the due countries. tick launches slot 0 and the collector harvests it until done, for at most the hour's slot plus 30 minutes. Whatever happens (an error, the time limit, or SIGTERM, SIGHUP or SIGINT, which cancel the run; a later signal never interrupts the removal), every recorded worker still up is removed through the guard, a worker whose create was in flight first taken by its exact name under the hour's tag and confirmed in project Proxy Index (one not confirmed is removed on the own-unassigned path; when they cannot be taken, the recorded workers are still removed), and every worker of the hour (recorded or still carrying the hour's tag) is read until it is gone. The outcome is <hour root>/daily.json (state, plan, leftover ids, error; cleanup says why workers were not removed: a launcher still held the hour, or the in-flight ones could not be taken; a TimeoutError raised by the run itself is an error, not the time limit; no address); the command exits 3 unless the hour is done and nothing is left. Workers need a wheel with due_countries; an older one runs the whole region.
  3. Ingest. daily ingest downloads the hour root with campaign collect (a rerun reuses a verified download; an unverified one exits 3), verifies each network and region round, turns each completed country into a run directory under runs/<run id>/ (the measurement as summary.json, the observations as IP rows per 5-minute bucket in ips.jsonl.gz), enriches it with DB-IP and imports it with storage.ingest. Each converted summary.json carries test_kind = daily, the run-identification contract of proxy_index.daily: the pulse latency baseline (pulse.latency_baseline) is the latest such run of a network in a country, and runs converted before the marker existed carry none, so the flagged census baseline applies until the next daily test. Each cell then gets daily_test_started and daily_test_finished (TAPE-1): done only when every due country was measured and imported. A rerun is safe: converted runs are reused, the import replays as a no-op, and a cell whose events are recorded in daily-ingest.json gets no second pair; a network not yet in the database gets its events on a later rerun. The first pair emitted is authoritative: a rerun that imports a country that failed before adds its data but no corrected event. A database error fails only its country or its cell's events (retried on a rerun). The marker needs no schema change.
  4. Estimates. With --formulas, every imported country also gets its estimated hours (schema v10, table estimated_hours; the measured tables are untouched): one row per network, country, UTC day and hour for the 24 hours from the measured hour, holding the measured IPs and requests, the run it came from and the formula version. Hour unique IPs = measured IPs × the hour factor over the measured hour's; requests follow the request curve the same way; the day's unique IPs = measured IPs × the daily factor over the measured hour's. A country on the network curve (curve network) uses the network's request curve; an hour whose factor is null gets no row. A rerun rewrites only unreleased hours, and an older test never replaces a newer one's. A missing formula or country is listed in the cell's estimate_issues and makes the report incomplete; the test itself still counts. So does a test that started outside its scheduled hour when the formula has no factor at the hour it measured (byteful's network curve, for one, is zero outside 16 UTC): it gets no estimates, and daily ingest exits 3.
  5. Release. An estimated hour is released once its UTC hour has ended (released_at), oldest first, each network hour with one estimate_hour_released event (TAPE-1) for all its countries, never one per country (its data carries day, hour, formula_version, the summed unique_ips and the countries count, TAPE-2), by the orchestrator's estimates_release job every minute and at the end of each ingest. The calculator windows (24h, 7d, 30d) then carry an estimated block beside the measured figures, never mixed into them: requests, unique IPs, per country and per hour, each flagged estimated with its formula_version; breakdown_scale scales the measured city, region, ASN and country shares; overlap, datacenter ASN share and latency stay the measured ones. Estimated hours older than retention.estimates_days (default 30, the longest window) are deleted by the daily retention job. Window unique IPs, set by [estimates] window_unique in the methodology: distinct (default) counts the exact distinct IPs the window's tests measured (of that product window's cohort only), scaled by their day factor, so an IP seen on several days counts once; sum adds each test's day estimate.
  6. Calculation cadence. The orchestrator's calculate job runs once an hour, calculate.hour_offset_seconds (default 360) after the hour, so the hour just released is in: the calculator floors as_of to 5 minutes and the release job runs every minute, so an offset below 360 is raised to 360 with a warning; calculate.trigger batch restores the earlier schedule (after every import batch, debounced).

Nothing schedules the run yet: a timer (each hour, or --start next-hour a few minutes before it) is installed only on the owner's go.
