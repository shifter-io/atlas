Proxy Index · Private operator workflow

Hourly droplet campaign

Every hour, one fresh worker droplet per network and region runs one onboarding round to its natural end, hands its data to a manager droplet and is destroyed. The account also holds production droplets of other projects, so every destructive step is provably scoped to resources this campaign created.

Overview

A manager droplet launches 16 networks × 8 regions = 128 workers per hour from a prepared snapshot, starts onboarding round on each at the whole hour, collects and verifies each finished round, and destroys the worker through the scope guard. Hours overlap freely; there is no request cap and no round deadline. A per-hour traffic report per network goes to the owner.

The only delete path

scope.guarded_delete(cloud, kind, id, scope, ledger, audit_path, role) deletes one resource by id. The Ledger holds the recorded ids per kind (an SSH key id never matches a droplet record) and the droplet records. role says which droplet the caller means: a worker, the recorded manager or a builder. For a droplet it takes a fresh GET immediately before the DELETE and requires every check:

  1. recorded: the id is in the campaign's ledger (or the recorded manager or builder id);
  2. tags: the role's tags are present (a worker also needs its campaign tag) and no other role's tag is;
  3. name: the role's exact name pattern, and for workers the campaign's short id;
  4. project_id and project: the scope's project id is the project named Proxy Index (checked once per client), and the droplet is in it (membership cached for at most 60 s and always re-read on a miss). Only the own-unassigned path may replace the membership check, and only when all of these hold: the record is assign_failed, set by assign_and_verify_project for this exact id in this process; the id came back from this client's own create; and the droplet is at most 30 minutes old. Its audit lines carry path: own_unassigned;
  5. not_manager: a worker or builder delete never targets the recorded manager id; a manager delete targets only it;
  6. created_after: created at or after the scope's time (the spec, or the inventory time for manager and builder).

Keys and snapshots need a recorded id and a pi-camp- name; firewalls also must reference only pi-camp- tags and recorded droplet ids. Every attempt appends to ledger/delete-audit.jsonl (0600): one attempt line just before the DELETE, then deleted, or a single refused, absent or failed line (any error, with its type). A refusal raises OwnershipError and never falls back to another path.

Enforcement

  • The client sends only the calls in its allowlist (do_api.ALLOWED): an exact method (any letter case is normalized first), a path pattern and the query keys allowed. Droplets are listed only by a pi-camp- tag. Everything else (droplet actions such as rebuild or power-off, tag changes, PUT, PATCH, listing all droplets) is refused before the network. DELETE (one resource, no query) and project assignment also need the token only scope.py holds (require_guard). Later tasks add their own endpoints to the allowlist under scope review.
  • Neither the Cloud protocol nor the client has a delete method.
  • tests/test_campaign_scope.py runs every destructive path against a fake account seeded with 1,125 production-like droplets and every near-miss of the markers, even with a ledger that lists every droplet, and proves only ours are deleted. A static scan of every file in src/proxy_index/campaign/, including later ones, allows the word delete (any case), raw client access and assign_project calls only in scope.py and do_api.py; a second scan of all of src/ and scripts/ finds no direct API host, no doctl and no import of the client's private names. A gate test keeps scope.py and do_api.py at 100% line and branch coverage.

Project assignment fails closed

scope.assign_and_verify_project(cloud, scope, droplet_ids, records, audit_path, role) is the only assignment path and returns (confirmed, failed). Before any request, each id must have its ledger record, have come from this client's own create, and show every marker on a fresh GET; anything else raises OwnershipError. It assigns the ids to the verified Proxy Index project and re-reads the project, up to 3 tries 5 s apart. A confirmed droplet becomes assigned. A droplet that is not confirmed fails closed: it becomes assign_failed (error_class project_assign_failed), must never be pushed or started, and is deleted at once through the guard (the own-unassigned path, or the normal path if the assignment landed late). Its record ends as destroyed, or destroy_refused / destroy_failed for the caller to flag.

Contracts

contracts.py is frozen: a change is its own reviewed task, merged first and re-run against the scope suite. It defines the tags and name patterns above, the accounts (leftclick, proxy-index, both with project Proxy Index), CampaignSpec (validated; JSON round-trip; concurrency per worker, default 2,000, 1–5,000), DropletRecord (with per-worker concurrency and CPU, steal, load and memory samples) and HourRecord (no IP addresses), Droplet and Scope, the Cloud and Remote protocols and the campaign-root paths (campaign-spec.json, ledger/HH/hour.json, ledger/delete-audit.jsonl, networks/<net>/residential/<mcid>, logs/HH, reports, status.json, alerts.jsonl, .runtime).

Client and limits

do_api.DigitalOcean(token_source) reads the token from the keychain (keychain_token(account)) or from a 0600 file owned by the current user (file_token(path)). The token lives in memory only and never appears in repr, errors or logs.

  • create refuses names or tags without every marker and sends at most 10 names per call, always with ssh_keys, monitoring, with_droplet_agent and ipv6 as given.
  • Listing pages hold 200 items; a page without meta.total is an error, so a listing never ends early.
  • A 429 waits for Retry-After or the rate-limit reset (at most 60 s); 5xx and connection errors back off 1, 2, 4, 8 s; other errors raise ApiError with method, path and status only. A droplet create is never retried after a 5xx or a lost answer, because it may already exist: create raises CreateError with the droplets already created and the names still pending (uncertain when the outcome is unknown). Resolve an uncertain create with adopt_uncertain(names, hour_tag), which finds exactly those names under our tag, before any re-create.
  • A limiter allows at most 200 requests per minute; ratelimit_remaining shows the API's count.

project_id(name) resolves project Proxy Index by its exact name; account() returns only the droplet limit and account status. A read-only campaign limits command, which prints counts only, follows in a later task.

Launch

launch.launch_hour(spec, record, root, cloud=…, remote_factory=…, clock=…) brings one hour from planned to running under the hour's lock (ledger/HH/.lock); the launcher owns hour.json until then, and saves it after every step.

  1. Plan. One DropletRecord per network and region (name pic-<sid>-hNN-<region>-<network>, size, image, the spec's concurrency, and overlap: the network and region's workers of earlier hours that are still armed or running). Cells start pending; traffic gets each network's countries_total. Names are on disk before any create.
  2. Wait for the lead. A launch earlier than scheduled_at − create_lead_seconds (HH:58:30) waits; onboarding round itself waits for HH:00:00.
  3. Adopt first. Before any create, recorded names without an id (or whose id this process did not create) are resolved with adopt_uncertain(names, hour_tag); ids another record already holds are never taken. A crashed launch therefore never creates a name twice.
  4. Create per region (at most 10 names per call) with the tags pi-camp-worker, pi-camp-<sid>, pi-camp-<sid>-hNN, the spec's SSH key, and monitoring, agent and IPv6 off. Ids are saved right after the answer. An uncertain answer is adopted by name; names still missing are retried once after 15 s, then create_failed.
  5. Assign every new id of the region through scope.assign_and_verify_project (one POST per region, 3 checks 5 s apart). An unconfirmed worker is never pushed; the guard removes it on the own-unassigned path and the hour gets a project_assign_failed alert.
  6. Ready. One GET /v2/droplets?tag_name=pi-camp-<sid>-hNN per 2 s, shared by every waiting worker, until the droplet is active with a public IPv4 (written only to .runtime/hosts-HH.json, 0600), then SSH; both within 180 s of the create.
  7. Push and arm. One tar on SSH stdin: the network's manifest, provider.toml (next to the manifest on the manager), assignment.json, the wheel whose SHA-256 the spec binds (from <base>/wheels/) and that network's credentials (from <base>/.secrets/credentials/<network>.toml), where <base> holds campaigns/<cid>. A push error is retried once on the same worker. A resumed worker that was already starting is inspected first and not pushed twice.

A boot, SSH, start or assignment failure removes the worker through scope.guarded_delete (a refusal is destroy_refused with a high alert and no fallback; an error is destroy_failed and retried by the next harvest pass) and gets one replacement, only before HH:00 + replace_until_minutes. The cell is failed_ours unless the replacement arms. An unexpected error fails only its own worker, no task outlives the launch, and every worker leaves it armed or in a final status: without a droplet create_failed, with one removed through the guard (which refuses an unassigned droplet it cannot prove ours); error_class keeps the cause. Synthetic specs make no cloud or SSH calls and arm every worker at once.

Worker start (fanout.START_SCRIPT, run by the worker's system Python with public arguments only): it writes the credentials to /run/proxy-index-worker/credentials.toml (0600, never under the worker root), extracts the rest with the data filter, installs the wheel with uv pip install --no-deps --offline only when its SHA-256 differs from the installed one, waits up to 10 s for NTPSynchronized, records both in worker-start.json in the round directory, writes active-run.json (the fleet marker), and starts systemd-run --unit=pi-camp-round (LimitNOFILE=65536, UMask=0077, Restart=no, RemainAfterExit=yes so the exit status stays readable; no run-time limit) and the sampler unit pi-camp-sampler.

SSH. fanout.OpenSSHRemote(identity, runtime, hour) runs ssh with BatchMode=yes, IdentitiesOnly=yes, User=root, a per-hour UserKnownHostsFile with accept-new, ConnectTimeout=5, ServerAliveInterval=10, ServerAliveCountMax=3 and ControlMaster=auto, ControlPersist=4h. The control socket is .runtime/cm-%C when that path fits the socket-path limit; under the manager's campaign root it does not, so sockets go to a private /tmp/pi-camp-cm-<uid>/. inspect runs fleet.REMOTE_INSPECT; stop sends SIGTERM to the round unit; pull streams the round directory only once its checkpoint is terminal or the round unit has ended (a killed round never writes a terminal checkpoint); while the unit runs, or when its state cannot be read, the pull is refused. It extracts it only when every entry lies under that directory, with no absolute path, .., link or device; journal keeps the last 5 MB of both units. Errors are fixed text with the exit code, never the host or its output.

Sampler (python -m proxy_index.campaign.sampler --interval 1 --output <round dir>/host-samples.jsonl): every second it appends total and per-core CPU busy, steal, load1, used memory and the RSS of the round unit's processes, and stops when the round unit has no process left. The file is pulled with the round; verify_round does not read it. sampler.summarize gives the record's cpu_p50_pct, cpu_p95_pct, cpu_max_pct, cpu_core_max_pct, steal_p95_pct, load1_p95, mem_used_max_pct, cpu_peak_pct and rss_peak_mb.
