Hourly droplet campaign

Every hour, one fresh worker droplet per network and region runs one onboarding round to its natural end, hands its data to a manager droplet and is destroyed. The account also holds production droplets of other projects, so every destructive step is provably scoped to resources this campaign created.

Overview

A manager droplet launches 16 networks × 8 regions = 128 workers per hour from a prepared snapshot, starts onboarding round on each at the whole hour, collects and verifies each finished round, and destroys the worker through the scope guard. Hours overlap freely; there is no request cap and no round deadline. A per-hour traffic report per network goes to the owner.

The only delete path

scope.guarded_delete(cloud, kind, id, scope, recorded_ids, audit_path, role=…) deletes one resource by id. For a droplet it takes a fresh GET immediately before the DELETE and requires every check:

  1. recorded: the id is in the campaign's ledger (or the recorded manager or builder id);
  2. tags: the role's tags are present (a worker also needs its campaign tag) and no other role's tag is;
  3. name: the role's exact name pattern, and for workers the campaign's short id;
  4. project: the droplet is in project Proxy Index (membership cached for at most 60 s and always re-read on a miss);
  5. not_manager: a worker or builder delete never targets the recorded manager id; a manager delete targets only it;
  6. created_after: created at or after the scope's time (the spec, or the inventory time for manager and builder).

Keys and snapshots need a recorded id and a pi-camp- name; firewalls also must reference only pi-camp- tags and recorded droplet ids. Every attempt (deleted, refused, absent or failed) appends one line with each check's result to ledger/delete-audit.jsonl (0600). A refusal raises OwnershipError and never falls back to another path.

Enforcement

  • The client's request() refuses DELETE unless it carries the token only scope.py holds, and only for a single resource path with no query: there is no bulk, by-tag, by-name or by-project delete.
  • Neither the Cloud protocol nor the client has a delete method.
  • tests/test_campaign_scope.py runs every destructive path against a fake account seeded with 1,125 production-like droplets and every near-miss of the markers, even with a ledger that lists every droplet, and proves only ours are deleted. A static scan of every file in src/proxy_index/campaign/, including later ones, allows "DELETE" only in scope.py and do_api.py. A gate test keeps scope.py at 100% line and branch coverage.

Project assignment fails closed

scope.assign_or_destroy assigns droplets we just created (recorded ids whose create response shows every marker; anything else is refused before any request) to project Proxy Index and re-reads the project to verify, up to 5 times 15 s apart. A droplet that never arrives is passed to the guard: if the assignment landed late it is deleted; otherwise the guard refuses it (it is not provably ours), the droplet stays up, and the caller flags the hour with a high alert for the operator.

Contracts

contracts.py is frozen: a change is its own reviewed task, merged first and re-run against the scope suite. It defines the tags and name patterns above, the accounts (leftclick, proxy-index, both with project Proxy Index), CampaignSpec (validated; JSON round-trip), DropletRecord and HourRecord (no IP addresses), Droplet and Scope, the Cloud and Remote protocols and the campaign-root paths (campaign-spec.json, ledger/HH/hour.json, ledger/delete-audit.jsonl, networks/<net>/residential/<mcid>, logs/HH, reports, status.json, alerts.jsonl, .runtime).

Client and limits

do_api.DigitalOcean(token_source) reads the token from the keychain (keychain_token(account)) or from a 0600 file owned by the current user (file_token(path)). The token lives in memory only and never appears in repr, errors or logs.

  • create refuses names or tags without every marker and sends at most 10 names per call, always with ssh_keys, monitoring, with_droplet_agent and ipv6 as given.
  • list_tag refuses tags without the pi-camp- prefix; listing pages hold 200 items.
  • A 429 waits for Retry-After or the rate-limit reset (at most 60 s); 5xx and connection errors back off 1, 2, 4, 8 s; other errors raise ApiError with method, path and status only.
  • A limiter allows at most 200 requests per minute; ratelimit_remaining shows the API's count.

project_id(name) resolves project Proxy Index by its exact name; account() returns only the droplet limit and account status. A read-only campaign limits command, which prints counts only, follows in a later task.
