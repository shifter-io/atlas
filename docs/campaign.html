Hourly droplet campaign

Every hour, one fresh worker droplet per network and region runs one onboarding round to its natural end, hands its data to a manager droplet and is destroyed. The account also holds production droplets of other projects, so every destructive step is provably scoped to resources this campaign created.

Overview

A manager droplet launches 16 networks × 8 regions = 128 workers per hour from a prepared snapshot, starts onboarding round on each at the whole hour, collects and verifies each finished round, and destroys the worker through the scope guard. Hours overlap freely; there is no request cap and no round deadline. A per-hour traffic report per network goes to the owner.

The only delete path

scope.guarded_delete(cloud, kind, id, scope, ledger, audit_path, role) deletes one resource by id. The Ledger holds the recorded ids per kind (an SSH key id never matches a droplet record) and the droplet records. role says which droplet the caller means: a worker, the recorded manager or a builder. For a droplet it takes a fresh GET immediately before the DELETE and requires every check:

  1. recorded: the id is in the campaign's ledger (or the recorded manager or builder id);
  2. tags: the role's tags are present (a worker also needs its campaign tag) and no other role's tag is;
  3. name: the role's exact name pattern, and for workers the campaign's short id;
  4. project_id and project: the scope's project id is the project named Proxy Index (checked once per client), and the droplet is in it (membership cached for at most 60 s and always re-read on a miss). Only the own-unassigned path may replace the membership check, and only when all of these hold: the record is assign_failed, set by assign_and_verify_project for this exact id in this process; the id came back from this client's own create; and the droplet is at most 30 minutes old. Its audit lines carry path: own_unassigned;
  5. not_manager: a worker or builder delete never targets the recorded manager id; a manager delete targets only it;
  6. created_after: created at or after the scope's time (the spec, or the inventory time for manager and builder).

Keys and snapshots need a recorded id and a pi-camp- name; firewalls also must reference only pi-camp- tags and recorded droplet ids. Every attempt appends to ledger/delete-audit.jsonl (0600): one attempt line just before the DELETE, then deleted, or a single refused, absent or failed line (any error, with its type). A refusal raises OwnershipError and never falls back to another path.

Enforcement

  • The client sends only the calls in its allowlist (do_api.ALLOWED): an exact method (any letter case is normalized first), a path pattern and the query keys allowed. Droplets are listed only by a pi-camp- tag. Everything else (droplet actions such as rebuild or restore, tag changes, PATCH, listing all droplets) is refused before the network. The operations calls also have a checked body (do_api.BODIES): a droplet action is only shutdown, power_off or a snapshot named pi-camp-worker-…; an image action is only a transfer to one of the 8 regions; a new SSH key and every firewall need a pi-camp- name, and a firewall may name only the role tags. DELETE (one resource, no query) and project assignment also need the token only scope.py holds (require_guard). Later tasks add their own endpoints to the allowlist under scope review.
  • Writes that could touch a droplet or firewall we may not own (droplet actions, firewall create and replace; do_api.OWNED_WRITES) are refused by the HTTP layer unless they carry a token private to do_api.py, the same way DELETE needs the scope guard's token. Only the client's own methods pass it, and only after an ownership check on a fresh GET: droplet actions run only on a builder this client created (builder tag and name) that is in project Proxy Index; a firewall is created or replaced only when it, and the firewall it replaces, has a pi-camp- name, only role tags, and only droplets that show a role's tag and name and are in project Proxy Index. A transfer only copies a snapshot whose name is a campaign worker snapshot. A power-off or a firewall can therefore not reach a production droplet, through the methods or through request().
  • Neither the Cloud protocol nor the client has a delete method.
  • tests/test_campaign_scope.py runs every destructive path against a fake account seeded with 1,125 production-like droplets and every near-miss of the markers, even with a ledger that lists every droplet, and proves only ours are deleted. A static scan of every file in src/proxy_index/campaign/, including later ones, allows the word delete (any case), raw client access and assign_project calls only in scope.py and do_api.py; a second scan of all of src/ and scripts/ finds no direct API host, no doctl and no import of the client's private names. A gate test keeps scope.py and do_api.py at 100% line and branch coverage.

Project assignment fails closed

scope.assign_and_verify_project(cloud, scope, droplet_ids, records, audit_path, role) is the only assignment path and returns (confirmed, failed). Before any request, each id must have its ledger record, have come from this client's own create, and show every marker on a fresh GET; anything else raises OwnershipError. It assigns the ids to the verified Proxy Index project and re-reads the project, up to 3 tries 5 s apart. A confirmed droplet becomes assigned. A droplet that is not confirmed fails closed: it becomes assign_failed (error_class project_assign_failed), must never be pushed or started, and is deleted at once through the guard (the own-unassigned path, or the normal path if the assignment landed late). Its record ends as destroyed, or destroy_refused / destroy_failed for the caller to flag.

Contracts

contracts.py is frozen: a change is its own reviewed task, merged first and re-run against the scope suite. It defines the tags and name patterns above, the accounts (leftclick, proxy-index, both with project Proxy Index), CampaignSpec (validated; JSON round-trip; concurrency per worker, default 2,000, 1–5,000), DropletRecord (with per-worker concurrency and CPU, steal, load and memory samples) and HourRecord (no IP addresses), Droplet and Scope, the Cloud and Remote protocols and the campaign-root paths (campaign-spec.json, ledger/HH/hour.json, ledger/delete-audit.jsonl, networks/<net>/residential/<mcid>, logs/HH, reports, status.json, alerts.jsonl, .runtime).

Client and limits

do_api.DigitalOcean(token_source) reads the token from the keychain (keychain_token(account)) or from a 0600 file owned by the current user (file_token(path)). The token lives in memory only and never appears in repr, errors or logs.

  • create refuses names or tags without every marker and sends at most 10 names per call, always with ssh_keys, monitoring, with_droplet_agent and ipv6 as given.
  • Listing pages hold 200 items; a page without meta.total is an error, so a listing never ends early.
  • A 429 waits for Retry-After or the rate-limit reset (at most 60 s); 5xx and connection errors back off 1, 2, 4, 8 s; other errors raise ApiError with method, path and status only. A droplet create is never retried after a 5xx or a lost answer, because it may already exist: create raises CreateError with the droplets already created and the names still pending (uncertain when the outcome is unknown). Resolve an uncertain create with adopt_uncertain(names, hour_tag), which finds exactly those names under our tag, before any re-create.
  • A limiter allows at most 200 requests per minute; ratelimit_remaining shows the API's count.

project_id(name) resolves project Proxy Index by its exact name; account() returns only the droplet limit and account status; sizes() lists the available sizes and their regions.

proxy-index campaign limits --account leftclick|proxy-index [--sizes …] is read-only and prints counts only: the droplet limit and account status, the number of droplets under each role tag, the number of droplets in project Proxy Index, the rate-limit remaining, and the regions (of the 8) that offer each size (default c-2, s-8vcpu-16gb, s-1vcpu-1gb). It never lists production droplets and prints no IP address and no token.

Launch

launch.launch_hour(spec, record, root, cloud=…, remote_factory=…, clock=…) brings one hour from planned to running under the hour's lock (ledger/HH/.lock); the launcher owns hour.json until then, and saves it after every step.

  1. Plan. One DropletRecord per network and region (name pic-<sid>-hNN-<region>-<network>, size, image, the spec's concurrency, and overlap: the network and region's workers of earlier hours that are still armed or running). Cells start pending; traffic gets each network's countries_total. Names are on disk before any create. A manifest whose settings.concurrency differs from the spec's is refused, so the recorded concurrency is the one the worker runs.
  2. Wait for the lead. A launch earlier than scheduled_at − create_lead_seconds (HH:58:30) waits; onboarding round itself waits for HH:00:00.
  3. Adopt first. Before any create, recorded names without an id (or whose id this process did not create) are resolved with adopt_uncertain(names, hour_tag); ids another record already holds are never taken. A crashed launch therefore never creates a name twice.
  4. Create per region (at most 10 names per call) with the tags pi-camp-worker, pi-camp-<sid>, pi-camp-<sid>-hNN, the spec's SSH key, and monitoring, agent and IPv6 off. Ids are saved right after the answer. An uncertain answer is adopted by name; names still missing are looked up once more (a create still in flight may be listed only now) and then retried once after 15 s, then create_failed.
  5. Assign every new id of the region through scope.assign_and_verify_project (one POST per region, 3 checks 5 s apart). An unconfirmed worker is never pushed; the guard removes it on the own-unassigned path and the hour gets a project_assign_failed alert. Its replacement runs alongside the region's confirmed workers, never before them.
  6. Ready. One GET /v2/droplets?tag_name=pi-camp-<sid>-hNN per 2 s, shared by every waiting worker, until the droplet is active with a public IPv4 (written only to .runtime/hosts-HH.json, 0600), then SSH; both within 180 s of the create.
  7. Push and arm. One tar on SSH stdin: the network's manifest, provider.toml (next to the manifest on the manager), assignment.json, the wheel whose SHA-256 the spec binds (from <base>/wheels/) and that network's credentials (from <base>/.secrets/credentials/<network>.toml), where <base> holds campaigns/<cid>. A push error is retried once on the same worker. After a failed push, and for a resumed worker, the worker is inspected first: a round unit in any state but inactive, or the fleet marker, means the round started, and the worker is armed, never pushed twice. start_failed is written only when the round provably never started: when the worker cannot be read after a failed push, it is armed with error_class start_unconfirmed and harvest decides. An error after arming never turns an armed worker into start_failed. A pull of a round directory that was never created returns it empty.

A boot, SSH, start or assignment failure removes the worker through scope.guarded_delete (a refusal is destroy_refused with a high alert and no fallback; an error is destroy_failed and retried by the next harvest pass) and gets one replacement, only before HH:00 + replace_until_minutes. The cell is failed_ours unless the replacement arms. An unexpected error fails only its own worker, no task outlives the launch, and every worker leaves it armed or in a final status: without a droplet create_failed, with one removed through the guard (which refuses an unassigned droplet it cannot prove ours); error_class keeps the cause. Synthetic specs make no cloud or SSH calls and arm every worker at once.

Worker start (fanout.START_SCRIPT, run by the worker's system Python with public arguments only): it writes the credentials to /run/proxy-index-worker/credentials.toml (0600, never under the worker root), extracts the rest with the data filter, installs the wheel with uv pip install --no-deps --offline only when its SHA-256 differs from the installed one, waits up to 10 s for NTPSynchronized, records both in worker-start.json in the round directory, writes active-run.json (the fleet marker), and starts systemd-run --unit=pi-camp-round (LimitNOFILE=65536, UMask=0077, Restart=no, RemainAfterExit=yes so the exit status stays readable; no run-time limit) and the sampler unit pi-camp-sampler.

SSH. fanout.OpenSSHRemote(identity, runtime, hour) runs ssh with BatchMode=yes, IdentitiesOnly=yes, User=root, a per-hour UserKnownHostsFile with accept-new, ConnectTimeout=5, ServerAliveInterval=10, ServerAliveCountMax=3 and ControlMaster=auto, ControlPersist=4h. The control socket is .runtime/cm-%C when that path fits the socket-path limit; under the manager's campaign root it does not, so sockets go to a private /tmp/pi-camp-cm-<uid>/; a directory owned by another user is refused. inspect runs fleet.REMOTE_INSPECT; stop sends SIGTERM to the round unit; pull streams the round directory only once its checkpoint is terminal or the round unit has ended (a killed round never writes a terminal checkpoint); while the unit runs, or when its state cannot be read, the pull is refused. It extracts it only when every entry lies under that directory, with no absolute path, .., link or device; journal keeps the last 5 MB of both units. Errors are fixed text with the exit code, never the host or its output. What a worker may send is capped: 16 MiB per command, 5 MB of journal, 8 GiB per pulled round, streamed to disk; past the cap the command is killed and fails.

Sampler (python -m proxy_index.campaign.sampler --interval 1 --output <round dir>/host-samples.jsonl): every second it appends total and per-core CPU busy, steal, load1, used memory and the RSS of the round unit's processes, and stops when the round unit has no process left. The file is pulled with the round; verify_round does not read it. sampler.summarize(path, since) ignores samples before the round's first start (the idle wait for HH:00) and gives the record's cpu_p50_pct, cpu_p95_pct, cpu_max_pct, cpu_core_max_pct, steal_p95_pct, load1_p95, mem_used_max_pct, cpu_peak_pct and rss_peak_mb.

Data and completeness

A cell is one network, region and hour: 24 per network and region, 3,072 for 16 networks in 8 regions. Its data is the round the harvest pulled into networks/<net>/residential/<mcid>/regions/<R>/rounds/<NN>/. Its status comes from that round and the droplet records in ledger/<HH>/hour.json (merge.cell_status, shared by merge and completeness):

  • a pulled, closed round is judged by its data; a round whose own status is failed is failed_ours;
  • a pulled round that is not closed is running while a worker of the cell is still requested, assigned, booting, starting, armed, running or finished; with no live worker it ended without closing (killed, out of memory, host lost) and is failed_ours, with its measured countries kept;
  • without a pulled round: no record is pending; a live worker is running; a collect_failed worker means the data waits on a kept worker (uncollected); failed_ours only when no worker ever started (create, assign, boot or start failed, or destroyed with no armed or start time); any other worker started a round whose data is not in the root (uncollected, "round ran; data not collected").
  • campaign merge --root R [--network N] (merge.merge_network) writes each spec region's state.json and summary.json: a closed onboarding checkpoint with all 24 rounds, the rounds' own jobs, and not_started_deadline jobs at the manifest's scheduled_at for a failed_ours cell. A round that ended without closing keeps its jobs, closed by the round executor's own rule (pending → not_started_deadline, running → failed). It checks every cell of every requested network first and writes nothing while any is pending, running or waiting on a kept worker (CampaignNotFinished), or when a started round is missing from the root (RoundDataMissing); the command prints the blocking cell and exits 3. validate_state and the unchanged onboarding export read the result.
  • campaign completeness --root R (completeness.build) checks every pulled, finished round with verify_round (chunk SHA-256, rows, time bounds, counters) and writes completeness/completeness.json (rows, issues, status counts per network and in total), per-hour-completeness.tsv and per-hour-tables.md (one table per network, regions × h00–h23). It only reads the data, exits 0 when every cell is complete and 3 otherwise. Cells: complete (every country completed and verified), partial (a country interrupted, failed, or a verification issue), failed_ours (verified too when a round was pulled), uncollected, running, pending; the issues name the reason ("round ended without closing", "data waits on a kept worker", "round ran; data not collected").
  • The TSV keeps DATA-1's columns (net region round scheduled started finished completed delay duration countries jobs_ok missing dup badchunk no_success requests errors observations) and adds cell size start_lateness_s create_to_ready_s overlap bytes_up bytes_down protocol. missing counts countries never run, badchunk countries with a data finding, the droplet columns come from the cell's last worker (create_to_ready_s = SSH ready − create request) and protocol is the network grammar's echo-test protocol.

Verified collect. campaign collect --inventory I --campaign-id CID --dest D (collect.collect) reads the manager's host, identity_file, optional user (root) and campaigns_root (/opt/proxy-index-campaign/campaigns) from the private local inventory, then:

  1. the manager writes, with its system python3 (3.11 or newer, a manager image requirement), ARCHIVE-MANIFEST.sha256 (SHA-256 of every regular file except .runtime/; a symbolic link aborts) and reports the total size;
  2. it checks local free space: at least 1.25 × the size, keeping 20% of the disk free;
  3. one tar stream without .runtime/ is extracted with the data filter (no absolute paths, .., outside links or devices) into D, which must be new or empty;
  4. every file is verified against the manifest and collect-report.json lists mismatches, missing and extra files. The command exits 0 only when all three are empty, 3 otherwise.

The host appears only in the SSH command line; no output of these commands holds an IP address.

Image and watch

Worker image

Build the inputs on the exact main head, then the image (about 30 minutes, once per framework version):

uv build --wheel --out-dir dist
uv export --frozen --no-dev --no-emit-project --format requirements-txt > dist/requirements.txt
proxy-index campaign image build --account leftclick --wheel dist/proxy_index-<version>-py3-none-any.whl --requirements dist/requirements.txt

image.build runs these steps; every id goes into the inventory .secrets/campaign-images.json (0600) before the next step:

  1. The Mac campaign key ~/.ssh/proxy-index-campaign (ed25519, created if absent, comment pi-camp-mac) is reused when its public part is already registered under a pi-camp- name, otherwise registered as pi-camp-mac-<yyyymmdd>.
  2. The builder pi-camp-builder-<yyyymmdd>-<hex4> (s-1vcpu-1gb, lon1, ubuntu-24-04-x64, tag pi-camp-builder, no monitoring, no droplet agent, no IPv6) is created and moved into project Proxy Index through scope.assign_and_verify_project (fail closed). After a lost create answer it is adopted by its exact name and tag.
  3. Over SSH (key only, a fresh known-hosts file), one tar on stdin carries assets/worker-provision.sh, the requirements and the wheel. The script installs python3.12-venv, the pinned uv 0.12.10 (download checked against its SHA-256), the venv with --require-hashes requirements and the wheel (its SHA-256 in wheel.sha256); masks snapd, apt-daily*, unattended-upgrades and motd-news; keeps systemd-timesyncd on; limits cloud-init to datasource_list: [ DigitalOcean ]; sets key-only sshd in sshd_config.d/01-pi-camp.conf (read before cloud-init's 50-cloud-init.conf); locks the root password; removes host keys, authorized keys and the build inputs; runs cloud-init clean --logs --machine-id; empties the login logs (auth.log, wtmp, btmp, lastlog, syslog). Its last line is a hygiene check (including the effective sshd -T settings and empty login logs) that must print clean; anything else stops the build before any snapshot.
  4. The builder is shut down, snapshotted as pi-camp-worker-<version>-<wheelsha12>-<yyyymmdd>, and the snapshot is transferred to the 7 other regions, one after another (each action is polled every 5 s, at most 2 h). The whole build can take more than an hour: run it as a background job.
  5. Whatever happened, the builder, and the Mac key if this build registered it, are removed through scope.guarded_delete (audit in .secrets/campaign-ops-audit.jsonl). A resource the guard did not remove is listed under leftovers and the command fails. After a lost create answer that found no builder, leftovers holds builder_unresolved: <name>: check the builder count with campaign limits before building again.
  6. The inventory entry ends built (with snapshot_id, snapshot_name and regions) or failed with the error. The snapshot is kept for the campaign and removed at teardown.

Firewalls and keys

ops_api.worker_firewall(manager_ipv4) admits TCP 22 only from the manager, attached by the tag pi-camp-worker; ops_api.manager_firewall(mac_ipv4, manager_id) admits TCP 22 only from the Mac's public IPv4, attached by droplet id. Both allow all outbound traffic. apply_firewall creates one, or replaces the recorded one. ensure_ssh_key registers a key once; release removes a recorded key, snapshot, droplet or droplet-free firewall through the guard. A firewall that names droplets (the manager's) needs a ledger that also records those droplet ids, which teardown passes to guarded_delete.

Mac watch agent

proxy-index campaign guard install --status-file <path> --traffic-dir <dir> [--inventory .secrets/campaign-manager.json] writes ~/Library/LaunchAgents/com.proxy-index.campaign-watch.plist from assets/launchd-watch.plist and loads it with launchctl bootstrap. It runs proxy-index campaign watch with those paths (absolute), logs to ~/Library/Logs/proxy-index-campaign/, and is restarted until it exits 0, which the watch does once the campaign is finished. guard status shows whether it is installed and loaded; guard remove unloads it and removes the plist. The agent is alert-only: it reads status and reports, and never removes or changes a cloud resource. It holds no token and no IP address.
