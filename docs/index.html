1. Run a test

From the standalone framework directory, install the locked dependencies. The MMDB stays in the local db-ip directory and is not included in wheels, source distributions or Git.

uv sync --locked --no-editable
uv run --no-editable atlas targets

# Supply a gateway privately through your environment:
# PROXY_URL accepts http://user:password@host:port or socks5://user:password@host:port.
# Percent-encode reserved characters in URL credentials.
uv run --no-editable atlas run \
  --target generic_http --requests 5000 --concurrency 100 \
  --provider example --product residential_rotating \
  --country US --location dubai --output results

Use generic_https for TLS tests. Both HTTP and SOCKS5 gateways support optional username/password authentication. SOCKS5 resolves the destination through the proxy. For static PROXY_URL runs, --country records requested geography; targeting flags must already be present in the supplied credentials.

Shifter Residential is implemented. Use --provider-config configs/shifter.toml --credentials-file .secrets/credentials.toml. The private file uses owner-only permissions and is excluded from Git, packages and remote uploads; copy credentials.toml.example to set up your own. Add optional overrides such as --param country=us. See the adapter guide, session policies and Python examples.

Set --url http://ip-info.com/myip (or another plain-IP echo endpoint) per test. For Generic HTTPS, use an HTTPS URL. Python callers pass RunConfig(target_url=...). IP Info is the default if omitted; the effective URL is recorded in each summary.

Defaults: 100 requests, concurrency 10, timeout 15 seconds, no rate cap. Optional --rate 50 paces request starts. There are no automatic retries, redirects, cookies or connection reuse. Response bodies are limited to 512 bytes, plus one byte to detect overflow.

A request succeeds only when the response is HTTP 200 and its complete trimmed body is one valid IPv4 or IPv6 address. HTTPS verifies the target certificate. Only Generic HTTP contributes IP observations and pool uniqueness metrics.

2. Call the runner from other code

import asyncio
import os
from atlas import JsonSink, ProxyConfig, RunConfig, run

async def measure():
    return await run(
        RunConfig(
            target="generic_http",
            proxy=ProxyConfig.from_url(os.environ["PROXY_URL"]),
            requests=5_000,
            concurrency=100,
            provider="example",
            product="residential_rotating",
        ),
        JsonSink("results"),
    )

summary = asyncio.run(measure())
print(summary.to_dict())

A future methodology layer chooses the target and configuration and invokes this function. It decides cadence, geography, budgets and which results to enrich/publish. Those policies do not live inside targets.

Pass an asyncio.Event as stop= for graceful interruption; it returns a partial summary with status="cancelled". Cancelling the caller task also saves partial results, then propagates cancellation. CLI SIGINT/SIGTERM does the former and exits 130. A normally completed measurement exits 0 even when proxies fail; configuration, storage or framework failures exit 2.

3. Result contract

Each invocation creates a unique run directory. summary.json is written last and serves as the completion marker. Interrupted or failed runs are explicitly marked; a directory without a summary is incomplete. An uploaded run archive (node results and browser bundles) is bounded before anything is held in memory (SEC-UPLOAD-1): a member's metadata header (pax or GNU long name) over 64 KiB, more than 8 such headers in a row, or a sparse member is refused before tarfile reads it, summary.json over 64 MiB (about ten times the largest real one) is refused before it is extracted, and reading an IP, geo or enrichment artifact stops with an error at the first row past the count its summary or report declares, or at a line over 1 MiB. On the manager, an upload whose summary declares more IP or geo rows than the setting results.max_artifact_rows (default 5,000,000), or a count that is not a non-negative integer, is refused with 400 and a failed run before any artifact is read (SEC-FOLLOWUP-3).

summary.json

Schema/framework/target versions; sanitized configuration; UTC start/end; requested, started, completed, cancelled and not-started counts; successes, errors by category, HTTP statuses, body bytes, throughput, latency percentiles (latency_ms: p50, p90, p95, p99), mean success latency (latency_mean_ms, from the 1 ms histogram bins, to 0.1 ms; null with no successes; absent from summaries written before it existed, which readers treat as unknown) and exact HTTP unique IPs. Includes five-minute counters/histograms and the IP file checksum/row count. A campaign country test (daily tests included) also keeps slices (DAILY-DIAG-1, atlas/slices.py): its tries, successes and error classes per 5 seconds of the run, so a dip inside a run of a few minutes shows when it happened. seconds is the slice width; tries, successes and each class under errors are arrays of one length, slice i starting i × seconds after started_at. A class is the error code (timeout, proxy_connect, dns, connection, ...), except a target status error, which is http_429, http_4xx or http_5xx; a class appears only when it occurred. A run longer than 120 slices doubles the width until it fits (10 s up to 20 minutes), so the field stays a few KB and its counts exact. Summaries written before it existed, and other runs, lack it.

ips.jsonl.gz

One row per run × five-minute UTC bucket × normalized IP. Each row contains schema_version, run_id, bucket_start, ip, count, first_seen and last_seen. HTTPS produces an empty IP file and null unique_ips.

Definitions that downstream consumers must preserve

  • requested = started + not_started; started = completed + cancelled; completed = successes + total_errors. On a framework failure, “cancelled” includes requests aborted by that failure.
  • Latency is measured with a monotonic clock from request execution through complete body receipt, including connection setup and TLS, excluding runner queue/rate waits. Percentiles include successes only; absent samples produce nulls.
  • The sparse ceil_ms_v1 histogram stores [upper_bound_ms, count] bins with 1 ms resolution. Percentiles use nearest-rank selection and round upward by less than 1 ms. Merge bin counts before calculating combined percentiles.
  • Throughput is completed requests divided by elapsed run time. response_body_bytes counts bytes read from bodies, including failed responses; it is not provider-billed traffic or total TCP/TLS bytes.
  • Byte accounting (BYTES-TRUTH-1): bytes_up and bytes_down are what crossed the link to the gateway, which is what a network bills, on every try, failed ones included. With a response they come from the gateway socket's kernel counters (TCP_INFO, exact on Linux; the CONNECT exchange or SOCKS5 negotiation and TLS included) or, elsewhere, a sized estimate. A try that fails before any response (connect timeout, a 407 or other CONNECT refusal, a TLS error, a read timeout before the headers) reads the gateway socket the connector made, kept when it closes: exact on Linux. Without a kernel count (macOS, or a SOCKS5 negotiation that failed before its tunnel) only what surely crossed is estimated: the CONNECT request (60 bytes) once the TCP connection was made, its response (39 bytes) once the proxy answered, never a TLS handshake; a connection that was never made counts 0. A browser try counts at its local relay (browser guide, Runner), exact, a time-out or crash included. The bill divides all of these by successes.
  • Observations belong to the bucket in which the response completes. UTC is anchored to the monotonic run clock so clock corrections do not reopen flushed buckets.
  • Deduplicate IPs across buckets/runs when computing window or fleet uniques. Adding per-run unique counts would overcount recurring addresses.
  • Error categories: proxy authentication, proxy connection, DNS, TLS, timeout, HTTP status, invalid body, oversized body, connection and protocol. Returned error data never includes raw exception messages or credentials.
  • Every failed request has one verdict, counted in challenges, blocks, timeouts or proxy_errors (or a plain error). A block is the target refusing us: HTTP 403, 429, 451 or a block page. Proxy-side failures are never blocks: 407, 502, 509, and 503/504 without a challenge or block page, a failed CONNECT, a reset or dropped connection and a gateway name that does not resolve are proxy_errors; no answer in time is a timeout. Other target statuses (404, 500, …), TLS failures and unusable bodies are plain errors. Block rate is published next to success and stays inside reliability; it is not a separate score component.

Memory scales with distinct IPs, the current bucket, a bounded export backlog and small aggregate histograms. A fixed pool bounds active requests. Bucket serialization runs on one background writer; slow storage delays new requests instead of blocking the event loop during existing requests. No list of all request objects is retained.

5. Add or change a target

Targets expose an ID, version, engine, pool eligibility, build_request() and assess(status, body). Register a new implementation in a TargetRegistry and pass it as run(config, sink, RunOptions(targets=registry)); every optional input of run is a RunOptions field. Adding a built-in also registers it in the default registry; the CLI automatically lists it. Change the target version whenever measurement semantics change.

from atlas import RunOptions
from atlas.targets import EchoIpTarget, TargetRegistry

targets = TargetRegistry()
targets.register(EchoIpTarget("my_ip_target", "https://example.test/ip"))
# await run(config_for_my_ip_target, sink, RunOptions(targets=targets))

Transport.execute(target, *, context=None) returns a normalized outcome. Since v0.2 the runner supplies a RequestContext with run, request and worker identities for provider sessions; custom transports must accept this keyword. A future browser adapter can implement the same execution protocol through transport_factory; browser targets can carry additional settings in their own implementation. Playwright is not needed or installed for baseline targets. Custom sinks implement start, observations, finish and abort. Observation writes are serialized on one background thread; finish runs only after they complete.

Database persistence is explicit: include --database-file for automatic CLI imports. Without it, runs continue to save files only. Python code can call atlas.storage.ingest(run_directory, credentials_file) after run(), or atlas.storage.ingest_many(run_directories, credentials_file, batch_ids=None, ip_rows=True, counters=False) for a batch (INGEST-RTT-1): every directory is read and checked first, so the transaction does no file I/O; then all the runs are stored in one transaction, in three round trips to the database whatever their number (the ingest lock, held shared, with the reads under it; every statement of the batch; the scope totals with the commit). With conn= the batch goes over an open connection. Batches run side by side (INGEST-PARALLEL-1): a batch writes its runs' own rows without a global lock, every multi-row insert into a shared table in key order; each batch first takes its networks' locks, so batches of one network go one after the other and batches of different networks never wait for each other (each network's counts, the IPs new to its pools, provider and scopes, product_ips and the scope totals, see every earlier batch of it); only the last statement before the commit, the provider_overlap increments, takes the global overlap lock (817452905); two imports of one run wait for each other (a lock per run id); a purge, seed, migration or rebuild takes the ingest lock exclusively and waits for them. atlas.storage_parallel.store(groups, credentials_file, connections=25, processes=P) stores an hour's batches (each an ingest_many then a compute.estimate_runs) over that many connections at once, spread over P worker processes (INGEST-PROCESSES-1, spawned; default min(7, CPUs − 1, connections), so preparing the rows uses P cores), as daily ingest --connections --processes does: a deadlock or serialization failure rolls back and retries only its batch (3 times, with backoff), a batch that still fails, or whose worker process died, is reported with its run ids, the connections are capped so that a quarter of max_connections (at least 20 slots) stays free, and the batches in flight over all processes fit a memory budget (4 GB; a batch is never split, it waits instead); the N and P used are printed. A storage_parallel.Pool stays open over several stores. One connection is the serial path, statement for statement. Their rows go in multi-row INSERT ... VALUES of as many rows as a statement's 65,535 parameters allow into session temporary tables, followed by set-based inserts, upserts and checks, all sent in pipeline mode; no statement runs per row, IP or run. The stored rows are those of importing the runs one at a time in that order, and a run already stored is skipped as on a replay. A database error or a failed check rolls the whole batch back and raises IngestBatchError naming its run ids, to retry one at a time; ingest is the batch of one and raises the run's own error. Rules/schedulers can therefore control when to ingest and enrich. If PostgreSQL is unavailable, the durable JSON artifacts remain available for retrying ingest.

Import transaction: validate counters/checksums → COPY observations into staging → insert run/history → import optional MMDB releases → update cached metrics → commit. Imports hold a database advisory lock shared and serialize only their cross-network step under a second one; measurement requests run independently. Invalid data rolls the entire import back. Raw-data archive (ARCHIVE-1): raw measurement rows are meant to stay 30 days in the database (partitions.RAW_DAYS); the calculator reads no further back, so the 30-day window's previous_period has no rows and its success_delta is null (the 24-hour and 7-day comparisons are unchanged). atlas archive export --date YYYY-MM-DD --database-file … --out DIR writes one UTC day into DIR/YYYY-MM-DD.tar.gz and deletes nothing. A batch belongs to the UTC day of its scheduled_for, a run to its batch's day (a daily test, which has no batch, to the day it started), and every row tied to a run or batch goes with it: the batches, batch runs, runs, buckets, geography buckets, IP observations, run enrichments, estimated hours and run roles of the day, the day's tape events, and the dimension rows they reference (providers, products, regions, countries, targets, nodes without their token hash, IPs, enrichment, places, networks, DB-IP releases, pools and scopes), so a file loads on its own. The file is a gzip tar: manifest.json first (format and version, day, storage and calculated schema versions, and per table its role, columns, rows, bytes and sha256), then one CSV per table in load order, each from COPY … TO STDOUT (FORMAT csv, HEADER) ordered by primary key, all from one snapshot in UTC/ISO settings; the same rows give the same bytes, so the file can be re-checked and re-imported with plain tar and COPY. atlas archive restore --file … --database-file … loads a file into a database of the same storage schema version in one transaction: every CSV's sha256 and row count must match the manifest, ids are kept, rows already present stay as they are (a repeated restore inserts nothing), and it refuses (exit 2, nothing changed) when the database's ids mean other rows (the same product id, IP id, run id or batch slot holding other values): restore into the database the file came from, or into an empty one. Links to batches outside the file (a retried census, a tape event of another day's batch) become NULL; missing partitions are created and identity sequences move past the restored ids.

Daily archive job. The orchestrator's archive job (00:40 UTC, off until the setting archive.enabled is true; archive.spaces_file, default .secrets/spaces.toml, and archive.work_dir, default .state/archive) takes the oldest day that still holds rows, at most 3 per run, and stops at the first that is not due. A day is due once none of its batches or batch runs is open and its last run end, batch end and estimated-hour end are at least 30 days old; with daily tests (whose 24 estimated hours reach into the next day) a day is archived about 32 days after it, so no calculator window loses a row. For each due day it exports the file, uploads it private to raw/YYYY/YYYY-MM-DD.tar.gz (signed payload sha256 and Content-MD5; the file's sha256 and the sha256 of its fact entries stored as object metadata), checks that the object has the file's size, MD5 and sha256, and only then deletes the day's rows in one transaction under the ingest lock: links from rows that stay (tape events, outages, a later retry) to the day's batches are set NULL, a daily partition holding only the day's rows is dropped whole, other rows are deleted by run, and every deleted count must equal the file's, else nothing is deleted. Objects are never overwritten or deleted: a rerun after a crash finds the object, and deletes the rows when its facts are the same; different facts leave the day alone and fail the job (archive_changed). Failures show in the job health and raise job_failed:archive. The job also fails (archive stalled) while the oldest day still holding rows is more than 33 days old (30 plus 3), whatever holds it: a batch left open, an unreachable bucket or database, or archive_changed. While archive.enabled is on, the daily retention job no longer deletes estimated hours: they go only with their run, after its day file is verified. Recovering from archive_changed (the bucket holds a file for the day whose facts differ from the database's, for example after a count mismatch stopped a purge): download it with archive restore --date D into an empty database and compare its fact tables with the source; once the difference is understood, keep the object (it stays, versioned) and delete or rename it deliberately with the owner's Spaces access, then let the next run export the day again. Every later day waits behind it, so the stall alert names it. Raw files of each update (owner decisions 2026-11-03 and 2026-11-14, ARCHIVE-RAW-1). Raw means as received, before any DB-IP enrichment. With the setting raw.spool_dir, the orchestrator API files every upload it has ingested, exactly as the node sent it, under <spool>/YYYY/MM/DD/HH/<network>/<kind>-b<batch>-<run id>.tar.gz by the UTC hour (network = the node's provider), and daily ingest --spool DIR files each converted daily-test run directory as daily-<run id>.tar.gz in its provider's folder right after conversion, before enrichment (enrichment files a rerun finds are left out; files 0600; a replay in the same hour keeps the first copy). The files stay byte for byte as received, which a rebuild needs (each run's summary.json holds the sha256 of its ips.jsonl.gz); since they are gzip already, zstd saves under 1% on them (scripts/archive/raw_zstd_bench.py: decompressing every file first would save about 24% but cost about 40 s per network-hour and lose the exact bytes). The upload (ARCHIVE-UPLOAD-ROBUST-1). A file over 64 MiB goes as a multipart upload: parts of 16 MiB (more when the file would need over 10,000 parts, Spaces' limit), 4 at a time, each with its own signed sha256 and Content-MD5; a smaller file is one PUT (Spaces takes at most 5 GiB in one). Every request times out after 60 s without a byte and every PUT body after 5 minutes, so a hung upload cannot block later hours. A request that fails on the way (a reset, a timeout, a 5xx, 429, RequestTimeout or SlowDown) is sent again up to 4 times in all, after 2, 8 and 30 s: only that part, never the whole file; a part still failing aborts the upload (no parts are left in the bucket). The orchestrator's journal logs each file's key, size, parts and seconds (Spaces PUT …: N bytes in P part(s), S s). A network-hour that still fails does not stop the others: the run goes on, and the next run (5 minutes later) tries it again. The run then fails with UploadFailed, which raises one job_failed alert per failure kind and hour (dedupe key job_failed:raw_upload:<kinds>:<hour>; a repeat in the same hour only counts as another occurrence), and a run still going after 30 minutes raises job_stuck (major, one per run) at the next skipped fire. It checks the object's size, ETag (the MD5, or for an object in parts the MD5 of its parts' MD5s with -<parts>) and sha256 in the bucket and records it in the network folder's uploaded.json; a file that arrives after its network-hour was uploaded goes into a further part (<network>.1.tar.zst). Objects are never overwritten or deleted and have no expiry. It then removes each local hour older than 30 days whose files are all uploaded; an hour with a file that is not uploaded is never removed, and an object in the bucket that differs fails the job (archive_changed). atlas archive raw --spaces-file F --hour YYYY-MM-DDTHH lists an hour's objects; with --network N --out DIR it downloads that network-hour's parts, checks each object's sha256 and each file against its manifest, and writes the files into the spool layout under DIR. atlas archive rebuild --spool DIR --from D --to D --database-file F [--mmdb DBIP] imports the spooled runs of those days, oldest first (with --mmdb, daily runs are enriched first, as daily ingest does: one already enriched keeps its enrichment, and one enrichment refuses is skipped and listed as not_enriched); replays are no-ops, and a run whose batch is not in the target is imported without its batch link (listed as unlinked). Estimated hours are not part of a rebuild (daily ingest --formulas recomputes them).

Atlas Score backfill. atlas calculate-backfill-scores recomputes the points the current build's Atlas Score trends lack under its methodology: of the 23 hours before its cutoff (--hours) and the 29 UTC days before its day (--days, each day at its last hour on the builds' grid), oldest first, those after the first stored test. Each point is the incremental calculation at that cutoff in a transaction that is rolled back once its networks are scored, so no build, list or memo of it stays; only its scores are written, as source = 'backfill', one point a transaction. It is resumable (a stopped run keeps its points, the next goes on) and idempotent (points already recorded under the methodology are skipped). A point holds the calculation's lock: it starts only while no build runs (else the command exits 3) and the next hourly build waits for it. A point costs about a recount at its cutoff (about 20-60 minutes at 1-3 days of production data, like an hourly build's memory; each point runs in a process of its own, so a run of several needs one point's memory), so run it off-peak, right after an hourly build, under a memory cap, and bound a run with --limit. --list prints the missing points only; --dry-run computes them and records nothing. Production computes no point: they are computed on a copy of its database on another server (the staging copy; never on the production host), then --export PATH writes that copy's recomputed records (about 54 rows a point) to a JSON file and --import PATH records them in production. The import takes the calculation's lock for a moment only (exit 3 while a build or recount holds it), writes only backfill rows, again without change, and refuses records of another methodology than the current build's. Run it between hourly builds, never during the HH:06 build or a recount.

A cutoff inside a five-minute bucket moves to that bucket's end when the bucket holds data and every run with data in it had finished by the requested time (always so for a calculation without --as-of: a run is stored only once it has finished), so a run that ended just before the calculation is in it; otherwise it moves to the bucket's start. A bucket is in a snapshot whole or not at all. Such a cutoff can be up to 5 minutes past the clock, so an open outage's duration and downtime can run up to 5 minutes ahead of it, and score and evidence expiry can take effect up to 5 minutes early. Latency bins are merged before nearest-rank percentiles at 1 ms ceiling precision. Window coverage (readiness) is the fraction of five-minute slots with requests, or of pulse slots for census/pulse cohorts, not measured uptime: pulse slots are the product's done pulse runs, filled by one with at least one request, also when every request failed (the provider was down: it lowers success and uptime and opens an outage, it is never a gap). A run is only ever failed by our side (no node, never started, went silent, node shut down or erred, upload rejected), so failed runs and operator-skipped or killed batches are not slots and never count against the provider. Charts have one point per UTC hour for 24h and one per UTC day for 7d and 30d, the newest partial (SERIES-HOURLY-DAILY-1). Every request counts for every metric: census, pulse and load runs alike feed success, blocks, timeouts, exit IPs, breakdowns and bytes, and minimum_requests counts every request of a required target; run roles are display labels only. New-IP counts use lifetime product first-seen timestamps; recurrence counts IPs seen on multiple UTC dates. DB-IP enrichment uses one identified release, with unknown values preserved.

DB-IP release per run (RELEASE-PER-RUN-1): the one identified release is chosen per run. Each observation is labelled from the newest release its run was enriched with (run_enrichments), so the daily DB-IP update, which replaces db-ip/dbip-full.mmdb under the same name, changes only the runs enriched after it, and every older run keeps the countries, regions, cities and networks it was saved with. A release is its file's sha256 (dbip_releases.sha256), never its file name: a replaced file with new content is a new release. Runs without enrichment stay unlabelled. Pulse runs are enriched on the manager with its current release at upload (PULSE-ENRICH-1); their exit IPs have no observation rows, only the lifetime counters (product_ips, PULSE-COUNTERS-1), with the run's release in run_enrichments. Those stored before it are counted from their raw files by atlas daily pulse-backfill (the deploy guide). An IP returned by runs with different releases takes the labels of its lowest run_key in the window. The snapshot's dbip_releases lists the ids of every release its observations were labelled with, ascending; dbip_release names the newest of them, or is null when the build used none.

Time-weighted metrics and latency under load

A window is split into time slots: the cohort's pulse interval (the shortest pulse_interval_minutes of the pulse-enabled targets) made a whole multiple of the 5-minute stored bucket, lcm(interval, 5): 30 minutes in production, 10 in staging (2-minute pulses), so no census request lands in a slot it did not run in. Pulse and load requests belong to their batch's slot, census and unbatched requests to the slot they ran in. Every slot with observed requests weighs the same: success_rate is the mean of the slot success rates, successes ÷ requests observed in the slot (nothing is counted for requests nobody observed); request_success_rate keeps successes ÷ requests. The slot cut by the window start does not vote (WINDOW-EDGE-SLOT-1): a window starts at its cutoff minus its length, usually inside a slot, and that slot holds only what was observed from the window start on (once the last 17 requests of a pulse, all failed, which voted 0 with the weight of a full hour of about 81,000 requests). Only slots that start at or after the window start vote on success_rate (also in previous_period, census_overlap, every target, a network's days and the fleet totals); the cut slot's requests still count in completed, request_success_rate and every other request figure, and time_slots.cut_at_start (0 or 1) says whether one was left out. The newest slot, cut by the cutoff, keeps voting: its pulses run at its start. Latency is measured on one target only, latency_target (default generic_http, the census target): light-load and under-load latency, the speed score, breakdown latency and the load factor all come from it. Other targets count for success, blocks, timeouts, IPs, authenticity, DC ASNs, bytes and uptime; their targets.<id>.metrics.latency_ms and latency_under_load_ms hold nulls, with latency_reason. Light-load latency (latency_ms, pulses only) merges the slots' latency histograms after normalising each to weight 1 and reads p50/p90/p99 from the merged distribution; a slot with fewer than [slots] min_latency_successes (30) successes does not vote. Percentiles are never averaged. Breakdown latency is light-load latency. The speed score reads the light-load p50 (speed_latency = "light_load", the owner's decision of 2026-11-16, SPEED-PULSE-1): the pulses are the same small test for every network every slot. The light-load latency is also the headline latency everywhere (HEADLINE-PULSE-1). Under-load latency (latency_under_load_ms, the daily tests, census and load runs) is display only; no score, rank or headline reads it, and a daily test's latency never enters a breakdown row. A network without a slot of min_latency_successes pulse successes outside a census has no speed and no score.

Census overlap. A pulse or load run of a product that ran while a census of the same product was running (any country: account and node are shared) is marked during_census, derived at calculation time from the stored run start and finish times (the ingested run's, else the orchestrator's). It still fills its slot and counts for uptime, outages, down slots and every request metric, but it is left out of light-load latency (breakdowns included), of the time-slot success (a slot votes with its other requests; one left with only such pulses votes 0 if every request in it failed and does not vote otherwise, time_slots.skipped_during_census), and of the load factor (it needs a clean load run and a clean reference pulse, otherwise the newest earlier factor carries forward, latency.regions[].factors.excluded_during_census). Each window publishes census_overlap: pulses and targets.<id> with clean and during_census (runs, requests, successes, request_success_rate, success_rate, latency_ms), load, census_batches and basis; metrics.latency_reason says why light-load latency is missing.

In every pulse slot of the census target each product also runs one wave of census_concurrency requests (1,000 in production, 100 in staging) at census concurrency in every runner region's reference country: a test_batches row of kind load with the pulse's scheduled_for, started load.delay_seconds (60) after the pulses so the reference pulse is not measured under its own load wave. Like every scheduled test it sends only the country parameter. The orchestrator picks each region's reference once per UTC day, with the day's first pulse plan, and stores it in load_references: the fastest enabled country tested from the region over the trailing load.reference_days (7), by the light-load p50 of its census-target pulses that did not run during a census (every product weighing the same; at least load.reference_min_successes, 300, successes; ties by country code; basis fastest); an operator override (load.reference_overrides, override); without enough history the region's default (load.reference_defaults: nyc3 US, fra1 DE, lon1 GB, ams3 NL, tor1 CA, sgp1 SG, blr1 IN, syd1 AU; staging fra1 RO; default); else its first enabled country (first_enabled). load.enabled switches the wave off. Per percentile, factor(R, t) = load latency ÷ pulse latency of region R's reference country in slot t, and every country's latency under load is its pulse latency(C, t) × factor(region of C, t). A slot without a usable load run (both runs need min_latency_successes successes) takes the region's newest earlier factor in the window; without one that country's slot has no under-load value, and a window without any has null with under_load.reason. The window value is the mean over slots and countries. Census latency never makes a factor. Load runs count for every request metric, not for light-load latency, slot coverage or uptime.

Network headline latency over a country basket (LATENCY-BASKET-1, the owner's decision of 2026-11-19). A network window's headline latency (targets.<latency_target>.metrics.latency_ms: p50, p90, p95, p99 and the mean; the site's latencyP50/P90/P99), the Speed component that reads its p50, and each series point's latency (the latency charts and sparks) use the methodology's [latency] basket: 38 fixed demand countries (CN US IN JP DE BR ID GB RU FR MX IT PK CA KR TR ES AU BD VN NG EG IR PH SA TH NL PL AR ZA CO TW CH MY IQ DZ BE PE; the largest countries of a neutral demand proxy, 50% share of world GDP and 50% share of world internet users, World Bank 2024, Taiwan IMF, 86.5% of it), each weighing the same. Per basket country the network's latency is that of its pulses there alone, by the slot rule above (each slot with min_latency_successes successes in that country weighs the same). A basket country the network has no such latency in (it does not serve it, or too few successes in the window) counts as the slowest network's of the same kind and window there, each percentile its own slowest (penalty = "slowest_network"). The network figure is the plain mean (aggregate = "mean") of the basket values, the percentiles in whole milliseconds, the mean to 0.1 ms; a basket country no network of the kind has a latency in is left out for every network, and a network (or series point) with no basket country of its own has no latency, so no Speed. Each such target publishes metrics.latency_basket: size (38), covered (the basket countries of its own), counted (those with a value of some network), unserved and unmeasured (country lists), aggregate, penalty, countries (the p50 used per counted country) and pooled_ms, the latency of every country pooled that it replaced. Example: a basket of US, DE and JP; network A has 100, 200 and 300 ms, B 400 and 600 ms and no JP, C 300 and 900 ms (JP) and no DE: A is (100 + 200 + 300) / 3 = 200 ms, B (400 + 600 + 900) / 3 = 633 ms with JP at C's 900, C (300 + 600 + 900) / 3 = 600 ms with DE at B's 600. Product group windows keep the pooled latency (only network windows are served), and the latency under load, the other targets' latency, the per-place (breakdown and country) latency and the latency change keep their own rules: the latency change (latency_day_delta, the site's latencyDeltaPct) compares the pooled pulse latency, not the basket, so it is the network's own change, with no penalty, both periods by the same rule. Without [latency] the headline is the pooled latency of every country the network is tested in (HEADLINE-PULSE-1).

Worked example: fra1's reference country is RO. In the 18:00 slot the RO pulse (100 requests) has a p50 of 600 ms and the RO load wave (1,000 at once) 900 ms, a factor of 1.5. The Bulgarian pulse in that slot (BG is tested from fra1) has a p50 of 800 ms, so Bulgaria's latency under load at 18:00 is 800 × 1.5 = 1,200 ms. nyc3 has its own reference and factor for the US, Mexico and the rest of its countries. If fra1's 18:30 load wave fails, 18:30 uses fra1's 1.5 of 18:00.

Snapshot fields per window: metrics.success_rate (time-weighted), metrics.request_success_rate, metrics.latency_ms (light load), metrics.latency_under_load_ms, metrics.latency_reason, metrics.under_load (slots, own_factor, carried_factor, without_factor, reason), metrics.time_slots, the same per target (latency fields null except on the latency target), census_overlap, and latency: target, regions (per runner region region, reference (country, target, concurrency of its newest load wave), chosen (the day's choices in the window: day, country, basis, p50_ms, successes, candidates) and factors (slots, excluded_during_census, mean and latest per percentile)) and countries (per requested country its region, light-load and under-load latency). benchmark is a copy of metrics for older readers.

Browser targets

Browser runs (test batches of kind browser; browser pulse contracts) are measured per target only and never enter a network-level figure: a network's window metrics, census overlap, series, uptime (their batch runs are not in its denominator), coverage, scores, fleet totals and breakdowns are exactly what they would be without any browser run (calculated/browser.py; a bucket is a browser bucket when its run's batch kind or its target's engine is browser). Browser runs never move the calculation cutoff either: a five-minute bucket that holds only browser data waits for a later calculation. Each browser target measured in a window gets the same per-target entry as a network target (time-weighted metrics over one engine's rows, the engine below, coverage as the share of 5-minute buckets, its own target score; no latency, which is the latency target's), plus browser. A group target of the methodology's [target_groups] (social_web = ["instagram_web", "x_web"], "Social media web app", and ai_answers = ["ai_overview", "ai_chatgpt", "ai_gemini"]) is measured over the union of its sources' requests and is never scheduled itself; each source keeps its own entry. No browser, group or source target may be a required target (the methodology refuses one). A window without browser runs has no browser entries. Fields of targets.<id>.browser (K-BP6):

  • outcome_rates: ok, challenge, block, login_wall, timeout, proxy_error, no_content, no_answer and other_error, each a fraction of the completed tries (they sum to 1; all null when none completed). ok counts successes; challenge, block, timeout and proxy_error the typed bucket counters; login_wall, no_content and no_answer the error codes of the error verdict; other_error every other failed try (browser_error, tls, ...).
  • page_load_ms: p50, p90, p95 and p99 of the successful tries' page-load times (the buckets' histograms hold successes only).
  • group: the group target this target is a source of, or null.
  • sources: on a group target its sources in the methodology's order, else null.
  • engine: the browser engine (K-BP3, camoufox or chrome) whose rows make the target's figures in this window: outcome_rates, page_load_ms and the target's metrics. It is the engine with the most completed tries in the window, ties going to camoufox. A row's engine is its run's browser_engine (scope config); a run without one, as every run before the engine choice, is Camoufox, so a window of Camoufox runs only has exactly the figures it had before.
  • engines: an object by engine name with, for each engine with rows in the window, its own completed and successes (tries), outcome_rates and page_load_ms. Engines are never added together; a group target's are split the same way, each engine over its sources' rows of that engine. Each engine also has scores (below).
  • scores: the scores of the main engine (engine).

Browser target scores (TARGET-SCORES-1, calculated/target_scores.py). Once every product window is built, the calculator ranks, per window label, browser target and engine, every product group with browser figures of that engine (never Chrome with Camoufox) on three outcome rates: success (ok, higher is better), challenge and block (the hard block; lower is better). Among the M ranked networks, rank r (1 the best; ties share the average of their ranks, so a rank may be fractional) scores 1 + 9 × (M − r) / (M − 1): 10 for the best, 1 for the last. A network is ranked only with at least the methodology's browser_min_requests = 100 completed tries of the engine in the window (else not_enough_data; SCORE-BROWSER-MIN-1 below); with fewer than MIN_RANKED = 3 such networks each gets too_few_networks; and when the best and worst ranked rates are less than the larger of TIGHT_RACE_MIN_PTS = 3 points and TIGHT_RACE_Z = 1.96 standard errors of their difference apart (√(p₁(1−p₁)/n₁ + p₂(1−p₂)/n₂); of tied extremes, the one with the most tries) each gets all_similar: about 3 points at 2,400 tries, 14 at 100. Each of browser.engines.<engine>.scores and browser.scores is {"success": S, "challenge": S, "block": S}, S = {"rate", "score", "rank", "ranked_of", "status"}: rate the outcome rate (null without completed tries), status ranked, not_enough_data, too_few_networks or all_similar, and score, rank and ranked_of (M) null unless ranked. Example: success rates 0.90, 0.80, 0.80 and 0.50 at 500 tries each rank 1, 2.5, 2.5 and 4 and score 10, 5.5, 5.5 and 1.

A window with browser targets also has browser_overall.<engine> = {"success": {"score", "rank", "ranked_of", "status"}, "targets": [ids used], "weights": {id: difficulty}}: the network's ranked success scores weighted by each target's difficulty, Σ(score × difficulty) ÷ Σ difficulty, over the page targets and each group target (never a group's sources, so Instagram and X count once as social_web and the AI answers once); a target that is not ranked for the network is left out. rank (ties averaged) and ranked_of are among the networks with an overall for that engine in the window label; with no ranked target the status is no_ranked_targets and the score, rank and ranked_of are null. There is no browser overall for challenge or block (the all-targets challenge_overall: CHALLENGE-OVERALL-1 below). Difficulty, 1 (easy) to 5 (hard), is the methodology's [browser_difficulty]: every run target needs an integer from 1 to 5, and a group without one takes its hardest source's (ai_answers: 4). Every other field keeps its value: with Camoufox the only engine, a build is byte-identical apart from these fields. The new module and table change the implementation and methodology ids once, so the next build rewrites the lists once.

Success scores across all targets (SUCCESS-SCORE-CALC-1, display only). Each HTTP target with metrics, generic_http and generic_https (HTTP_TARGETS), gains targets.<id>.scores.success = {"rate", "score", "rank", "ranked_of", "status"}, the browser rule on metrics.success_rate (the API's successRate) over metrics.completed tries: the same minimums, tight-race bound, statuses and per-kind ranking, success only. No Index Score, component, breakdown, Speed, rank, browser_overall or browser score changes; browser_overall stays as it is.

Success scores by day (DAY-SCORE-1, display only). Each network summary has days = [{"start", "success_overall"}]: the 30 slices of its 30d window a day apart from its start, as its series points, so the last is the 24h window's span. A day's targets are measured as a 24h window's over that day's rows (an HTTP target on its requests, a browser target on its run) and scored as the windows are, the networks of one kind ranked per day with the same minimums and statuses (target_scores.score_days()). success_overall is the window's shape without weights (the fixed difficulties): {"score", "rank", "ranked_of", "status", "targets": {id: score}}, null on a day with no target. The challenge score across all targets (CHALLENGE-OVERALL-1, display only). Each window with a scored target also has challenge_overall, success_overall's shape and its former all-targets rule on the challenge scores: Σ(score × weight) ÷ Σ weight over the network's ranked scores.challenge (an HTTP target's, from metrics.challenge_rate; a browser target's main engine's, browser.scores.challenge), the same targets, groups and weights, ranked among the networks of its kind as success_overall is, with the same no_ranked_targets status. Whole browser runs (BROWSER-WHOLE-RUN-1, the owner's report of 2026-11-16, #1266; calculated/browser.py). A browser run is one batch of 100 tries. With the top-level methodology setting browser_window_rule = "whole_run" it counts whole, by its finish time, in the window (24h, 7d, 30d, a day) that holds its end: all its tries, outcomes and page loads, or none, for every browser target and group. A run that finishes after the window's end is out of it; a run that started before the build's 30 days of raw rows is in no window, because its first tries are no longer read. A browser target's time slots are not cut at the window start, so the run's first slot votes too. The browser minimum below counts these whole runs, so one complete run of 100 tries always scores. The value bill's 7-day browser window ([value] browser_window) keeps its length and holds whole runs too. Pulse and daily-test windows are unchanged. Why: the 24h window starts 5 minutes after the hour of the build, so a run from 14:49 to 15:34 showed only the tries after the start (44 to 76 of 100 on 2026-11-16), did not score, and left the window at the next build. Without the setting ("bucket") a window holds the tries whose 5-minute bucket starts in it. A change of the setting changes the methodology id.

The browser minimum (SCORE-BROWSER-MIN-1, the owner's decision of 2026-11-15, #1134; BROWSER-MIN-100-1, the owner's decision of 2026-11-16, #1232). A browser target counts for a network only with browser_min_requests (a top-level methodology setting, 100: one run; it was 500, about five runs, until every network turned out to have only 100 to 300 tries per browser target in 7 days, so no browser target was scored) completed tries of its engine in the window, each window (24h, 7d, 30d, a day) on its own tries; the HTTP targets keep MIN_REQUESTS = 100, and a methodology without the setting uses 100 for both. Under it the network's success, challenge and block scores of that target are not_enough_data (score, rank and ranked_of null, the rate kept), so the target is left out of its browser_overall and challenge_overall (and success_overall and days until SUCCESS-DAILY-DISTANCE-1, below, which reads no browser target) (their targets and weights list only the targets that count; the mean is over their weights) and is no peer in the target's ranking: it is not one of the MIN_RANKED networks and moves no other network's rank. Why: a rate from fewer tries than one run is too noisy to rank (about 5 points of standard error at 100 tries). The known trade-off: a browser target weighs 2 to 5 against 1 for an HTTP target, so one run of 100 tries can move a network's overall a lot (on 2026-11-15 one LinkedIn run of 100 tries, 11 ok, moved a network's overall success score from 10, rank 1, to 6.90, rank 12, in an hour while its pulses did not change); the 500 of #1134 prevented that but left every browser score not_enough_data. Example: three networks with 600 LinkedIn tries and a fourth with 99 (a run cut short): the fourth's overall is its HTTP targets' alone and the other three rank among themselves, 3 of 3, in every hour until the fourth reaches 100. The value component and every other Index Score input are unchanged. Each change of the setting changes the methodology id.

Which countries count (COUNTRY-MIN-IPS-1, the owner's decision of 2026-11-15, #1137). With the top-level methodology settings country_verdicts = true and country_min_ips (1 since #1253, the owner's decision of 2026-11-16; was 10), a network's country counts only while its latest daily test there found at least country_min_ips unique IPs (the test's own unique_ips: distinct exit IPs of successful answers in the requested country). Each daily test is a verdict in country_verdicts (schema v16, written by its import), which holds from its start until the next daily test of the network and country starts; before a country's first daily test it does not count. A run counts when the verdict in force at its start counts (its country: its batch's, else the requested one); a run that does not count stays in its group, but none of its rows reaches a figure: requests, success, latency, series, targets, IP counts, breakdowns and coverage, pulse slots and tested spans, the latest census, estimates (an estimated hour counts when its daily test counts), the runs list and the * totals. Outages are cut to the counting spans and uptime counts only the time a country counted, so a measured span never bridges a stretch it did not count. The decision is SQL, once per run (atlas/verdicts.py: the counting spans cut by UTC day and joined on network, country and day: linear in the runs; about +0.2 s per hourly build today, +5 s at a full 30-day window). Example with a minimum of 1: 100 IPs on Monday (counts), 0 on Tuesday (still counts: two days in a row), 0 on Wednesday (left out from Wednesday's test), 1 on Thursday (counts again from Thursday's test). Two days in a row (LOWAVAIL-1, #1181): a country that was normally big (its previous test found the minimum or more and its tests of the 7 days before reached 50) still counts on its first test under the minimum, so one bad day never hides its failures. Whether a verdict counts is decided when it is read, from its stored unique IPs and the verdicts before it (verdicts.RULE, schema v20), so a changed minimum applies to every stored verdict at once and nothing is rewritten. A country that does not count is shown as low availability (too_few_ips), or no exits (no_exits) when its test found no IP. The setting changes the methodology id; without it every country counts.

The previous build's success scores (SUCCESS-SCORE-DELTA-1, display only). The Atlas Score is unchanged: its reliability reads each target's metrics.success_rate; the targets' scores.success, challenge_overall and browser_overall are unchanged.

The success score over the 8 card targets (SUCCESS-ALL-8-1, the owner's decision of 2026-11-19; display only). Scores are a ratio to the leader

Every sub-score compares a network with the best network of the same kind (the product's kind, or its name when none is set) in the same window. Higher-is-better values score 100 × yours ÷ best; lower-is-better values (speed: p50 latency of the pulses; value: price per GB) are flipped to 100 × best ÷ yours. Scores are clamped to 0–100, so each component's leader scores 100. Leaders are found again on every calculation. A network alone in its kind is its own leader and scores 100 on every ready component. Only ready, freshly measured components set the best; incomplete, retained, expired and historical scores never do.

Incremental calculation. atlas calculate (incremental by default, also --incremental; the orchestrator's hourly job passes --incremental explicitly) reads metadata first: every run outside a batch, the batch runs started since a day before the 30-day window or with a slot or bucket in it plus each product's first batch run (census and pulse summaries are not read), the window's request buckets, and each daily window's list signature. A window whose signature names a stored list reuses its list id, row counts and since-independent figures from calculated_lists and returns no observation row to Python. Every other window (census-pulse windows have no signature yet, so they always miss) is counted in the database (calculated/sqlwindow.py, each run labelled with its own DB-IP release): the breakdowns of its label combinations, weighted by their IPs, and its geo rows give its list. Since CALC-PARALLEL-1 the missed groups' statements (one per group) run ahead of the group loop on helper connections (calculated/parallel_reads.py). The calculation's transaction exports its snapshot once (pg_export_snapshot()) and each helper opens REPEATABLE READ, READ ONLY, imports it (SET TRANSACTION SNAPSHOT) with the calculation's time zone, and only reads (fleetsql.py's slice counts use the same helper); every write stays on the calculation's connection, in the same order, so the results equal the serial ones. Group sizes are very uneven, so each missed group's observation rows are estimated first (its runs' successful requests in the window, from the bucket rows already read) and the groups go to two lanes: the heavy ones (above calculate.heavy_rows, default 1,000,000) are read largest first on at most calculate.heavy_parallel helpers (default 2) at calculate.heavy_work_mem (default 1GB), the light ones in the build's order on the other helpers at calculate.work_mem (default 256MB, also SET LOCAL in the calculation's own transaction). Each lane keeps at most 2 × K results waiting; the group the build needs next is read first, and a group read out of order is read on the calculation's own connection. These operator settings live in the settings table: calculate.parallel_reads, K, all the helpers (default 8, 1 to 16; calculate --parallel-reads overrides it), and calculate.max_parallel_memory (default 6GB; the database server is shared with production). The calculation prints the helpers of each lane and the worst-case server memory (heavy × heavy_work_mem × 2 + light × work_mem × 2) and lowers the light helpers, then the heavy ones, while it would pass the maximum; there are never more helpers than groups of their lane, nor more than the server's free connections (a quarter of max_connections, at least 20, stays free). With the defaults and both kinds of group that is 2 heavy and 4 light helpers (6 GB). It also prints the temp file bytes the database wrote during the calculation (pg_stat_database.temp_bytes before and after). Since CALC-POINT-IPS-1 the series points' distinct IPs (calculated/point_ips.py) are counted without a sort over their observations: each point once per build (the 7-day and 30-day series share their daily points through the slot memo's digest), its distinct IPs (SELECT DISTINCT) counted per point, which PostgreSQL hash-aggregates, where count(DISTINCT ip_id) sorted every observation row of every point into temp files (38.8 GB in one full recount). The points are cut into batches of at most calculate.point_rows estimated observation rows (default 20,000,000: their runs' successful requests in the point); a lone batch of at most calculate.heavy_rows is counted on the calculation's connection, otherwise the batches run on the same helpers in its snapshot, largest first, the ones above heavy_rows at heavy_work_mem, and the calculation prints the step's batches, time and temp bytes. A failing helper fails the whole calculation: nothing is written or published. A group's missed lists are written together once its last missed window is counted (one INSERT, one label lookup, one COPY), so a missed window, like a reused one, returns no observation row to Python, and only the group's own list rows are held in memory. Such a list also stores its window's IPs per 5-minute bin of their product's first sighting (figures.first_seen, from the window's start on, outside the content hash: a late run moves first sightings, which no signature names). What moves with the cutoff every hour (new IPs, daily pools, the series' IP counts, fleet and overlap IP counts, the estimates' distinct IPs) is counted in the database by calculated/hourly.py and calculated/fleetsql.py, so no observation row comes back to Python for them (the database still reads the window's observations for these counts until CALC-INC-2 and CALC-FLEET-1 keep them in the memo tables); census and pulse inputs come from calculated/rollups.py: since CALC-PULSE-1a their geo rows (totals and light-load histograms) are read from per-hour rollups, not from a scan of the 30-day window, since CALC-PULSE-1b the batch runs' buckets from per-hour copies in one query, not one scan of the window per product, and the census overlaps, pulse slots and tested spans from one read of the batch runs, not three, while the full calculation keeps the 30-day query as its oracle. calculate --oracle (also the Python calculate()'s default) is the full calculation: it reads every observation and aggregates it in Python as before: the oracle every incremental test compares with, byte for byte, for tests and small data (it holds ~5.5 KB per observation row). calculate --full is a recount (CALC-SCALE-1): the incremental calculation reusing no stored list, so every window is counted again in the database and every list written or verified against its stored twin's content hash, in the same worker processes, with the hourly build's memory. Every build keeps each request bucket's latency histogram in two integer arrays (calculated/bins.py: 0.9 KB instead of 8.5 KB a pulse bucket row), lets the runs of one scope share its scope, and hashes its inputs' runs, bucket rows and observations one at a time (calculated/fingerprints.py), not as one JSON copy of them all. Snapshots stored in parts (calculated schema v8)

PostgreSQL refuses a jsonb value whose array or object elements total more than 268,435,455 bytes, and any value over 1 GB; one hourly build of 18 networks × 249 countries is 1.1-1.6 GB. Since calculated schema v8 a build's calculated_snapshots.payload is its head: every top-level key except products and runs, plus "parts": {"products": n, "runs": m} (the number of part rows of each kind), at most 64 MiB (a larger head is refused). Each product group is one 'product' row of calculated_snapshot_parts (with its part_id, product_id and cohort), and the runs, in order, fill 'runs' rows of at most 2,000 runs, written with COPY into the build's LIST partition calculated_snapshot_parts_b<build_id>, which the draft prune and retention drop with the snapshot. Like dropping a breakdown partition, dropping a parts partition locks calculated_snapshot_parts until that transaction commits, so readers of any build's parts wait meanwhile; keep part reads in short transactions. A build that is gone (pruned or expired after a reader looked up its id) reads as no snapshot, never as one without groups: the local API answers 404. A part's content_hash is the SHA-256 of its canonical JSON; the snapshot's is the SHA-256 of the head's followed by every part's (products, then runs, each by position), in hex. Reassembled (head without parts, then products and the runs in order) the payload is the single jsonb payload of the same content, key order included. Builds stored before v8 keep their single payload row (no parts key): the v7 → v8 migration only adds the table and checks that every kept snapshot reads back unchanged, and every reader accepts both. calculated/parts.py holds the format; store.read assembles, store.read_head and store.read_parts read one side, the local API reads the head plus only the parts an answer needs, and snapshot-export streams the parts into the same file as before. The calculation makes each group JSON-ready, validates, persists and slims it on its own, and reads only the ids and scores of the previous build's groups. Since this version a daily (unbatched) group's 24h series lists only the 5-minute buckets with stored requests or availability: a left-out point is the empty point (completed and successes 0, every other value null), which readers restore (parts.dense; the local API does). calculated_series follows the payload: a missing 5-minute row of such a window is that empty point. The 7d and 30d series and the census/pulse groups' series stay complete, and windows no longer carry ip_samples (the methodology keeps sample_limit, unused, so its id does not change).

Windows reference their lists (payload v3)

Since payload schema_version 3 a stored product group no longer copies the top rows of its lists. Each window carries "lists": {"id": list_id, "entries": {name: rows}} instead of its breakdowns arrays and of the pool's geo, countries_breakdown and asns_breakdown arrays: id is its calculated_windows.list_id, and entries names every breakdown (country, region, city, asn, country_asn, city_asn) and pool list with the number of rows the window keeps (the [payload] cap, or fewer). breakdown_entries and pool.list_entries, the full row counts, stay. So a list shared by builds (contract K2) is written to and read from calculated_list_rows only, never copied into each build's parts. A breakdown is the first rows rows of its dimension by position; a pool list is picked from its dimension's rows (geo from the city rows, countries_breakdown from the country rows, asns_breakdown from the ASN rows) as aggregate.pool_lists() picks it: rows with IPs, most IPs first, then by Python's str() of the row. store.read, store.read_parts, snapshot-export and the local API fill every v3 window back (parts.fill, one query per read), so they return the v2 window byte for byte, key order included; only schema_version says 3. A list with fewer rows than a window keeps fails the read. The rows of a list are checked (successes at most completed) when they are inserted, as the calculation validates each group before persisting it; a stored v3 window must name an integer list id and non-negative row counts. Builds stored as v2 keep their rows in their parts and read as before. The website API reads v2 and v3 (API-LISTS-1) and must be deployed first.

Read isolation. store.read_parts (the local API) runs REPEATABLE READ, so its head, parts and list rows come from one database snapshot. store.read and snapshot-export run READ ONLY at READ COMMITTED: each statement has its own snapshot. They are still safe: a build's list rows are collected only once no calculated_windows row references them, a build's windows are deleted only by discard, and discard first drops the build's parts partition, which waits for any reader holding a lock on calculated_snapshot_parts.

Grants for serve. A narrow database role for the local API needs SELECT on calculated_snapshots, calculated_snapshot_parts and current_calculation, and since payload v3 also on calculated_list_rows, place_names and asn_label_names (the rows that fill a v3 window and their labels). It never needs the raw tables (ip_observations stays denied).

Network summaries in the head (payload v4, contract K9)

Since payload schema_version 4 the head carries networks: one entry per network (a (provider, kind) pair), ordered by provider, then kind, computed over every product group of that network (all its countries) by the rules one group uses (calculated/network.py). A reader of the head alone gets every figure the site shows for a network; the product parts, the group lists, the typed rows and the serve answers are unchanged. The entry uses a group's key names: id <provider>:<kind>:network, product_id and product the headline product (the most 30d completed requests; on a tie the lowest id), provider, name, kind, cohort network, criteria (country null, requested_countries the groups' requested countries in upper case, groups their number), census, pricing and evidence (30d values) of the headline product's census-pulse group (else its busiest group; census is then empty), outages the newest 50 of the census-pulse groups, and windows (24h, 7d, 30d).

A network window is computed over the union of its groups: metrics is timed() over all their bucket rows with every pulse slot of the census-pulse groups (requests summed, success time-weighted, light-load latency merged from the histograms, never an average of percentiles), latency under load from the load factors of the union's latency-target rows, uptime and pulse-slot coverage from the census-pulse groups' batches, outages and tested countries; uptime, tests (sums), targets (each target's metrics and readiness; browser targets with their browser object, while browser rows change no network-level figure), series (288 five-minute points for 24h, daily points for 7d and 30d) and success_delta follow the same rules. pool.unique_ips and each series point's unique_ips are distinct over the union's observations in the window, counted in the database (hourly.bucket_ips() with the window as one point; no IP set in Python, so the incremental calculation reads no observation for them). pool.new_ips and observations are sums, churn_rate new over unique IPs, the shares (recurring_share, datacenter_asn_share, classification_coverage, geo_accuracy, enrichment_coverage) the groups' weighted by their unique IPs (null when none has one), daily the most days and the sum of the groups' daily unique IPs. countries, regions, cities and asns (also in daily) are the row counts of the window's network list (K10), and lists is {"id": its list_id, "entries": its full row counts}, which breakdown_entries and pool.list_entries repeat (lists null without one); Network scores, ranks and overlap (payload v4, contract K9)

Each network window has scores {"balanced": score}, scored against the networks of the same kind and window by the rules one group's window is scored with (calculated/network_scores.py, window_scoring.score_window()): every component is 100 × its value over the best ready, fresh value of the networks (lower is better: best over value). The inputs are product_inputs() on the network pool (coverage from pool.daily.unique_ips, diversity from the window's network place counts in pool.daily), the headline product's pricing, the window's measured uptime and the headline group's evidence of that window, whose validity also caps the score's; reliability and speed come from target_score() on the network target metrics, each target fresh by its own last observation. The headline product's effective methodology gives the required targets, weights, minimum requests and coverage and the validity hours; time coverage is metrics.coverage as published (pulse-slot coverage when the network has a census-pulse group, else bucket coverage). rank ranks the networks of the kind (none when fewer than two are ready or retained); previous_rank, scored_at, valid_until and a retained or expired score follow the group rule from the previous build's head networks (same id and window). Only the balanced profile is published, and network targets carry no score. readiness is ready when the balanced score is ready, else partial with completed requests, else unavailable.

overlap is {"exclusive_share", "shared_share", "compared_products", "peers", "as_of"} over the network's distinct IPs in the window against every other network of its kind with IPs (compared_products of them): shared_share is the share of its IPs any of them also has, exclusive_share the rest, and peers lists, in provider order, each such network that shares at least one IP (provider, product_id its headline product, shared_ips, ips_ours, ips_theirs). Without IPs both shares are null, compared_products 0 and peers empty. The IPs are the window's observations of the network's runs inside the window, the set pool.unique_ips counts, so ips_ours equals it; one database statement per window counts them for every network (no IP set in Python). as_of is the cutoff the overlap was counted at. The 24h overlap is counted every build; the 7d and 30d overlaps once a UTC day (owner decision): a build whose previous published head holds them for the same networks, counted the same UTC day and not after its cutoff, by the same implementation and with at least one pair in the window, carries them unchanged, so they can be up to a day old and their ips_ours is the pool of their own as_of. The first build after a deploy or a code change (another implementation_id), and a build whose previous head has no pair in the window, counts them again.

The API serves from it exclusiveIps, the range's uniqueIps (the hour formula's figure the network's pool is shown with) × exclusive_share rounded, so the share stays measured and the count is on the same pool as every other answer (EXCLUSIVE-ESTIMATE-1); the measured ips_ours × exclusive_share (the window's pool.unique_ips for a network with no pair) is observedExclusiveIps, and a window without the formula's figure uses it as exclusiveIps. It serves exclusiveScore, its 1-10 score against the leader of the kind in the window: max(1, 10 × exclusiveIps / the kind's highest exclusiveIps), ranked by exclusiveIps with a tie sharing the average place (EXCLUSIVE-SCORE-1, api/FIELDS.md "Exclusive score"). It is display only: no score component reads it.
