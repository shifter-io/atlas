1. Run a test

From the standalone framework directory, install the locked dependencies. The MMDB stays in the local db-ip directory and is not included in wheels, source distributions or Git.

uv sync --locked --no-editable
uv run --no-editable proxy-index targets

# Supply a gateway privately through your environment:
# PROXY_URL accepts http://user:password@host:port or socks5://user:password@host:port.
# Percent-encode reserved characters in URL credentials.
uv run --no-editable proxy-index run \
  --target generic_http --requests 5000 --concurrency 100 \
  --provider example --product residential_rotating \
  --country US --location dubai --output results

Use generic_https for TLS tests. Both HTTP and SOCKS5 gateways support optional username/password authentication. SOCKS5 resolves the destination through the proxy. For static PROXY_URL runs, --country records requested geography; targeting flags must already be present in the supplied credentials.

Shifter Residential is implemented. Use --provider-config configs/shifter.toml --credentials-file .secrets/credentials.toml. The private file uses owner-only permissions and is excluded from Git, packages and remote uploads; copy credentials.toml.example to set up your own. Add optional overrides such as --param country=us. See the adapter guide, session policies and Python examples.

Set --url http://ip-info.com/myip (or another plain-IP echo endpoint) per test. For Generic HTTPS, use an HTTPS URL. Python callers pass RunConfig(target_url=...). IP Info is the default if omitted; the effective URL is recorded in each summary.

Defaults: 100 requests, concurrency 10, timeout 15 seconds, no rate cap. Optional --rate 50 paces request starts. There are no automatic retries, redirects, cookies or connection reuse. Response bodies are limited to 512 bytes, plus one byte to detect overflow.

A request succeeds only when the response is HTTP 200 and its complete trimmed body is one valid IPv4 or IPv6 address. HTTPS verifies the target certificate. Only Generic HTTP contributes IP observations and pool uniqueness metrics.

2. Call the runner from other code

import asyncio
import os
from proxy_index import JsonSink, ProxyConfig, RunConfig, run

async def measure():
    return await run(
        RunConfig(
            target="generic_http",
            proxy=ProxyConfig.from_url(os.environ["PROXY_URL"]),
            requests=5_000,
            concurrency=100,
            provider="example",
            product="residential_rotating",
        ),
        JsonSink("results"),
    )

summary = asyncio.run(measure())
print(summary.to_dict())

A future methodology layer chooses the target and configuration and invokes this function. It decides cadence, geography, budgets and which results to enrich/publish. Those policies do not live inside targets.

Pass an asyncio.Event as stop= for graceful interruption; it returns a partial summary with status="cancelled". Cancelling the caller task also saves partial results, then propagates cancellation. CLI SIGINT/SIGTERM does the former and exits 130. A normally completed measurement exits 0 even when proxies fail; configuration, storage or framework failures exit 2.

3. Result contract

Each invocation creates a unique run directory. summary.json is written last and serves as the completion marker. Interrupted or failed runs are explicitly marked; a directory without a summary is incomplete.

summary.json

Schema/framework/target versions; sanitized configuration; UTC start/end; requested, started, completed, cancelled and not-started counts; successes, errors by category, HTTP statuses, body bytes, throughput, latency percentiles (latency_ms: p50, p90, p95, p99), mean success latency (latency_mean_ms, from the 1 ms histogram bins, to 0.1 ms; null with no successes; absent from summaries written before it existed, which readers treat as unknown) and exact HTTP unique IPs. Includes five-minute counters/histograms and the IP file checksum/row count.

ips.jsonl.gz

One row per run × five-minute UTC bucket × normalized IP. Each row contains schema_version, run_id, bucket_start, ip, count, first_seen and last_seen. HTTPS produces an empty IP file and null unique_ips.

Definitions that downstream consumers must preserve

  • requested = started + not_started; started = completed + cancelled; completed = successes + total_errors. On a framework failure, “cancelled” includes requests aborted by that failure.
  • Latency is measured with a monotonic clock from request execution through complete body receipt, including connection setup and TLS, excluding runner queue/rate waits. Percentiles include successes only; absent samples produce nulls.
  • The sparse ceil_ms_v1 histogram stores [upper_bound_ms, count] bins with 1 ms resolution. Percentiles use nearest-rank selection and round upward by less than 1 ms. Merge bin counts before calculating combined percentiles.
  • Throughput is completed requests divided by elapsed run time. response_body_bytes counts bytes read from bodies, including failed responses; it is not provider-billed traffic or total TCP/TLS bytes.
  • Observations belong to the bucket in which the response completes. UTC is anchored to the monotonic run clock so clock corrections do not reopen flushed buckets.
  • Deduplicate IPs across buckets/runs when computing window or fleet uniques. Adding per-run unique counts would overcount recurring addresses.
  • Error categories: proxy authentication, proxy connection, DNS, TLS, timeout, HTTP status, invalid body, oversized body, connection and protocol. Returned error data never includes raw exception messages or credentials.
  • Every failed request has one verdict, counted in challenges, blocks, timeouts or proxy_errors (or a plain error). A block is the target refusing us: HTTP 403, 429, 451 or a block page. Proxy-side failures are never blocks: 407, 502, 509, and 503/504 without a challenge or block page, a failed CONNECT, a reset or dropped connection and a gateway name that does not resolve are proxy_errors; no answer in time is a timeout. Other target statuses (404, 500, …), TLS failures and unusable bodies are plain errors. Block rate is published next to success and stays inside reliability; it is not a separate score component.

Memory scales with distinct IPs, the current bucket, a bounded export backlog and small aggregate histograms. A fixed pool bounds active requests. Bucket serialization runs on one background writer; slow storage delays new requests instead of blocking the event loop during existing requests. No list of all request objects is retained.

4. Enrich from the existing MMDB

The supplied file is db-ip/dbip-full-2026-09-14.mmdb, identified internally as DBIP-Location-ISP (compat=Enterprise). It is a local copy from the existing DB-IP folder. Its SHA-256 is ca81b1d51dd4e502bc9c9568b5c3dd7a865094f7c29ed6b63947d1763ac6c4f2.

uv run --no-editable proxy-index db-info
uv run --no-editable proxy-index enrich results/RUN_ID

# Select a different local release explicitly:
uv run --no-editable proxy-index enrich results/RUN_ID --mmdb /path/to/release.mmdb

DBIP_MMDB is the environment alternative. Automatic discovery takes db-ip/dbip-full.mmdb, the one file proxy-index dbip update replaces with each newly verified release (the daily update on the manager and on pulse nodes: README, “Daily DB-IP update”); without it, it requires exactly one file, and with multiple releases you select one explicitly. The database is memory-mapped. A bounded cache reuses lookups; no geolocation API requests are made.

Enrichment validates the IP artifact checksum, then writes a separate compressed JSON Lines file and release report. Original measurements are preserved. Each row records the release checksum and country, region, city, coordinates, ISP, organization, ASN, connection type and usage type. Missing records remain unknown. Re-enriching with another MMDB creates another version; repeating the same release refuses to overwrite existing output.

Enrichment is optional and only accepts Generic HTTP pool results. The source MMDB is a separate licensed data asset; the framework’s MIT license covers its code. Field definitions follow the DB-IP MMDB specification.

5. Add or change a target

Targets expose an ID, version, engine, pool eligibility, build_request() and assess(status, body). Register a new implementation in a TargetRegistry and pass it to run(..., targets=registry). Adding a built-in also registers it in the default registry; the CLI automatically lists it. Change the target version whenever measurement semantics change.

from proxy_index.targets import EchoIpTarget, TargetRegistry

targets = TargetRegistry()
targets.register(EchoIpTarget("my_ip_target", "https://example.test/ip"))
# await run(config_for_my_ip_target, sink, targets=targets)

Transport.execute(target, *, context=None) returns a normalized outcome. Since v0.2 the runner supplies a RequestContext with run, request and worker identities for provider sessions; custom transports must accept this keyword. A future browser adapter can implement the same execution protocol through transport_factory; browser targets can carry additional settings in their own implementation. Playwright is not needed or installed for baseline targets. Custom sinks implement start, observations, finish and abort. Observation writes are serialized on one background thread; finish runs only after they complete.

Import transaction: validate counters/checksums → COPY observations into staging → insert run/history → import optional MMDB releases → update cached metrics → commit. Imports are serialized with a database advisory lock; measurement requests run independently. Invalid data rolls the entire import back. Replays validate the same content and can attach a newly generated enrichment release without counting measurements again.

Raw-data archive (ARCHIVE-1): raw measurement rows are meant to stay 30 days in the database (partitions.RAW_DAYS); the calculator reads no further back, so the 30-day window's previous_period has no rows and its success_delta is null (the 24-hour and 7-day comparisons are unchanged). proxy-index archive export --date YYYY-MM-DD --database-file … --out DIR writes one UTC day into DIR/YYYY-MM-DD.tar.gz and deletes nothing. A batch belongs to the UTC day of its scheduled_for, a run to its batch's day (a daily test, which has no batch, to the day it started), and every row tied to a run or batch goes with it: the batches, batch runs, runs, buckets, geography buckets, IP observations, run enrichments, estimated hours and run roles of the day, the day's tape events, and the dimension rows they reference (providers, products, regions, countries, targets, nodes without their token hash, IPs, enrichment, places, networks, DB-IP releases, pools and scopes), so a file loads on its own. The file is a gzip tar: manifest.json first (format and version, day, storage and calculated schema versions, and per table its role, columns, rows, bytes and sha256), then one CSV per table in load order, each from COPY … TO STDOUT (FORMAT csv, HEADER) ordered by primary key, all from one snapshot in UTC/ISO settings; the same rows give the same bytes, so the file can be re-checked and re-imported with plain tar and COPY. proxy-index archive restore --file … --database-file … loads a file into a database of the same storage schema version in one transaction: every CSV's sha256 and row count must match the manifest, ids are kept, rows already present stay as they are (a repeated restore inserts nothing), and it refuses (exit 2, nothing changed) when the database's ids mean other rows (the same product id, IP id, run id or batch slot holding other values): restore into the database the file came from, or into an empty one. Links to batches outside the file (a retried census, a tape event of another day's batch) become NULL; missing partitions are created and identity sequences move past the restored ids.

Daily archive job. The orchestrator's archive job (00:40 UTC, off until the setting archive.enabled is true; archive.spaces_file, default .secrets/spaces.toml, and archive.work_dir, default .state/archive) takes the oldest day that still holds rows, at most 3 per run, and stops at the first that is not due. A day is due once none of its batches or batch runs is open and its last run end, batch end and estimated-hour end are at least 30 days old; with daily tests (whose 24 estimated hours reach into the next day) a day is archived about 32 days after it, so no calculator window loses a row. For each due day it exports the file, uploads it private to raw/YYYY/YYYY-MM-DD.tar.gz (signed payload sha256 and Content-MD5; the file's sha256 and the sha256 of its fact entries stored as object metadata), checks that the object has the file's size, MD5 and sha256, and only then deletes the day's rows in one transaction under the ingest lock: links from rows that stay (tape events, outages, a later retry) to the day's batches are set NULL, a daily partition holding only the day's rows is dropped whole, other rows are deleted by run, and every deleted count must equal the file's, else nothing is deleted. Objects are never overwritten or deleted: a rerun after a crash finds the object, and deletes the rows when its facts are the same; different facts leave the day alone and fail the job (archive_changed). Failures show in the job health and raise job_failed:archive. The job also fails (archive stalled) while the oldest day still holding rows is more than 33 days old (30 plus 3), whatever holds it: a batch left open, an unreachable bucket or database, or archive_changed. While archive.enabled is on, the daily retention job no longer deletes estimated hours: they go only with their run, after its day file is verified. Recovering from archive_changed (the bucket holds a file for the day whose facts differ from the database's, for example after a count mismatch stopped a purge): download it with archive restore --date D into an empty database and compare its fact tables with the source; once the difference is understood, keep the object (it stays, versioned) and delete or rename it deliberately with the owner's Spaces access, then let the next run export the day again. Every later day waits behind it, so the stall alert names it. A day without any batch or run gets no file. proxy-index archive run --database-file … --spaces-file … --work-dir … does the same by hand; archive restore --date D --spaces-file … restores a day straight from the bucket; archive bucket --spaces-file … [--apply] checks that the bucket has no public grant and has versioning (--apply enables it).

Raw files of each update (owner decision 2026-11-03). With the setting raw.spool_dir, the orchestrator API files every upload it has ingested, exactly as the node sent it, under <spool>/YYYY/MM/DD/HH/<kind>-b<batch>-<run id>.tar.gz by the UTC hour of the import, and daily ingest --spool DIR files each imported daily-test run directory as daily-<run id>.tar.gz (files 0600; a replay keeps the first copy). The orchestrator's raw_upload job (every 5 minutes, when archive.enabled and raw.spool_dir are set) packs each hour that ended at least 5 minutes ago into one private object raw-files/YYYY/MM/DD/YYYY-MM-DDTHH.tar (a manifest.json with each file's size and sha256, then the files), checks its size, MD5 and sha256 in the bucket and records it in the hour's uploaded.json; a file that arrives after its hour was uploaded goes into a further part (…THH.1.tar). It then removes each hour older than 30 days whose files are all uploaded; an hour with a file that is not uploaded is never removed, and an object in the bucket that differs fails the job (archive_changed). proxy-index archive rebuild --spool DIR --from D --to D --database-file F imports the spooled runs of those days, oldest first; replays are no-ops, and a run whose batch is not in the target is imported without its batch link (listed as unlinked). Estimated hours are not part of a rebuild (daily ingest --formulas recomputes them).

Spaces settings. A 0600 file with a [spaces] table: endpoint (https, for example https://fra1.digitaloceanspaces.com), bucket, access_key_id, optionally region (default the endpoint's first label) and secret_access_key. Without the secret it is read from the macOS keychain (generic password, service Proxy Index Spaces archive, account the access key id). campaign manager deploy --spaces-file … writes the complete file, secret included, to the manager's root-only .secrets/spaces.toml over SSH stdin; the secret never appears in argv, logs or the repository. The client is a small AWS Signature V4 implementation on the standard library (single PUT, Spaces' limit 5 GB).

Database server check and nightly ANALYZE (DB-CHECK-1): proxy-index db-server check --database-file … reads, in one read-only transaction that is rolled back, the server version, the session's SSL, the settings (recorded, never judged or changed), the extensions and whether pg_stat_statements is installed and preloaded, the database size and the ten largest tables (partitions counted toward their root), every role's attributes and memberships, the owner of every partitioned table and the default privileges. It judges three roles (--runtime-role, --api-role, --admin-role; default proxy_reviews, proxy_api, proxy_admin): the run-time role needs USAGE and CREATE on schema public, SELECT, INSERT, UPDATE and DELETE on every framework table and ownership of every partitioned table and of its partitions (creating a partition needs the parent's owner, the archive drops partitions, and ownership also allows ANALYZE; otherwise MAINTAIN); the API role needs SELECT on every framework table and view; the admin role, which runs migrations, needs CREATEDB, default privileges that give both roles those privileges on its new tables, and membership in the run-time role once that role owns the partitioned tables. Every gap is printed with the exact statements that close it, in the order to run them, each marked admin (run with the admin config) or superuser (role attributes and memberships the admin role cannot grant itself); --sql prints only those statements. The check never runs them. proxy-index db-server analyze --database-file … runs ANALYZE on the partitioned parents autovacuum never analyzes (ip_observations, run_buckets, run_geo_buckets, test_events, and calculated_snapshot_parts once it exists), each in its own transaction with a 60-second lock timeout, and prints one JSON health line with each table's status and seconds; it exits 1 when a table is missing, fails, or is skipped with a warning (no MAINTAIN privilege). Both commands read an existing database file in place; a file without sslmode connects with sslmode=require, and no output holds the password. PostgreSQL 17 or newer.

Calculated results, scores and website API

The source history stays in schema v5. The additive calculated schema (v7) has its own version/checksum; db-migrate upgrades an unmodified calculated v2 to v6 layer in place: calculated/migrate_v5_v6.sql moves every breakdown row into its build's partition and calculated/migrate_v6_v7.sql moves the breakdown names into the shared name lists, each step verified against a copy before committing. No IP membership is stored per reporting window; observations supply exact distinct counts. A calculation reads a repeatable snapshot of history and writes all prepared results in one transaction. Publication switches a single pointer only after validation. Failed calculations keep the previous publication intact.

calculated_lists / calculated_list_rowsSince calculated schema v9 (contract K2): each target-free window's full breakdowns are one list, named by calculated_windows.list_id. calculated_lists holds its group and window, the row count per breakdown (entries), the window's since-independent pool figures and pool-list counts (figures), a content hash and a signature. A later build whose window has a stored list's signature reuses that list and writes no rows; the list is still computed and its content hash compared, and a mismatch fails the calculation ("list signature is incomplete"), so the previous build keeps serving. The mismatch is permanent for that signature: the stored list stays referenced by the builds kept, so every later calculation with the same window inputs fails the same way and the current build keeps serving. It ends when the runs leave the window (up to 30 days for 30d) or when IMPLEMENTATION_ID changes, which changes every signature. Build retention. After every publication (calculate --publish and snapshot-publish, in the same transaction, after the draft prune) the database keeps the current build, the newest published build of each UTC day of the last 30 days, and the drafts whose payload the prune kept; every other build is deleted with its snapshot, windows, series, scores, components, reasons and overlaps, and then every list no remaining window references (lists shared with a kept build stay). Days count back from the UTC day of the current build's cutoff, not from the clock, so a paused calculator loses nothing. RETAIN_DAYS (30) and RETAIN_PER_DAY (1) in calculated/store.py set the defaults. proxy-index calculate-expire applies the rule now; --dry-run only reports, read-only, the builds it would keep and delete with the rows and approximate bytes per table; --days and --per-day override the numbers. It also runs on a calculated v5 database, so on a large database expire first and migrate afterwards: the migration then moves only the kept rows. Deleted rows, list rows included, leave dead space until VACUUM reuses it (calculated_list_rows autovacuums at 1% of the table); dropped snapshot-part partitions free theirs at once. Creating a build's calculated_snapshot_parts partition (every calculate that writes a build) and dropping expired ones (every publication and calculate-expire) lock that table exclusively until the transaction commits. Lists are deleted row by row, with ordinary row locks only, so readers of calculated_list_rows, calculated_list_details, calculated_breakdown_details and current_breakdowns (Postico, typed-row queries) never wait for retention: a reader's snapshot keeps seeing the lists it started with. The website API's refresh also reads calculated_snapshot_parts, so it waits for that table's lock while a build is written or partitions are dropped; meanwhile the API keeps serving the version it loaded before.

Browse views (Postico, no payload reads). calculated_snapshots_list: one row per build with cutoff, methodology, published, is_current, content hash and payload_bytes (the stored, compressed size, taken from the TOAST pointer without fetching the payload). current_windows: the current build's windows with provider and product names. current_breakdowns: the current build's breakdown rows with provider, product, cohort, window, dimension name, country/region/city, ASN name and usage type, counters and success rate. All windows are half-open [start,end) and end on a five-minute boundary. A cutoff inside a five-minute bucket moves to that bucket's end when the bucket holds data and every run with data in it had finished by the requested time (always so for a calculation without --as-of: a run is stored only once it has finished), so a run that ended just before the calculation is in it; otherwise it moves to the bucket's start. A bucket is in a snapshot whole or not at all. Such a cutoff can be up to 5 minutes past the clock, so an open outage's duration and downtime can run up to 5 minutes ahead of it, and score and evidence expiry can take effect up to 5 minutes early. Latency bins are merged before nearest-rank percentiles at 1 ms ceiling precision. Window coverage (readiness) is the fraction of five-minute slots with requests, or of pulse slots for census/pulse cohorts, not measured uptime: pulse slots are the product's done pulse runs, filled by one with at least one request, also when every request failed (the provider was down: it lowers success and uptime and opens an outage, it is never a gap). A run is only ever failed by our side (no node, never started, went silent, node shut down or erred, upload rejected), so failed runs and operator-skipped or killed batches are not slots and never count against the provider. Daily charts group successive 24-hour intervals from the window start. Every request counts for every metric: census, pulse and load runs alike feed success, blocks, timeouts, exit IPs, breakdowns and bytes, and minimum_requests counts every request of a required target; run roles are display labels only. New-IP counts use lifetime product first-seen timestamps; recurrence counts IPs seen on multiple UTC dates. DB-IP enrichment uses one identified release, with unknown values preserved.

DB-IP release per run (RELEASE-PER-RUN-1): the one identified release is chosen per run. Each observation is labelled from the newest release its run was enriched with (run_enrichments), so the daily DB-IP update, which replaces db-ip/dbip-full.mmdb under the same name, changes only the runs enriched after it, and every older run keeps the countries, regions, cities and networks it was saved with. A release is its file's sha256 (dbip_releases.sha256), never its file name: a replaced file with new content is a new release. Runs without enrichment (pulse runs) stay unlabelled. An IP returned by runs with different releases takes the labels of its lowest run_key in the window. The snapshot's dbip_releases lists the ids of every release its observations were labelled with, ascending; dbip_release names the newest of them, or is null when the build used none.

Time-weighted metrics and latency under load

A window is split into time slots: the cohort's pulse interval (the shortest pulse_interval_minutes of the pulse-enabled targets) made a whole multiple of the 5-minute stored bucket, lcm(interval, 5): 30 minutes in production, 10 in staging (2-minute pulses), so no census request lands in a slot it did not run in. Pulse and load requests belong to their batch's slot, census and unbatched requests to the slot they ran in. Every slot with observed requests weighs the same: success_rate is the mean of the slot success rates, successes ÷ requests observed in the slot (nothing is counted for requests nobody observed); request_success_rate keeps successes ÷ requests. Latency is measured on one target only, latency_target (default generic_http, the census target): light-load and under-load latency, the speed score, breakdown latency and the load factor all come from it. Other targets count for success, blocks, timeouts, IPs, authenticity, DC ASNs, bytes and uptime; their targets.<id>.metrics.latency_ms and latency_under_load_ms hold nulls, with latency_reason. Light-load latency (latency_ms, pulses only) merges the slots' latency histograms after normalising each to weight 1 and reads p50/p90/p99 from the merged distribution; a slot with fewer than [slots] min_latency_successes (30) successes does not vote. Percentiles are never averaged. Breakdown latency is light-load latency.

Census overlap. A pulse or load run of a product that ran while a census of the same product was running (any country: account and node are shared) is marked during_census, derived at calculation time from the stored run start and finish times (the ingested run's, else the orchestrator's). It still fills its slot and counts for uptime, outages, down slots and every request metric, but it is left out of light-load latency (breakdowns included), of the time-slot success (a slot votes with its other requests; one left with only such pulses votes 0 if every request in it failed and does not vote otherwise, time_slots.skipped_during_census), and of the load factor (it needs a clean load run and a clean reference pulse, otherwise the newest earlier factor carries forward, latency.regions[].factors.excluded_during_census). Each window publishes census_overlap: pulses and targets.<id> with clean and during_census (runs, requests, successes, request_success_rate, success_rate, latency_ms), load, census_batches and basis; metrics.latency_reason says why light-load latency is missing.

In every pulse slot of the census target each product also runs one wave of census_concurrency requests (1,000 in production, 100 in staging) at census concurrency in every runner region's reference country: a test_batches row of kind load with the pulse's scheduled_for, started load.delay_seconds (60) after the pulses so the reference pulse is not measured under its own load wave. Like every scheduled test it sends only the country parameter. The orchestrator picks each region's reference once per UTC day, with the day's first pulse plan, and stores it in load_references: the fastest enabled country tested from the region over the trailing load.reference_days (7), by the light-load p50 of its census-target pulses that did not run during a census (every product weighing the same; at least load.reference_min_successes, 300, successes; ties by country code; basis fastest); an operator override (load.reference_overrides, override); without enough history the region's default (load.reference_defaults: nyc3 US, fra1 DE, lon1 GB, ams3 NL, tor1 CA, sgp1 SG, blr1 IN, syd1 AU; staging fra1 RO; default); else its first enabled country (first_enabled). load.enabled switches the wave off. Per percentile, factor(R, t) = load latency ÷ pulse latency of region R's reference country in slot t, and every country's latency under load is its pulse latency(C, t) × factor(region of C, t). A slot without a usable load run (both runs need min_latency_successes successes) takes the region's newest earlier factor in the window; without one that country's slot has no under-load value, and a window without any has null with under_load.reason. The window value is the mean over slots and countries. Census latency never makes a factor. Load runs count for every request metric, not for light-load latency, slot coverage or uptime.

Worked example: fra1's reference country is RO. In the 18:00 slot the RO pulse (100 requests) has a p50 of 600 ms and the RO load wave (1,000 at once) 900 ms, a factor of 1.5. The Bulgarian pulse in that slot (BG is tested from fra1) has a p50 of 800 ms, so Bulgaria's latency under load at 18:00 is 800 × 1.5 = 1,200 ms. nyc3 has its own reference and factor for the US, Mexico and the rest of its countries. If fra1's 18:30 load wave fails, 18:30 uses fra1's 1.5 of 18:00.

Snapshot fields per window: metrics.success_rate (time-weighted), metrics.request_success_rate, metrics.latency_ms (light load), metrics.latency_under_load_ms, metrics.latency_reason, metrics.under_load (slots, own_factor, carried_factor, without_factor, reason), metrics.time_slots, the same per target (latency fields null except on the latency target), census_overlap, and latency: target, regions (per runner region region, reference (country, target, concurrency of its newest load wave), chosen (the day's choices in the window: day, country, basis, p50_ms, successes, candidates) and factors (slots, excluded_during_census, mean and latest per percentile)) and countries (per requested country its region, light-load and under-load latency). benchmark is a copy of metrics for older readers.

Browser targets

Browser runs (test batches of kind browser; browser pulse contracts) are measured per target only and never enter a network-level figure: a network's window metrics, census overlap, series, uptime (their batch runs are not in its denominator), coverage, scores, fleet totals and breakdowns are exactly what they would be without any browser run (calculated/browser.py; a bucket is a browser bucket when its run's batch kind or its target's engine is browser). Browser runs never move the calculation cutoff either: a five-minute bucket that holds only browser data waits for a later calculation. Each browser target measured in a window gets the same per-target entry as a network target (time-weighted metrics, coverage as the share of 5-minute buckets, its own target score; no latency, which is the latency target's), plus browser. A group target of the methodology's [target_groups] (ai_answers = ["ai_overview", "ai_chatgpt", "ai_gemini"]) is measured over the union of its sources' requests and is never scheduled itself; each source keeps its own entry. No browser, group or source target may be a required target (the methodology refuses one). A window without browser runs has no browser entries. Fields of targets.<id>.browser (K-BP6):

  • outcome_rates: ok, challenge, block, login_wall, timeout, proxy_error, no_content, no_answer and other_error, each a fraction of the completed tries (they sum to 1; all null when none completed). ok counts successes; challenge, block, timeout and proxy_error the typed bucket counters; login_wall, no_content and no_answer the error codes of the error verdict; other_error every other failed try (browser_error, tls, ...).
  • page_load_ms: p50, p90, p95 and p99 of the successful tries' page-load times (the buckets' histograms hold successes only).
  • group: the group target this target is a source of, or null.
  • sources: on a group target its sources in the methodology's order, else null.

traffic.by_test has a browser entry only when there were browser runs; its bytes are the browser's estimates, so it carries bytes_exact: false. The traffic report's total and by_provider (GET /v1/traffic) add those estimates to the exact bytes of the other tests. Adding [target_groups] changes the methodology id once, as any methodology change does.

Edit configs/methodology.toml: target weights initially 80% success / 20% speed; product weights 22/14/10/12/8/10/10/14. Diversity weights, hosting usage types, slot settings, grade boundaries, required targets, minimum samples, coverage, validity, refresh interval, product/target overrides and ranking profiles are configurable. The balanced profile uses the top-level weights. Scores do not replace missing inputs with zero or redistribute missing weights. Previous complete scores retain their dates; expired scores and scores from an older methodology leave current rankings. Editorial content never enters scoring.

Scores are a ratio to the leader

Every sub-score compares a network with the best network of the same kind (the product's kind, or its name when none is set) in the same window. Higher-is-better values score 100 × yours ÷ best; lower-is-better values (speed: p50 latency under load; value: price per GB) are flipped to 100 × best ÷ yours. Scores are clamped to 0–100, so each component's leader scores 100. Leaders are found again on every calculation. A network alone in its kind is its own leader and scores 100 on every ready component. Only ready, freshly measured components set the best; incomplete, retained, expired and historical scores never do.

Pool counts are the average of daily (24-hour) counts over the window's days with observations, so a new network measured for a few days compares fairly with one measured for the full 30-day window. Window totals stay in pool for display; the daily averages are in pool.daily. The composite is the weighted mean of the eight ratios with the profile's weights and maps to a grade. Every component's inputs carries the raw value, the leader's raw value best and the number of ready peers (diversity per dimension, product reliability and speed per target), so every score can be reproduced from the snapshot.

Incremental calculation. proxy-index calculate --incremental reads metadata first: every run outside a batch, the batch runs started since a day before the 30-day window or with a slot or bucket in it plus each product's first batch run (census and pulse summaries are not read), the window's request buckets, and each daily window's list signature. A window whose signature names a stored list reuses its list id, row counts and since-independent figures from calculated_lists and returns no observation row to Python. Every other window (census-pulse windows have no signature yet, so they always miss) is counted in the database (calculated/sqlwindow.py, each run labelled with its own DB-IP release): the breakdowns of its label combinations, weighted by their IPs, and its geo rows give its list, written with one COPY as soon as the window is counted, so a missed window, like a reused one, returns no observation row to Python and keeps only its counts in memory. Such a list also stores its window's IPs per 5-minute bin of their product's first sighting (figures.first_seen, from the window's start on, outside the content hash: a late run moves first sightings, which no signature names). What moves with the cutoff every hour (new IPs, daily pools, the series' IP counts, fleet and overlap IP counts, the estimates' distinct IPs) is counted in the database by calculated/hourly.py and calculated/fleetsql.py, so no observation row comes back to Python for them (the database still reads the window's observations for these counts until CALC-INC-2 and CALC-FLEET-1 keep them in the memo tables); census and pulse inputs come from calculated/rollups.py: since CALC-PULSE-1a their geo rows (totals and light-load histograms) are read from per-hour rollups, not from a scan of the 30-day window, while the full calculation keeps the 30-day query as its oracle. calculate, the orchestrator's hourly job (also --full, and the Python calculate()'s default), stays the full calculation until CALC-INC-2 and CALC-FLEET-1: it reads every observation and aggregates it in Python as before: the oracle every incremental test compares with, byte for byte, and the only mode that recomputes a reused list and compares its content hash. A build's input hash differs between the modes (the incremental one hashes run metadata and signatures instead of observations), so each mode reuses only its own stored builds.

Fleet counts from memos (CALC-FLEET-1). In the incremental calculation calculated/fleetsql.py counts every IP figure across product groups in the database from memos. Each 5-minute bucket of the longest window keeps the digest of its runs and its distinct IPs (calculated_bucket_ips); a bucket whose runs changed, a new or a late run, is counted again and folded into calculated_ip_last_seen (each IP's newest bucket, with greatest()). The * fleet window totals are the IPs last seen in the window, which holds when no folded bucket is at or after the cutoff (the hourly build); an older cutoff counts its window directly and changes no memo. The * 24h series takes its points from the bucket memo; the 7d and 30d series run one count(DISTINCT ip_id) per daily slice on the (bucket_start, ip_id) index, at most 4 at a time on connections that import the calculation's snapshot. A cohort of one group takes its group's pool count and has no overlap; a cohort of two or more is counted again only when a member's runs in the window changed (its counts are kept in calculated_distinct under the digest of the members' runs clipped to the window). The fleet's timed() runs on bucket rows merged per bucket, time slot, target, light-load, census-overlap and outcome flag, which gives the same integers as the rows. IPs and buckets older than 31 days and fleet cohort counts unused for 2 days are collected.

Cutoff values from memos (CALC-INC-2). The daily pools, new IPs, series IP counts and the estimates' distinct IPs come from the memo tables (calculated/hourly.py), so an hour without a new test reads no observation for them. When a run is first recorded, calculated_run_ranges stores the figures of each of its single buckets; the whole run, or the prefix or suffix a 24-hour edge cuts from a run of at most 12 buckets, is counted and stored the first time a slice holds it alone. A slice or series point holding two or more runs, or a longer run's other ranges, uses calculated_slot_figures, keyed by the digest of its runs, their releases, bounds and requested countries, counted in the database on a miss. The estimates' distinct IPs are kept per run set in calculated_distinct, in both modes. First-seen bins are kept only from the earliest start a slice of that length can have. Every build mode records runs the same way, and a run recorded for the first time (or ingested after the newest recorded run, whatever its window) passes the late-run rule: if it saw an IP first that runs already counted saw too, the ranges of its product's runs with a bucket since then are counted again, with the slot memos holding them. This module's memos unused for 2 days and the ranges of runs started over 31 days ago are deleted once per build transaction.

Historical cutoffs can be calculated and exported, but cannot rewind the current publication. The saved Shifter receipt reconciles 5,000 requests, 4,997 successes, 4,967 IPs; p50/p90/p95/p99 are 1113/1395/1644/3292 ms. Its original run date remains visible even after it leaves a reporting window.

Network lists (contract K10). A network is one (provider, kind) pair, id <provider>:<kind>:network. Every build writes one list per network window to calculated_lists and calculated_list_rows, after it has stored every product group (calculated/netlists.py): cohort network, product_id the headline product (the network's product with the most 30d completed requests; on a tie, the lowest id), signature NULL, figures {}, entries the full row counts by dimension (country, region, city, asn, city_asn) and content_hash the sha256 of the rows. Its rows merge the rows of every group of the network with a list for that window (daily country groups and the census-pulse group), in one INSERT … SELECT per window, so no row passes through Python: dimensions c, r, g, a and y (no country × ASN), grouped by place and ASN label. ips, observations, completed, successes, challenges and blocks are summed; an IP that two groups of the network saw counts twice, so a merged row's ips is an upper bound of its distinct IPs, as a group row's is. p50, p90 and p99 are those of the member row with the most successes (ties: the lowest list id, then position). 7. Validate in CI

Tier 1 is the CI check tier1 (.github/workflows/ci.yml) on the exact head of every ready pull request, every push to main and every night. It runs on one fresh self-hosted CI server: the privacy, commit-message, commit-identity and secret checks for every change, then for code the locked uv sync, the wheel and sdist build, ruff, ruff format, complexity, source limits, the campaign scope suite and the scale benchmark in the background, while pytest runs every test on all CPUs (pytest-xdist), each worker with its own databases in one PostgreSQL. Tests marked serial measure time or memory and run afterwards on their own. Pull requests skip the tests marked slow (over 60 s alone); every push to main, the nightly run and owner dispatches run them. Branch coverage of the combined run gates changed lines (85%), critical campaign files (90%) and the delete and project paths (100%).

uv run --no-editable ruff check src tests scripts
uv run --no-editable ruff format --check src tests scripts
uv run --no-editable pytest -n auto --dist worksteal --cov=proxy_index --cov-branch
uv run --no-editable python scripts/benchmark.py

Tests outside CI run on a disposable test server, never on a workstation; the source stays in the local checkout and only evidence comes back.

Tests use loopback HTTP/SOCKS5 gateways and a private test certificate authority. They check both TLS verification outcomes, authentication, proxy-side DNS, no hidden retry, fragmented/oversized bodies, concurrency, timeouts, cancellation, exact counts, bucket transitions, checksums and versioned enrichment. The optional real-MMDB test uses the local licensed file and is skipped in public builds.

The scale script simulates 5,000 successful requests with 5,000 distinct IPs at concurrency 100 and checks exported counts/percentiles. It reports wall time, peak in-flight requests and peak process memory. This is a processing benchmark, not an estimate of real proxy throughput.

Live proxy tests require PROXY_URL or a provider config with a private credential file (environment credentials also remain supported). Automated unit/integration tests never send traffic to external IP-check services; live measurements are explicitly invoked. Provider tests cover Shifter flags, overrides, session isolation, both targets/transports, status preservation, secret redaction, credential-file permissions and configurable URLs.

Snapshots stored in parts (calculated schema v8)

PostgreSQL refuses a jsonb value whose array or object elements total more than 268,435,455 bytes, and any value over 1 GB; one hourly build of 18 networks × 249 countries is 1.1-1.6 GB. Since calculated schema v8 a build's calculated_snapshots.payload is its head: every top-level key except products and runs, plus "parts": {"products": n, "runs": m} (the number of part rows of each kind), at most 64 MiB (a larger head is refused). Each product group is one 'product' row of calculated_snapshot_parts (with its part_id, product_id and cohort), and the runs, in order, fill 'runs' rows of at most 2,000 runs, written with COPY into the build's LIST partition calculated_snapshot_parts_b<build_id>, which the draft prune and retention drop with the snapshot. Like dropping a breakdown partition, dropping a parts partition locks calculated_snapshot_parts until that transaction commits, so readers of any build's parts wait meanwhile; keep part reads in short transactions. A build that is gone (pruned or expired after a reader looked up its id) reads as no snapshot, never as one without groups: the local API answers 404. A part's content_hash is the SHA-256 of its canonical JSON; the snapshot's is the SHA-256 of the head's followed by every part's (products, then runs, each by position), in hex. Reassembled (head without parts, then products and the runs in order) the payload is the single jsonb payload of the same content, key order included. Builds stored before v8 keep their single payload row (no parts key): the v7 → v8 migration only adds the table and checks that every kept snapshot reads back unchanged, and every reader accepts both. calculated/parts.py holds the format; store.read assembles, store.read_head and store.read_parts read one side, the local API reads the head plus only the parts an answer needs, and snapshot-export streams the parts into the same file as before. The calculation makes each group JSON-ready, validates, persists and slims it on its own, and reads only the ids and scores of the previous build's groups. Since this version a daily (unbatched) group's 24h series lists only the 5-minute buckets with stored requests or availability: a left-out point is the empty point (completed and successes 0, every other value null), which readers restore (parts.dense; the local API does). calculated_series follows the payload: a missing 5-minute row of such a window is that empty point. The 7d and 30d series and the census/pulse groups' series stay complete, and windows no longer carry ip_samples (the methodology keeps sample_limit, unused, so its id does not change).

Windows reference their lists (payload v3)

Since payload schema_version 3 a stored product group no longer copies the top rows of its lists. Each window carries "lists": {"id": list_id, "entries": {name: rows}} instead of its breakdowns arrays and of the pool's geo, countries_breakdown and asns_breakdown arrays: id is its calculated_windows.list_id, and entries names every breakdown (country, region, city, asn, country_asn, city_asn) and pool list with the number of rows the window keeps (the [payload] cap, or fewer). breakdown_entries and pool.list_entries, the full row counts, stay. So a list shared by builds (contract K2) is written to and read from calculated_list_rows only, never copied into each build's parts. A breakdown is the first rows rows of its dimension by position; a pool list is picked from its dimension's rows (geo from the city rows, countries_breakdown from the country rows, asns_breakdown from the ASN rows) as aggregate.pool_lists() picks it: rows with IPs, most IPs first, then by Python's str() of the row. store.read, store.read_parts, snapshot-export and the local API fill every v3 window back (parts.fill, one query per read), so they return the v2 window byte for byte, key order included; only schema_version says 3. A list with fewer rows than a window keeps fails the read. The rows of a list are checked (successes at most completed) when they are inserted, as the calculation validates each group before persisting it; a stored v3 window must name an integer list id and non-negative row counts. Builds stored as v2 keep their rows in their parts and read as before. The website API reads v2 and v3 (API-LISTS-1) and must be deployed first.

Read isolation. store.read_parts (the local API) runs REPEATABLE READ, so its head, parts and list rows come from one database snapshot. store.read and snapshot-export run READ ONLY at READ COMMITTED: each statement has its own snapshot. They are still safe: a build's list rows are collected only once no calculated_windows row references them, a build's windows are deleted only by discard, and discard first drops the build's parts partition, which waits for any reader holding a lock on calculated_snapshot_parts.

Grants for serve. A narrow database role for the local API needs SELECT on calculated_snapshots, calculated_snapshot_parts and current_calculation, and since payload v3 also on calculated_list_rows, place_names and asn_label_names (the rows that fill a v3 window and their labels). It never needs the raw tables (ip_observations stays denied).

Network summaries in the head (payload v4, contract K9)

Since payload schema_version 4 the head carries networks: one entry per network (a (provider, kind) pair), ordered by provider, then kind, computed over every product group of that network (all its countries) by the rules one group uses (calculated/network.py). A reader of the head alone gets every figure the site shows for a network; the product parts, the group lists, the typed rows and the serve answers are unchanged. The entry uses a group's key names: id <provider>:<kind>:network, product_id and product the headline product (the most 30d completed requests; on a tie the lowest id), provider, name, kind, cohort network, criteria (country null, requested_countries the groups' requested countries in upper case, groups their number), census, pricing and evidence (30d values) of the headline product's census-pulse group (else its busiest group; census is then empty), outages the newest 50 of the census-pulse groups, and windows (24h, 7d, 30d).

A network window is computed over the union of its groups: metrics is timed() over all their bucket rows with every pulse slot of the census-pulse groups (requests summed, success time-weighted, light-load latency merged from the histograms, never an average of percentiles), latency under load from the load factors of the union's latency-target rows, uptime and pulse-slot coverage from the census-pulse groups' batches, outages and tested countries; uptime, tests (sums), targets (each target's metrics and readiness; browser targets with their browser object, while browser rows change no network-level figure), series (288 five-minute points for 24h, daily points for 7d and 30d) and success_delta follow the same rules. pool.unique_ips and each series point's unique_ips are distinct over the union's observations in the window, counted in the database (hourly.bucket_ips() with the window as one point; no IP set in Python, so the incremental calculation reads no observation for them). pool.new_ips and observations are sums, churn_rate new over unique IPs, the shares (recurring_share, datacenter_asn_share, classification_coverage, geo_accuracy, enrichment_coverage) the groups' weighted by their unique IPs (null when none has one), daily the most days and the sum of the groups' daily unique IPs. countries, regions, cities and asns (also in daily) are the row counts of the window's network list (K10), and lists is {"id": its list_id, "entries": its full row counts}, which breakdown_entries and pool.list_entries repeat (lists null without one); the rows stay in the K10 tables. estimated, when a group has one, sums the groups' estimated unique IPs and requests and their hours per released hour (start, unique_ips, requests), and breakdown_scale is estimated over distinct unique IPs. Until NET-SUM-2 a window has scores {}, overlap null and readiness partial with completed requests (else unavailable). It has no benchmark, previous_period, census_overlap, latency detail, evidence_sources, unavailable, roles or list rows. A v4 build must not become current under a website API that cannot read v4.

Network scores, ranks and overlap (payload v4, contract K9)

Each network window has scores {"balanced": score}, scored against the networks of the same kind and window by the rules one group's window is scored with (calculated/network_scores.py, calculator.score_window()): every component is 100 × its value over the best ready, fresh value of the networks (lower is better: best over value). The inputs are product_inputs() on the network pool (coverage from pool.daily.unique_ips, diversity from the window's network place counts in pool.daily), the headline product's pricing, the window's measured uptime and the headline group's evidence of that window, whose validity also caps the score's; reliability and speed come from target_score() on the network target metrics, each target fresh by its own last observation. The headline product's effective methodology gives the required targets, weights, minimum requests and coverage and the validity hours; time coverage is metrics.coverage as published (pulse-slot coverage when the network has a census-pulse group, else bucket coverage). rank ranks the networks of the kind (none when fewer than two are ready or retained); previous_rank, scored_at, valid_until and a retained or expired score follow the group rule from the previous build's head networks (same id and window). Only the balanced profile is published, and network targets carry no score. readiness is ready when the balanced score is ready, else partial with completed requests, else unavailable.

overlap is {"exclusive_share", "shared_share", "compared_products", "peers", "as_of"} over the network's distinct IPs in the window against every other network of its kind with IPs (compared_products of them): shared_share is the share of its IPs any of them also has, exclusive_share the rest, and peers lists, in provider order, each such network that shares at least one IP (provider, product_id its headline product, shared_ips, ips_ours, ips_theirs). Without IPs both shares are null, compared_products 0 and peers empty. The IPs are the window's observations of the network's runs inside the window, the set pool.unique_ips counts, so ips_ours equals it; one database statement per window counts them for every network (no IP set in Python). as_of is the cutoff the overlap was counted at. The 24h overlap is counted every build; the 7d and 30d overlaps once a UTC day (owner decision): a build whose previous published head holds them for the same networks, counted the same UTC day and not after its cutoff, carries them unchanged, so they can be up to a day old and their ips_ours is the pool of their own as_of.
