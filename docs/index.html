1. Run a test

From the standalone framework directory, install the locked dependencies. The MMDB stays in the local db-ip directory and is not included in wheels, source distributions or Git.

uv sync --locked --no-editable
uv run --no-editable proxy-index targets

# Supply a gateway privately through your environment:
# PROXY_URL accepts http://user:password@host:port or socks5://user:password@host:port.
# Percent-encode reserved characters in URL credentials.
uv run --no-editable proxy-index run \
  --target generic_http --requests 5000 --concurrency 100 \
  --provider example --product residential_rotating \
  --country US --location dubai --output results

Use generic_https for TLS tests. Both HTTP and SOCKS5 gateways support optional username/password authentication. SOCKS5 resolves the destination through the proxy. For static PROXY_URL runs, --country records requested geography; targeting flags must already be present in the supplied credentials.

Shifter Residential is implemented. Use --provider-config configs/shifter.toml --credentials-file .secrets/credentials.toml. The private file uses owner-only permissions and is excluded from Git, packages and remote uploads; copy credentials.toml.example to set up your own. Add optional overrides such as --param country=us. See the adapter guide, session policies and Python examples.

Set --url http://ip-info.com/myip (or another plain-IP echo endpoint) per test. For Generic HTTPS, use an HTTPS URL. Python callers pass RunConfig(target_url=...). IP Info is the default if omitted; the effective URL is recorded in each summary.

Defaults: 100 requests, concurrency 10, timeout 15 seconds, no rate cap. Optional --rate 50 paces request starts. There are no automatic retries, redirects, cookies or connection reuse. Response bodies are limited to 512 bytes, plus one byte to detect overflow.

A request succeeds only when the response is HTTP 200 and its complete trimmed body is one valid IPv4 or IPv6 address. HTTPS verifies the target certificate. Only Generic HTTP contributes IP observations and pool uniqueness metrics.

2. Call the runner from other code

import asyncio
import os
from proxy_index import JsonSink, ProxyConfig, RunConfig, run

async def measure():
    return await run(
        RunConfig(
            target="generic_http",
            proxy=ProxyConfig.from_url(os.environ["PROXY_URL"]),
            requests=5_000,
            concurrency=100,
            provider="example",
            product="residential_rotating",
        ),
        JsonSink("results"),
    )

summary = asyncio.run(measure())
print(summary.to_dict())

A future methodology layer chooses the target and configuration and invokes this function. It decides cadence, geography, budgets and which results to enrich/publish. Those policies do not live inside targets.

Pass an asyncio.Event as stop= for graceful interruption; it returns a partial summary with status="cancelled". Cancelling the caller task also saves partial results, then propagates cancellation. CLI SIGINT/SIGTERM does the former and exits 130. A normally completed measurement exits 0 even when proxies fail; configuration, storage or framework failures exit 2.

3. Result contract

Each invocation creates a unique run directory. summary.json is written last and serves as the completion marker. Interrupted or failed runs are explicitly marked; a directory without a summary is incomplete.

summary.json

Schema/framework/target versions; sanitized configuration; UTC start/end; requested, started, completed, cancelled and not-started counts; successes, errors by category, HTTP statuses, body bytes, throughput, latency percentiles (latency_ms: p50, p90, p95, p99), mean success latency (latency_mean_ms, from the 1 ms histogram bins, to 0.1 ms; null with no successes; absent from summaries written before it existed, which readers treat as unknown) and exact HTTP unique IPs. Includes five-minute counters/histograms and the IP file checksum/row count.

ips.jsonl.gz

One row per run × five-minute UTC bucket × normalized IP. Each row contains schema_version, run_id, bucket_start, ip, count, first_seen and last_seen. HTTPS produces an empty IP file and null unique_ips.

Definitions that downstream consumers must preserve

  • requested = started + not_started; started = completed + cancelled; completed = successes + total_errors. On a framework failure, “cancelled” includes requests aborted by that failure.
  • Latency is measured with a monotonic clock from request execution through complete body receipt, including connection setup and TLS, excluding runner queue/rate waits. Percentiles include successes only; absent samples produce nulls.
  • The sparse ceil_ms_v1 histogram stores [upper_bound_ms, count] bins with 1 ms resolution. Percentiles use nearest-rank selection and round upward by less than 1 ms. Merge bin counts before calculating combined percentiles.
  • Throughput is completed requests divided by elapsed run time. response_body_bytes counts bytes read from bodies, including failed responses; it is not provider-billed traffic or total TCP/TLS bytes.
  • Observations belong to the bucket in which the response completes. UTC is anchored to the monotonic run clock so clock corrections do not reopen flushed buckets.
  • Deduplicate IPs across buckets/runs when computing window or fleet uniques. Adding per-run unique counts would overcount recurring addresses.
  • Error categories: proxy authentication, proxy connection, DNS, TLS, timeout, HTTP status, invalid body, oversized body, connection and protocol. Returned error data never includes raw exception messages or credentials.
  • Every failed request has one verdict, counted in challenges, blocks, timeouts or proxy_errors (or a plain error). A block is the target refusing us: HTTP 403, 429, 451 or a block page. Proxy-side failures are never blocks: 407, 502, 509, and 503/504 without a challenge or block page, a failed CONNECT, a reset or dropped connection and a gateway name that does not resolve are proxy_errors; no answer in time is a timeout. Other target statuses (404, 500, …), TLS failures and unusable bodies are plain errors. Block rate is published next to success and stays inside reliability; it is not a separate score component.

Memory scales with distinct IPs, the current bucket, a bounded export backlog and small aggregate histograms. A fixed pool bounds active requests. Bucket serialization runs on one background writer; slow storage delays new requests instead of blocking the event loop during existing requests. No list of all request objects is retained.

4. Enrich from the existing MMDB

The supplied file is db-ip/dbip-full-2026-09-14.mmdb, identified internally as DBIP-Location-ISP (compat=Enterprise). It is a local copy from the existing DB-IP folder. Its SHA-256 is ca81b1d51dd4e502bc9c9568b5c3dd7a865094f7c29ed6b63947d1763ac6c4f2.

uv run --no-editable proxy-index db-info
uv run --no-editable proxy-index enrich results/RUN_ID

# Select a different local release explicitly:
uv run --no-editable proxy-index enrich results/RUN_ID --mmdb /path/to/release.mmdb

DBIP_MMDB is the environment alternative. Automatic discovery takes db-ip/dbip-full.mmdb, the one file proxy-index dbip update replaces with each newly verified release (the daily update on the manager and on pulse nodes: README, “Daily DB-IP update”); without it, it requires exactly one file, and with multiple releases you select one explicitly. The database is memory-mapped. A bounded cache reuses lookups; no geolocation API requests are made.

Enrichment validates the IP artifact checksum, then writes a separate compressed JSON Lines file and release report. Original measurements are preserved. Each row records the release checksum and country, region, city, coordinates, ISP, organization, ASN, connection type and usage type. Missing records remain unknown. Re-enriching with another MMDB creates another version; repeating the same release refuses to overwrite existing output.

Enrichment is optional and only accepts Generic HTTP pool results. The source MMDB is a separate licensed data asset; the framework’s MIT license covers its code. Field definitions follow the DB-IP MMDB specification.

5. Add or change a target

Targets expose an ID, version, engine, pool eligibility, build_request() and assess(status, body). Register a new implementation in a TargetRegistry and pass it to run(..., targets=registry). Adding a built-in also registers it in the default registry; the CLI automatically lists it. Change the target version whenever measurement semantics change.

from proxy_index.targets import EchoIpTarget, TargetRegistry

targets = TargetRegistry()
targets.register(EchoIpTarget("my_ip_target", "https://example.test/ip"))
# await run(config_for_my_ip_target, sink, targets=targets)

Transport.execute(target, *, context=None) returns a normalized outcome. Since v0.2 the runner supplies a RequestContext with run, request and worker identities for provider sessions; custom transports must accept this keyword. A future browser adapter can implement the same execution protocol through transport_factory; browser targets can carry additional settings in their own implementation. Playwright is not needed or installed for baseline targets. Custom sinks implement start, observations, finish and abort. Observation writes are serialized on one background thread; finish runs only after they complete.

Import transaction: validate counters/checksums → COPY observations into staging → insert run/history → import optional MMDB releases → update cached metrics → commit. Imports are serialized with a database advisory lock; measurement requests run independently. Invalid data rolls the entire import back. Replays validate the same content and can attach a newly generated enrichment release without counting measurements again.

Raw-data archive (ARCHIVE-1): raw measurement rows are meant to stay 30 days in the database (partitions.RAW_DAYS); the calculator reads no further back, so the 30-day window's previous_period has no rows and its success_delta is null (the 24-hour and 7-day comparisons are unchanged). proxy-index archive export --date YYYY-MM-DD --database-file … --out DIR writes one UTC day into DIR/YYYY-MM-DD.tar.gz and deletes nothing. A batch belongs to the UTC day of its scheduled_for, a run to its batch's day (a daily test, which has no batch, to the day it started), and every row tied to a run or batch goes with it: the batches, batch runs, runs, buckets, geography buckets, IP observations, run enrichments, estimated hours and run roles of the day, the day's tape events, and the dimension rows they reference (providers, products, regions, countries, targets, nodes without their token hash, IPs, enrichment, places, networks, DB-IP releases, pools and scopes), so a file loads on its own. The file is a gzip tar: manifest.json first (format and version, day, storage and calculated schema versions, and per table its role, columns, rows, bytes and sha256), then one CSV per table in load order, each from COPY … TO STDOUT (FORMAT csv, HEADER) ordered by primary key, all from one snapshot in UTC/ISO settings; the same rows give the same bytes, so the file can be re-checked and re-imported with plain tar and COPY. proxy-index archive restore --file … --database-file … loads a file into a database of the same storage schema version in one transaction: every CSV's sha256 and row count must match the manifest, ids are kept, rows already present stay as they are (a repeated restore inserts nothing), and it refuses (exit 2, nothing changed) when the database's ids mean other rows (the same product id, IP id, run id or batch slot holding other values): restore into the database the file came from, or into an empty one. Links to batches outside the file (a retried census, a tape event of another day's batch) become NULL; missing partitions are created and identity sequences move past the restored ids. Uploading the files, deleting archived days and the daily job follow in the next steps of the task.

Calculated results, scores and website API

The source history stays in schema v5. The additive calculated schema (v7) has its own version/checksum; db-migrate upgrades an unmodified calculated v2 to v6 layer in place: calculated/migrate_v5_v6.sql moves every breakdown row into its build's partition and calculated/migrate_v6_v7.sql moves the breakdown names into the shared name lists, each step verified against a copy before committing. No IP membership is stored per reporting window; observations supply exact distinct counts. A calculation reads a repeatable snapshot of history and writes all prepared results in one transaction. Payloads are kept for the current build, every published build and the two newest unpublished drafts; calculate and snapshot-publish prune older draft payloads (their typed rows remain until the next publication, whose retention deletes the pruned draft). Build retention. After every publication (calculate --publish and snapshot-publish, in the same transaction, after the draft prune) the database keeps the current build, the newest published build of each UTC day of the last 30 days, and the drafts whose payload the prune kept; every other build is deleted with its snapshot, windows, breakdown partition, series, scores, components, reasons and overlaps. Days count back from the UTC day of the current build's cutoff, not from the clock, so a paused calculator loses nothing. RETAIN_DAYS (30) and RETAIN_PER_DAY (1) in calculated/store.py set the defaults. proxy-index calculate-expire applies the rule now; --dry-run only reports, read-only, the builds it would keep and delete with the rows and approximate bytes per table; --days and --per-day override the numbers. It also runs on a calculated v5 database, so on a large database expire first and migrate afterwards: the migration then moves only the kept rows. Deleted rows leave dead space until VACUUM reuses it; dropped partitions free theirs at once. Creating a build's partition (every calculate that writes a build) and dropping expired ones (every publication and calculate-expire) lock calculated_breakdowns exclusively until that transaction commits: readers of it and of calculated_breakdown_details and current_breakdowns (Postico, typed-row queries) wait meanwhile. The website API's refresh also reads calculated_breakdown_details, so it waits for that lock too; meanwhile the API keeps serving the version it loaded before.

Browse views (Postico, no payload reads). calculated_snapshots_list: one row per build with cutoff, methodology, published, is_current, content hash and payload_bytes (the stored, compressed size, taken from the TOAST pointer without fetching the payload). current_windows: the current build's windows with provider and product names. current_breakdowns: the current build's breakdown rows with provider, product, cohort, window, dimension name, country/region/city, ASN name and usage type, counters and success rate. Open these instead of calculated_snapshots, whose payload column is megabytes per row.

All windows are half-open [start,end) and end on a five-minute boundary. A cutoff inside a five-minute bucket moves to that bucket's end when the bucket holds data and every run with data in it had finished by the requested time (always so for a calculation without --as-of: a run is stored only once it has finished), so a run that ended just before the calculation is in it; otherwise it moves to the bucket's start. A bucket is in a snapshot whole or not at all. Such a cutoff can be up to 5 minutes past the clock, so an open outage's duration and downtime can run up to 5 minutes ahead of it, and score and evidence expiry can take effect up to 5 minutes early. Latency bins are merged before nearest-rank percentiles at 1 ms ceiling precision. Window coverage (readiness) is the fraction of five-minute slots with requests, or of pulse slots for census/pulse cohorts, not measured uptime: pulse slots are the product's done pulse runs, filled by one with at least one request, also when every request failed (the provider was down: it lowers success and uptime and opens an outage, it is never a gap). A run is only ever failed by our side (no node, never started, went silent, node shut down or erred, upload rejected), so failed runs and operator-skipped or killed batches are not slots and never count against the provider. Daily charts group successive 24-hour intervals from the window start. Every request counts for every metric: census, pulse and load runs alike feed success, blocks, timeouts, exit IPs, breakdowns and bytes, and minimum_requests counts every request of a required target; run roles are display labels only. New-IP counts use lifetime product first-seen timestamps; recurrence counts IPs seen on multiple UTC dates. DB-IP enrichment uses one identified release, with unknown values preserved.

Time-weighted metrics and latency under load

A window is split into time slots: the cohort's pulse interval (the shortest pulse_interval_minutes of the pulse-enabled targets) made a whole multiple of the 5-minute stored bucket, lcm(interval, 5): 30 minutes in production, 10 in staging (2-minute pulses), so no census request lands in a slot it did not run in. Pulse and load requests belong to their batch's slot, census and unbatched requests to the slot they ran in. Every slot with observed requests weighs the same: success_rate is the mean of the slot success rates, successes ÷ requests observed in the slot (nothing is counted for requests nobody observed); request_success_rate keeps successes ÷ requests. Latency is measured on one target only, latency_target (default generic_http, the census target): light-load and under-load latency, the speed score, breakdown latency and the load factor all come from it. Other targets count for success, blocks, timeouts, IPs, authenticity, DC ASNs, bytes and uptime; their targets.<id>.metrics.latency_ms and latency_under_load_ms hold nulls, with latency_reason. Light-load latency (latency_ms, pulses only) merges the slots' latency histograms after normalising each to weight 1 and reads p50/p90/p99 from the merged distribution; a slot with fewer than [slots] min_latency_successes (30) successes does not vote. Percentiles are never averaged. Breakdown latency is light-load latency.

Census overlap. A pulse or load run of a product that ran while a census of the same product was running (any country: account and node are shared) is marked during_census, derived at calculation time from the stored run start and finish times (the ingested run's, else the orchestrator's). It still fills its slot and counts for uptime, outages, down slots and every request metric, but it is left out of light-load latency (breakdowns included), of the time-slot success (a slot votes with its other requests; one left with only such pulses votes 0 if every request in it failed and does not vote otherwise, time_slots.skipped_during_census), and of the load factor (it needs a clean load run and a clean reference pulse, otherwise the newest earlier factor carries forward, latency.regions[].factors.excluded_during_census). Each window publishes census_overlap: pulses and targets.<id> with clean and during_census (runs, requests, successes, request_success_rate, success_rate, latency_ms), load, census_batches and basis; metrics.latency_reason says why light-load latency is missing.

In every pulse slot of the census target each product also runs one wave of census_concurrency requests (1,000 in production, 100 in staging) at census concurrency in every runner region's reference country: a test_batches row of kind load with the pulse's scheduled_for, started load.delay_seconds (60) after the pulses so the reference pulse is not measured under its own load wave. Like every scheduled test it sends only the country parameter. The orchestrator picks each region's reference once per UTC day, with the day's first pulse plan, and stores it in load_references: the fastest enabled country tested from the region over the trailing load.reference_days (7), by the light-load p50 of its census-target pulses that did not run during a census (every product weighing the same; at least load.reference_min_successes, 300, successes; ties by country code; basis fastest); an operator override (load.reference_overrides, override); without enough history the region's default (load.reference_defaults: nyc3 US, fra1 DE, lon1 GB, ams3 NL, tor1 CA, sgp1 SG, blr1 IN, syd1 AU; staging fra1 RO; default); else its first enabled country (first_enabled). load.enabled switches the wave off. Per percentile, factor(R, t) = load latency ÷ pulse latency of region R's reference country in slot t, and every country's latency under load is its pulse latency(C, t) × factor(region of C, t). A slot without a usable load run (both runs need min_latency_successes successes) takes the region's newest earlier factor in the window; without one that country's slot has no under-load value, and a window without any has null with under_load.reason. The window value is the mean over slots and countries. Census latency never makes a factor. Load runs count for every request metric, not for light-load latency, slot coverage or uptime.

Worked example: fra1's reference country is RO. In the 18:00 slot the RO pulse (100 requests) has a p50 of 600 ms and the RO load wave (1,000 at once) 900 ms, a factor of 1.5. The Bulgarian pulse in that slot (BG is tested from fra1) has a p50 of 800 ms, so Bulgaria's latency under load at 18:00 is 800 × 1.5 = 1,200 ms. nyc3 has its own reference and factor for the US, Mexico and the rest of its countries. If fra1's 18:30 load wave fails, 18:30 uses fra1's 1.5 of 18:00.

Scores are a ratio to the leader

Every sub-score compares a network with the best network of the same kind (the product's kind, or its name when none is set) in the same window. Higher-is-better values score 100 × yours ÷ best; lower-is-better values (speed: p50 latency under load; value: price per GB) are flipped to 100 × best ÷ yours. Scores are clamped to 0–100, so each component's leader scores 100. Leaders are found again on every calculation. A network alone in its kind is its own leader and scores 100 on every ready component. Only ready, freshly measured components set the best; incomplete, retained, expired and historical scores never do.

Shares are per unique exit IP over every request in the window; IPs without the DB-IP field (country or usage type) are left out of numerator and denominator, so incomplete enrichment never blocks a component (enrichment_coverage and classification_coverage stay published). There is no blocklist term and no claim-gap input. Prices are effective-dated metric_evidence: price_per_gb_lowest (scored) and price_per_gb_entry (the smallest plan's rate), naming the product by provider and product with cohort "*"; the newest record in effect at the cutoff is published per product as pricing (currency, lowest_per_gb, entry_per_gb, effective_from, valid_until, sources). Without a price, value (and the composite) has no value.

Pool counts are the average of daily (24-hour) counts over the window's days with observations, so a new network measured for a few days compares fairly with one measured for the full 30-day window. Window totals stay in pool for display; the daily averages are in pool.daily. The composite is the weighted mean of the eight ratios with the profile's weights and maps to a grade. Every component's inputs carries the raw value, the leader's raw value best and the number of ready peers (diversity per dimension, product reliability and speed per target), so every score can be reproduced from the snapshot.
