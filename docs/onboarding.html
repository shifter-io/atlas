24-hour network onboarding

A manually armed campaign that reuses Test #1’s Generic HTTP tester, keeps every successful IP observation, and stores results outside the website and normal measurement database.

24 roundsAbsolute UTC hourly schedule
8 servers249 assigned countries/territories
1 countryAt a time on each server

1. Create one shared campaign

Run from the proxy-index/ checkout. Install its dependencies with uv sync. All commands below use the source checkout explicitly, avoiding an older installed wheel.

uv run --no-editable proxy-index onboarding plan \
  --provider-config configs/shifter.toml \
  --product residential \
  --start 2027-01-01T22:00:00Z

Replace the example start with a future whole UTC hour. The command prints the path to campaign.json under onboarding-networks/<provider>/<product>/<campaign-id>/. Create this manifest once. Copy the same manifest and public provider configuration to all eight servers; keep the manifest in that same relative folder structure.

The manifest freezes country order, 24 scheduled timestamps, the exact end timestamp, provider configuration checksum, framework version and census rule version. Provider configuration changes require a new campaign. It contains no credentials.

Parallel or sequential regional campaigns

onboarding plan --execution-mode parallel is the default: all eight regions share one 24-hour window, preserving the existing version-1 manifest behavior. --execution-mode sequential creates a version-2 manifest spanning eight days. Each region owns one non-overlapping 24-hour window, with 24 hourly rounds over its existing ordered country list. Both modes schedule all 249 countries 24 times: 5,976 country jobs.

proxy-index onboarding plan \
  --provider-config configs/geonode-onboarding.toml --product residential \
  --start 2027-01-01T08:00:00Z --execution-mode sequential \
  --region-order nyc3 tor1 lon1 fra1 ams3 sgp1 blr1 syd1 \
  --concurrency 1500 --processes 4 --timeout 10 \
  --target-url http://checkip.amazonaws.com/ --retry-http-469

Replace the example date with a future whole UTC hour. The region order must contain each region exactly once; when omitted, the configured regional order applies. The manifest freezes the order and overall window. Each regional window is derived from that order, never from process launch time. Arm the same manifest on all eight servers before their scheduled windows. Waiting schedulers keep heartbeats but start no request workers until their own day. Each region enforces its own deadline, so backlog cannot spill into the next region’s day. Keep all hosts’ clocks synchronized and inspect active worker counts during handoffs.

Changes to timing or retry policy require a new manifest. Preserve interrupted runs and missing-job evidence; a terminal job is not necessarily a completed measurement. A restart must not overlap another region’s reserved window. If recovery requires moving the schedule, stop only affected assignments, preserve data, and plan full replacement windows rather than backdating or shortening a region.

Continuous checks and daily private backups

PYTHONPATH=src .venv/bin/python -m proxy_index.onboarding.health \
  --manifest <campaign.json> --inventory <private-inventory.json> \
  --output .state/network-monitor --watch

PYTHONPATH=src .venv/bin/python -m proxy_index.onboarding.backup \
  --manifest <campaign.json> --inventory <private-inventory.json> --region nyc3

The read-only watcher refreshes the existing monitor and writes campaign-audit.json every ten seconds, plus private alert receipts at most once per minute. It checks regional windows, overlaps, heartbeats, service state, clock offsets, disk, memory, backlog, incomplete jobs, and active-run 469/other error rates. It does not send notifications or repair runs by itself; pair it with an operator or scheduled agent that reviews alerts, finalized summaries and chunks, resolves faults, and verifies each handoff. The local watcher and retrieval need the local device awake; remote campaign scheduling runs independently.

After each region closes naturally and its process exits, run the backup command for that region. It uses a resumable, bandwidth-limited transfer, preserves remote originals, compares every local file’s name/size/SHA-256 with the remote tree, and validates every observation chunk, summary, job count and row count. A failed transfer keeps staging for retry. A backup can be intact while its measurement is incomplete; receipts distinguish these states. Only when all eight regional measurements and backups verify does it produce the combined export and backup/complete.json. Inspect the final 5,976 completed jobs, totals, export checksum and private export/report.html; never publish the observations or reports.

Ephemeral hourly rounds

--execution-mode ephemeral creates a version-3 manifest for campaigns that run every hourly round of every region on its own fresh node. The manifest keeps the 24 hourly rounds and all eight regional country lists. Its default concurrency is 2,000 requests per country; --concurrency overrides it. ends_at is the last round's start plus one hour plus --grace-hours (default 48, range 1–168). It bounds observation validity only and never stops a round. --allow-current-hour accepts the current whole UTC hour as the start, for an immediate test; past hours are always refused.

proxy-index onboarding plan \
  --provider-config configs/shifter.toml --product residential \
  --start 2027-01-01T08:00:00Z --execution-mode ephemeral --grace-hours 48

proxy-index onboarding round \
  --manifest <campaign.json> --region lon1 --round 0 \
  --provider-config configs/shifter.toml --credentials-file .secrets/credentials.toml

proxy-index onboarding verify-round --manifest <campaign.json> --region lon1 --round 0

onboarding round runs exactly one round of one region: its countries in manifest order, one at a time, with the census rule and no request cap or deadline, so every country runs to its natural end. Before any traffic it checks the provider configuration's SHA-256 against the manifest and every country's proxy targeting. It may be started up to 300 seconds before the round's scheduled time and waits for it; an earlier start is refused. A node runs a round once: an existing checkpoint refuses a replay.

The round writes regions/<region>/rounds/<NN>/round.json beside its country folders and checkpoints it at least every 5 seconds while a country runs. Its status is armed, running, completed, stopped or failed; its jobs use the same fields as state.json. SIGTERM or SIGINT marks the active country interrupted and the rest not_started_deadline; an error records failed the same way. Exit codes: 0 when the round finished, whatever the providers returned; 130 when stopped; 1 on our-side error (only the error type is printed).

onboarding verify-round reads one collected round without writing anything. It verifies every chunk's SHA-256, rows and time bounds up to its country's finished_at, rejects .partial and unregistered chunks, and reconciles rows, successes, unique IPs and request counts with each country summary. It prints per-country status, requests, successes, errors, observations, unique IPs, bytes up and down and duration, with no IP addresses, and exits 0 when complete, 3 when incomplete and 1 on error. The regional run command and versions 1 and 2 are unchanged.

Use the same campaign, substituting the server’s region. Credentials use the existing owner-only TOML mechanism or the provider’s credential environment variables.

  --credentials-file .secrets/credentials.toml \

--concurrency1,000Maximum in-flight requests for the active country. Positive integer; may differ per server.

Keep the process running in a supervised terminal or service. Starting it before the campaign start arms it; no proxy requests run until the scheduled start. Validate synchronized server clocks before the first live run. On Linux, check timedatectl show -p NTPSynchronized --value. The schedule uses UTC, independent of server display timezone.

Only implemented adapters can run. Shifter is currently registered. New network authentication and targeting belongs in a reusable provider adapter, not in the onboarding scheduler.

3. Scheduling, ordering and the hard deadline

Every whole-hour boundary makes a new round eligible. A durable, precomputed FIFO preserves each round’s country order. If a round overruns, finish its countries before starting the next round. No country runs concurrently with another on the same server.

Campaign start       Day 1 22:00 UTC
Round 0 scheduled    Day 1 22:00 UTC
Round 1 scheduled    Day 1 23:00 UTC
…
Round 23 scheduled   Day 2 21:00 UTC
Campaign deadline    Day 2 22:00 UTC

If round 0 ends at 23:08, round 1 starts then and retains 23:00 as its scheduled time. Round 2 remains scheduled for 00:00. Each country’s actual start is recorded separately. Finishing all available work early leaves the process waiting for the next boundary, including the final deadline.

The deadline wins over the backlog. At 24 hours, new requests stop, outstanding requests are cancelled and responses at or beyond the cutoff are excluded. Queued work becomes not_started_deadline. Local file finalization can finish after the cutoff; proxy testing cannot.

Backward wall-clock changes do not extend a running campaign. Real systems may wake slightly late; recorded start delays make that visible.

4. Shared census rule, version 2

completed_requests >= 1000
AND
unique_successful_IPs * 2 < completed_requests

All completed failures count toward the sample and denominator. Only successful IP responses contribute unique addresses. Exactly 50% does not stop. The ratio resets for every country run.

An all-error country stops issuing at 1,000 completions and retains the no_success classification. Existing time-based no-success and stalled-network protections remain. In-flight requests normally finish after the stopping rule fires; at concurrency 1,000, up to 999 more requests can already be outstanding.

The correction is shared with regular Test #1. New normal runs record census rule version 2 and the completed-request basis; old results keep their original metadata. Count-limited tests retain their existing behavior. The normal tester’s existing timeout defaults are unchanged; onboarding defaults to 10 seconds.

Geonode: HTTP 469 and census retries

Operational notice, 7 October 2026. Geonode returned HTTP 469 with an explicit request-rate-limit message. Treat this separately from 465 strict-targeting unavailability. Changing the HTTP destination from ip-info.com/myip to checkip.amazonaws.com/ did not remove the 469 responses. The exact provider limit and its scope have not been established.

Agreed counting policy

census_requests = completed_attempts - HTTP_469_responses
stop issuing when census_requests >= min_sample
                  AND unique_successful_IPs * 2 < census_requests
reported_469_percentage = 100 * HTTP_469_responses / completed_attempts

A 469 response must not consume the census minimum sample or lower its unique/request ratio. Issue a replacement request while the run remains eligible to continue. Preserve every 469 in raw attempt, error, status-code and traffic counters; all other completed failures still count in the census denominator. Exactly 50% does not stop. Deadlines, explicit attempt caps and operator stops still apply. In-flight cancellations are not completed attempts.

Enable and verify explicitly

The 0.9.4 implementation tested on the fleet uses RunConfig(retry_http_469=True, stop_rule="unique_ratio", ...). It is opt-in; the default retains rule version 2. The tested policy records census_rule_version=3, census_ratio_basis="completed_requests_excluding_http_469", and summary counters census_requests and http_469_responses.

These configuration comments do not enable the policy. Framework 0.9.5 exposes --retry-http-469 on onboarding plan; it freezes the policy in the manifest and passes it to every country run. Deploy the intended build and verify the saved metadata and counters on all eight servers before relying on it. Do not assume that selecting the Geonode provider enables retries, or reinterpret older rule-2 results.

Observed bounded test

Eight servers ran simultaneously with 2,500 concurrency and four worker processes each, rotating gateway port 9000, strict country targeting, and http://checkip.amazonaws.com/. The two-minute maximum diagnostic recorded 1,320,321 HTTP 469 responses out of 1,443,709 completed attempts (91.45%), including replacement attempts. The 123,388 non-469 attempts yielded 116,625 successful observations and 6,763 other failures (5.48% of non-469 attempts).

Six probes reached the census ratio threshold; New York and Bangalore reached the two-minute deadline. This was one representative country per server, not a completed 249-country or 24-hour campaign. Immediate retries were unpaced and generated many rapid 469 responses; retrying preserves the census denominator but does not resolve the provider limit. These percentages are not directly comparable with older probes that counted 469 toward the stopping rule and therefore stopped earlier. No new 24-hour campaign was started by this diagnostic.

Keep all observation files, real exit addresses, credentials, raw logs and private reports outside Git. Only this aggregate operational notice belongs in the repository. See the rotating census configuration and the general provider example.

5. Check progress and resume

uv run --no-editable proxy-index onboarding status \
  --manifest onboarding-networks/shifter/residential/<campaign-id>/campaign.json \
  --region fra1

Status reports the active country, live counters, due queue depth, regional settings, deadline, round duration, start delay and peak process memory. Country summaries include errors, throughput and the shared runner’s measurements. The initial performance target is 30–40 minutes per regional round.

Stop gracefully with SIGINT or SIGTERM. To resume, run the original command with --resume. Omit concurrency and timeout to reuse saved values; conflicting overrides are rejected. Completed countries are never replayed. A country interrupted by a crash keeps its committed chunks and is marked interrupted before advancing to the next country. Partial diagnostic counters are identified as such. Closed campaigns never restart.

Only one process can own a campaign/region on a local filesystem. Different servers must be assigned different regions; there is no distributed lock between separate machines. Storage or configuration failures stop the regional process, while ordinary proxy failures remain census outcomes.

6. Observation format and private files

Each successful response writes one compact JSON line, including duplicates. The country code is the requested country, not geolocation. IPv4 and IPv6 are both supported.

{"ip":"203.0.113.42","country_code":"us","round_scheduled_at":"2027-01-01T22:00:00.000Z","country_started_at":"2027-01-01T22:04:12.381Z","observed_at":"2027-01-01T22:04:12.947Z"}

Chunks rotate after 100,000 records or five seconds of pending records. A bounded queue applies storage backpressure. Each committed chunk has a checksum and row-count sidecar. Directories are owner-only and data files use mode 0600.

onboarding-networks/<provider>/<product>/<campaign-id>/
  campaign.json
  regions/fra1/
    state.json
    rounds/00/de/
      observations-000001.jsonl.gz
      observations-000001.jsonl.meta.json
      summary.json
    summary.json
  export/
    observations.jsonl.gz
    manifest.json
    report.html

A crash can lose the uncommitted queue and active chunk; finalized chunks remain valid. Partial files are excluded and identified in the export report. JSONL buffering is bounded, while the exact census uniqueness set grows with distinct addresses in the current country and is released between countries.

The default runtime directory is Git-ignored and excluded from source archives. Do not move captured files into another tracked folder. Onboarding never calls database ingestion, publication, or website APIs.

7. Collect and export

After the campaign, copy each server’s regions/<region>/ folder into the matching campaign directory on the collection machine. Preserve the manifest and all sidecars. The command operates on local files; it does not connect to servers or upload results.

uv run --no-editable proxy-index onboarding export \
  --manifest onboarding-networks/shifter/residential/<campaign-id>/campaign.json

The exporter locks regional folders, verifies checksums, row counts, IPs and timestamps, then streams gzip members into one observations.jsonl.gz. Python’s gzip module and standard gzip tools read this concatenated stream. Missing regions and incomplete runs are flagged; corruption fails the export. The export manifest is the commit marker and includes the final checksum. report.html opens directly without a server or external assets.

CPU parallelism for all HTTP tests

The shared runner uses spawned worker processes, each with its own Python interpreter, HTTP event loop and connection pool. This applies to HTTP, HTTPS, count tests, normal census/pulse runs and onboarding. The default --processes 0 selects the available CPU count, bounded by concurrency and request count. Use --processes 4 to select four workers, or --processes 1 for diagnostics.

Concurrency is global: --concurrency 2500 --processes 4 assigns 625 slots to each worker. One coordinator owns the request budget, rate limit, exact unique-IP set and census stopping decision. Counts from separate workers are never summed as independent unique-IP pools. Provider request/session identities remain global. In-flight work drains at normal census termination; operator stop and the deadline terminate all worker processes. A worker crash fails the run and preserves partial results.

The fleet monitor shows interval CPU use per core and per worker PID, including the coordinator. 100% for a process means one occupied core. Live RAM is summed across these processes. The saved peak_memory_mb field is the coordinator process peak; it does not include worker memory. Use the live process readings when checking whole-run RAM use. The first sample needs a subsequent sample to calculate CPU use. Network waiting can leave cores idle even when work is correctly distributed; core utilization and throughput must be measured together. Injected custom execution adapters remain responsible for their own parallelism; all built-in HTTP targets use this process backend.

Strict country targeting for onboarding

Use configs/shifter-onboarding.toml for onboarding country campaigns. It sets strict = true, preventing Shifter from substituting a broader pool when no matching exit is available. Such requests fail and contribute to census termination; unsuccessful countries have no observation rows. Every assigned country is still attempted.

The saved country code remains the requested country, not an independently verified geographic claim. Local geolocation databases can disagree with the provider. Each campaign freezes the provider configuration checksum, so distribute the exact same strict configuration to all nodes.

For a single-round calibration, scripts/onboarding-calibration.py runs the normal scheduler and stops after the final country of its first round. Later rounds stay pending by design. scripts/onboarding-verify-round.py validates and combines that round's files. Create a separate manifest for the full 24-hour campaign.

Single-country calibration and fleet monitoring

Before a full campaign, use onboarding probe to measure one country with the same census rule and individual-observation writer. A scheduled start must be a future whole UTC hour. Omitting --start starts this manual calibration immediately.

uv run --no-editable proxy-index onboarding probe \
  --provider-config configs/shifter.toml \
  --credentials-file .secrets/credentials.toml \
  --region nyc3 --country us --concurrency 2500 --timeout 10 \
  --start 2027-01-01T22:00:00Z \
  --output onboarding-networks/shifter/residential/probes/us-calibration

The probe writes state.json every five seconds while testing, plus a final summary.json and compressed observation chunks. The final measurement records total requests, successes, errors, unique IPs, throughput and elapsed tester time. total_duration_seconds also includes final file flushing. A probe has a 24-hour safety deadline by default; --max-seconds can set another explicit cap. Its output directory cannot be reused.

Keep production host addresses and SSH identity paths in the ignored, owner-only file .secrets/onboarding-servers.json. Each servers entry maps a region to host, user, identity_file and an absolute remote root. Never include this inventory in Git, a wheel or a deployment upload.

uv run --no-editable proxy-index onboarding fleet-status \
  --inventory .secrets/onboarding-servers.json \
  --output .state/onboarding-monitor --watch

The monitor uses SSH to collect service state, heartbeat freshness, current country, request/error/unique counts, throughput, queue depth, host memory, process memory and free disk. It writes a standalone index.html and snapshot.json locally. Collection repeats after a ten-second pause; SSH collection time adds a few seconds. The HTML reloads itself and displays a stale-monitor warning if collection stops.

Health states: armed/running; behind (an older hourly round remains unfinished); stale (heartbeat older than 20 seconds); failed (service exited unexpectedly); unreachable (SSH failed); not_deployed (reachable but not installed); completed/closed. A probe exceeding an hour is marked over_hour while it continues toward its stopping rule. Armed campaigns and completed-round waits also persist fresh heartbeats.

Remote helpers are project-specific: scripts/onboarding-deploy.py transfers a locally built wheel, locked dependency list, provider config and the selected credential file; scripts/onboarding-remote-probe.py starts one supervised systemd service with a 65,536-file limit and writes the private active-run pointer. They read the local inventory and never upload it. Deployment alone does not start proxy traffic.

Run each helper with --help for exact arguments. Each remote root contains active-run.json with the unit name and relative state-file path used by the monitor. On the collection machine, stop a detached watcher with the process ID in .state/onboarding-monitor/collector.pid after confirming the process identity.
